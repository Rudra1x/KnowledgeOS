# Checkpoint 1.4 — CSV Loader

## What we built
- `CSVLoader` with two strategies: `row` (each row = Document), `file` (whole CSV = one Document as Markdown table)
- **Field-value templating** — `"col1: val1 | col2: val2"` preserves column semantics
- Encoding fallback (utf-8 → latin-1) for Excel-exported CSVs
- Optional column filtering via `text_columns`
- `max_rows` safety valve for massive files
- Empty-value skip logic (NaN, blank strings)

## Core concepts

### 1. Strategy matches the data's semantics, not the file format
A CSV isn't automatically "one row = one document." The right strategy depends on how the data is used:

| CSV shape | Example | Strategy |
|-----------|---------|----------|
| Row = one entity | Products, FAQs, tickets | **row-per-Document** |
| Rows = time series / aggregate | Sales, sensors, financials | **whole-file Document** |

Ask "would a user query be answered by a *single row* or by looking at *many rows together*?" If single → row. If aggregate → file.

Get this wrong and retrieval is architecturally broken regardless of embedding quality.

### 2. Field-value templating vs. naive join
- Naive: `"Blue Widget 99 42"` — meaningless to the embedder
- Templated: `"name: Blue Widget | price: 99 | stock: 42"` — embeds semantic roles

The BGE model has seen millions of "key: value" patterns in its training. It *knows* what column names imply. Templating is a huge quality lever for near-zero effort.

### 3. CSVs are always malformed in production
Real-world CSV problems:
- Missing quotes around fields with commas
- Mixed encodings (UTF-8 vs latin-1 vs cp1252 from Excel)
- Inconsistent line endings (CRLF vs LF vs CR)
- BOM markers on UTF-8 files
- Embedded newlines in cells
- Ragged rows (row N has 4 fields when header has 5)

A production loader needs `on_bad_lines='skip'`, encoding detection, and defensive parsing. We hit exactly one of these in our test (missing quotes) — real deployments hit them all.

### 4. Pandas is the pragmatic choice
The stdlib `csv` module makes you handle quoting, encoding, and type inference manually. Pandas handles all of it in one call. For a learning project *and* production, pandas is the right layer.

### 5. Whole-file as Markdown table
When strategy='file', we render the whole CSV as a Markdown table (`| col1 | col2 | ... |`). LLMs are extensively trained on Markdown; they read tables in this format cleanly and can reason across rows. Alternative serializations (JSON, TSV, raw string) waste tokens and confuse the generator.

## Why the design choices

- **Two strategies, not one**: forces the caller to think about the data's semantics
- **Templated rows**: preserves column semantics for the embedder
- **`keep_default_na=False`**: treats "NA" as a string, not NaN — needed for FAQ / product-name columns
- **UTF-8 → latin-1 fallback**: Excel exports on Windows often produce cp1252/latin-1; a fallback saves the day silently
- **`max_rows` guard**: a 500K-row CSV would OOM the process; explicit cap is safer
- **Skip empty cells in templating**: `"name: Widget | price:  | stock: 42"` looks broken; skipping empties keeps content clean

## Interview flashcards

1. **Q:** Row-per-doc or whole-file — how do you decide?
   **A:** Ask what the queries look like. Row-per-doc when a query is answered by a single row (product, FAQ entry). Whole-file when the query is aggregate (trends, comparisons). Match strategy to query semantics; get it wrong and retrieval is broken by design.

2. **Q:** Why templating instead of just concatenating cell values?
   **A:** Column names carry semantic meaning the embedder can use. "Blue Widget 99 42" is 4 tokens with no context. "name: Blue Widget | price: 99 | stock: 42" tells the embedder *what* each value means. Small formatting change, large retrieval quality impact.

3. **Q:** What common CSV bugs would break your loader in production?
   **A:** Missing quotes around fields with commas (parser splits mid-value). Mixed encodings (UTF-8 vs cp1252). BOM markers. Embedded newlines in cells. Ragged rows. Production loaders need `on_bad_lines='skip'`, encoding detection, and per-row error logging.

4. **Q:** Why pandas over the stdlib `csv` module?
   **A:** Pandas handles quoting, encoding fallback, type inference, and malformed-row policies out of the box. Stdlib requires you to write all of that yourself. For anything beyond trivial CSVs, pandas is the pragmatic default.

5. **Q:** Rendering a whole CSV as Markdown table — why that format?
   **A:** LLMs are extensively trained on Markdown tables and read them cleanly in context. Alternative serializations (JSON with column keys, raw comma-separated) either waste tokens or confuse the generator. Markdown balances readability and token cost.
