# Checkpoint 0.5 — Vector Retriever & OpenRouter Generator

## What we built
- `retrievers/vector_retriever.py` — glues embedder + index into one `retrieve()` call
- `generation/prompt_builder.py` — grounded, citation-enforcing prompt template
- `generation/generator.py` — direct HTTP client to OpenRouter with reasoning enabled
- Full end-to-end pipeline: file → chunks → vectors → search → grounded, cited answer

## Core concepts

### 1. The retriever as a composition boundary
`VectorRetriever` takes an `Embedder` and an `Index` in its constructor and exposes `retrieve(query, top_k, tenant_id)`. It has no independent state — it's pure composition. This is the **strategy pattern**: swap the embedder or the index without touching the retriever, or swap the retriever without touching either.

Concretely, this means when M4 adds a BM25 index and M5 adds hybrid retrieval, the shape of the code stays the same — only which classes get instantiated changes.

### 2. Grounded generation via prompt engineering
The system prompt has three constraints that turn an LLM into a RAG generator:
"Answer using ONLY the provided context chunks"
"At the end of every factual claim, cite the chunk number like [1] or [2]"
"If the context does not contain enough information, say 'I don't have enough context to answer this.'"

These are the **guard rails**. Without them:
- Constraint 1 missing → hallucinations from training data
- Constraint 2 missing → unverifiable answers
- Constraint 3 missing → confident-sounding wrong answers on out-of-context questions

Citations are a **prompt problem, not a code problem**. We don't parse the model's output to inject `[1]` — the model produces them because the prompt asks for them. Cheap and effective.

### 3. Context assembly — order matters
The prompt lists chunks in retrieval order: `[1]` is the top-scored chunk, `[N]` is the least relevant. LLMs exhibit **lost-in-the-middle** behavior — they attend more to content at the start and end of the context than the middle. So ordering by relevance (best first) generally produces better answers than random order.

M7 will explore context reordering strategies (put best at both ends).

### 4. Provider-agnostic generation
`OpenRouterGenerator` uses `requests.post` to hit an OpenAI-compatible endpoint. OpenAI, OpenRouter, Groq, DeepInfra, together.ai, and local vLLM servers all expose the same `/v1/chat/completions` shape. Swapping providers = one URL change.

That's why the class is `Generator` in the ABC layer — the interface is provider-neutral. The concrete `OpenRouterGenerator` is just one implementation.

### 5. Reasoning mode
Setting `"reasoning": {"enabled": True}` tells reasoning-capable models to think through the problem before answering. Trade-off:
- **Pro**: more accurate on multi-step questions, better citation coverage
- **Con**: higher latency, uses more tokens (the reasoning trace is billed on paid tiers)

For a benchmark platform like ours, reasoning-on is the right default while iterating; reasoning-off is worth measuring for latency-sensitive production.

### 6. `response.raise_for_status()` + JSON error check
OpenRouter sometimes returns errors as **HTTP 200 with an `error` object in the JSON body**. Naive code that only checks `response.status_code` misses these. Our defensive check:
```python
if "choices" not in data:
    raise RuntimeError(f"OpenRouter error: {data}")
```
catches provider-side errors (rate limits, model unavailable, quota) that arrive as 200-OK. This is a real production pitfall.

## Why the design choices

- **`temperature=0.0`**: deterministic outputs for reproducible eval. Non-zero temperature makes benchmarking harder.
- **`max_tokens=512`**: bounded response length. Prevents runaway generation on ambiguous queries.
- **HTTP client over SDK**: one less dependency, one fewer thing to break on version bumps, transparent behavior. SDKs hide retries and error handling; sometimes you want to see the wire.
- **`timeout=120`**: reasoning models can take a while. Too-short timeouts cause spurious failures.
- **`os.environ["OPENROUTER_API_KEY"]` (KeyError on missing)**: fail loud at init time, not on first call.

## Interview flashcards

1. **Q:** How does your system prevent hallucinations?
   **A:** Three prompt constraints. First, the system prompt restricts answers to the provided context only. Second, every claim must cite a chunk number. Third, if the context is insufficient, the model is instructed to say so explicitly instead of guessing. This turns hallucination detection from a post-hoc problem into a prompt-time constraint.

2. **Q:** Why is your generator called `OpenRouterGenerator` when the ABC is `Generator`?
   **A:** Separation of interface from implementation. The `Generator` ABC defines the contract — `generate(query, chunks) → str`. `OpenRouterGenerator` is one concrete implementation. I could add a `GroqGenerator`, `LocalLlamaGenerator`, or `AnthropicGenerator` tomorrow, and the retriever, prompt builder, and evaluator wouldn't need to change.

3. **Q:** Why did you write direct HTTP instead of using the openai SDK?
   **A:** One less dependency to version-manage, no vendor lock-in on client behavior, and total transparency into retries, error shapes, and rate-limit responses. The OpenAI SDK hides some of these behind abstractions. For a learning project and for production observability, direct HTTP is fine.

4. **Q:** What is "lost-in-the-middle" and how do you address it?
   **A:** LLMs attend more strongly to the beginning and end of their context window than the middle. If the most relevant chunk sits in the middle of a long context, the model may under-weight it. My prompt orders chunks by retrieval score, best first — a partial fix. A more advanced approach (M7) is bookending: place the best chunk at position 1, second-best at the end, and less relevant ones in between.

5. **Q:** What's your citation mechanism?
   **A:** Prompt-driven, not code-driven. The prompt lists chunks as `[1] content...\n\n[2] content...` and instructs the model to cite them by number in its answer. The output naturally contains `[1]` and `[2]` markers. Downstream UI can resolve these to chunk IDs for source linking. No output parsing needed.

6. **Q:** Why `temperature=0`?
   **A:** Reproducibility. For a benchmark platform, I need the same input to produce the same output. Non-zero temperature introduces variance that makes A/B comparisons noisy. In production for user-facing chat, `temperature=0.2-0.5` is more natural, but zero is right for eval.

7. **Q:** How would you swap in a local model instead of OpenRouter?
   **A:** Write a `LocalGenerator(Generator)` that calls a vLLM or Ollama endpoint. Add it to the config as a new generator name. Change one line in the YAML: `generator: local`. No other code changes. That's the whole point of the plugin architecture.

8. **Q:** What happens if the retrieved context doesn't actually contain the answer?
   **A:** The prompt instructs the model to say "I don't have enough context to answer this." Whether the model actually does this depends on how strongly instruction-tuned it is. Weak models will confabulate anyway. That's why we measure faithfulness — to detect this failure mode quantitatively.

9. **Q:** Why isn't the generator's `Generator` interface async?
   **A:** Learning-phase simplicity. Every API call is sync `requests.post`. In production (M9), you'd swap to `httpx.AsyncClient` and make the ABC's `generate` a coroutine — but that's a scaling concern, not a correctness one. The interface is stable enough that adding async later doesn't break the plugin contract for other components.

## Code walkthrough prompt

*"Walk me through what happens when a user asks a question."*

> "The query hits `VectorRetriever.retrieve()`. It first passes the query to the BGE embedder, which applies the query prefix — 'Represent this sentence for searching relevant passages: ...' — and returns a 384-dimensional normalized vector. That vector goes to the FAISS index, which returns the top-k nearest chunks by cosine similarity, filtered by tenant_id. Those chunks then flow into the prompt builder, which formats them as numbered blocks in the context section and constructs a two-message chat prompt: a system message enforcing grounded, cited answers, and a user message containing context plus the question. The prompt hits OpenRouter over plain HTTPS with reasoning mode enabled. The response comes back as JSON; we defensively check for the `choices` key because OpenRouter sometimes returns errors as HTTP 200. The final answer contains numbered citations like `[1]` and `[2]` that a downstream UI can resolve back to chunk IDs."
