# Checkpoint 2.2 — RecursiveChunker

## What we built
- `RecursiveChunker` — hierarchical splitting on natural boundaries
- Separator priority: `\n\n` → `\n` → `. ` → ` ` → char-level fallback
- Round-trippable splitting (separator reattached to each piece)
- Greedy merge phase — small pieces coalesce toward `chunk_size`
- Overlap applied between adjacent final chunks via tail-prepend
- Boundary quality diagnostic: 0/8 → 9/10 vs OverlappingChunker

## Core concepts

### 1. The split-then-pack pattern
Naive recursive splitting gives many tiny pieces (one sentence each). Naive fixed splitting gives uniform chunks that cut mid-sentence. RecursiveChunker does both:

**Phase 1 — Split:**
```
Try \n\n first. If result > chunk_size, try \n. If still too big, try '. '. Then ' '. Then char-slice.
```

**Phase 2 — Pack (merge):**
```
Greedily concatenate adjacent pieces until the next would exceed chunk_size.
When it would exceed, start a new chunk with chunk_overlap tail from the previous.
```

Result: chunks that respect natural boundaries AND approach the target size. This is what LangChain's `RecursiveCharacterTextSplitter` and LlamaIndex's default splitter implement.

### 2. Round-trippable splitting
```python
parts = text.split(sep)
parts = [p + sep for p in parts[:-1]] + [parts[-1]]
```

By reattaching the separator to each piece, `"".join(parts) == text`. This matters for:
- Offset tracking (`start_index`, `end_index`)
- Deduplication across re-indexing runs
- Unit testing (split + join = identity)

If splitting is lossy (separator consumed), offsets become wrong and deduplication breaks.

### 3. Boundary quality as a metric
```
Overlapping: 0/8 chunks end at a natural boundary
Recursive:   9/10 chunks end at a natural boundary
```

A "natural boundary" ends with `.`, `!`, `?`, `"`, `)`, `:`, `;`, `\n`, or whitespace. This is measurable without any model. It's a fast, cheap proxy for "would a human reading this feel like they got a complete thought?"

### 4. Overlap semantics differ from OverlappingChunker
OverlappingChunker: exact character-count shift (`step = chunk_size - overlap`).
RecursiveChunker: tail-prepend (`new_chunk = prev_tail + next_piece`).

Both create overlap, but RecursiveChunker's overlap is coarser — it's at the sentence/word boundary nearest `chunk_overlap` chars from the end. In practice, retrieval quality doesn't care which you use; both catch boundary-split queries.

### 5. Variable chunk size is a feature
Recursive produced chunks ranging 270–365 chars at a 400-char target. Overlapping produced uniform 400-char chunks. The variability in Recursive reflects the document's natural structure — some paragraphs are longer, some shorter. Forcing uniformity fights the structure.

## Why the design choices
- **`\n\n` first**: paragraphs are the primary semantic unit in most documents
- **`. ` before ` `**: sentence boundary is more informative than word boundary
- **`""` as last fallback**: guarantees no piece exceeds chunk_size, even without any separators
- **Greedy merge, not optimal**: greedy is O(N); optimal (dynamic programming) is O(N²) — not worth it for this application
- **Overlap as tail-prepend**: simple, predictable, no index arithmetic needed

## Interview flashcards

1. **Q:** What's the difference between RecursiveChunker and OverlappingChunker?
   **A:** OverlappingChunker uses a fixed character-count window regardless of content. RecursiveChunker tries natural boundaries first — paragraphs, then sentences, then words — falling back to character slicing only when needed. Then it greedily merges small pieces to approach the target size. Result: 9/10 chunks end at natural boundaries vs 0/8 for overlapping.

2. **Q:** Why is the separator reattached to each piece after splitting?
   **A:** Round-trippability: `"".join(pieces) == original_text`. This makes offset tracking, deduplication, and unit testing correct. If the separator is consumed, offsets drift and deduplication breaks.

3. **Q:** Why greedy merge instead of something smarter?
   **A:** O(N) vs O(N²). Greedy is fast, predictable, and deterministic. The quality difference vs optimal merging is negligible for text chunking — the goal is "approximately chunk_size," not "exactly chunk_size." Engineering trade-off: cheap and correct enough wins over expensive and marginally better.

4. **Q:** Your benchmark shows recursive and overlapping have the same recall@1 (0.900) on the technical corpus. Does that mean recursive is not worth it?
   **A:** Retrieval quality is the same on a small, clean corpus. The difference shows on larger corpora where chunk boundary artifacts compound — more documents, more chance of a critical sentence straddling a boundary. Boundary quality (9/10 vs 0/8) is a leading indicator of corpus-scale retrieval quality, not a guarantee on any single benchmark.

5. **Q:** Why is `\n\n` prioritized over `. `?
   **A:** Paragraphs contain multiple sentences and represent a complete thought. Sentences are sub-units of that thought. The best chunk is a complete paragraph; failing that, a complete sentence. The hierarchy reflects semantic granularity from coarsest to finest.

## Code walkthrough prompt

*"How does your recursive chunker work?"*

> "The algorithm has two phases. Phase 1 is hierarchical splitting: try paragraph boundaries first (`\n\n`), then line breaks, then sentence-ending punctuation, then word boundaries, then character-level as a last resort. Any piece still larger than chunk_size gets recursively split with the next separator in the list. After all splitting, each separator is reattached to its piece so the split is round-trippable — joining all pieces reconstructs the original text, which keeps offsets correct. Phase 2 is greedy merging: walk the pieces and concatenate adjacent ones until the next would exceed chunk_size. When it would exceed, start a new chunk that begins with a tail of chunk_overlap characters from the previous one. The result is chunks that respect natural boundaries — 9 of 10 end at a sentence or paragraph end — while still approaching the target size. LangChain's `RecursiveCharacterTextSplitter` and LlamaIndex's default text splitter use the same fundamental algorithm."
