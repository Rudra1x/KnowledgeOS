# Checkpoint 7.5 — Streaming Generator

## What we built
- `StreamingGenerator` — SSE parsing, yields tokens one-by-one via Python generator
- `collect()` — streams internally, measures TTFT + TPS + total latency
- Ollama primary → OpenRouter fallback, both with stream=True
- Verified: correct answers with inline citations, streaming works end-to-end
- Measured: TTFT=7.4s on CPU (expected), ~2 tok/s on Qwen2.5-3B CPU

## Core concepts

### 1. Why streaming matters for UX
```
No streaming:  user sees blank screen for 15s → full answer appears
Streaming:     first token in 200ms → answer builds word by word over 15s
```
Same total time, completely different experience. Streaming decouples time-to-first-token (UX metric) from total generation time (hardware metric). For RAG systems, TTFT is the number users experience.

### 2. SSE (Server-Sent Events) parsing
Ollama's streaming format:
```
data: {"choices": [{"delta": {"content": "BM25"}}]}
data: {"choices": [{"delta": {"content": " is"}}]}
data: {"choices": [{"delta": {"content": " a"}}]}
data: [DONE]
```

Each line starts with `data: `. Empty lines are separators. `[DONE]` signals completion. JSON decode errors on partial lines are expected and must be silently skipped — partial buffering can produce malformed JSON mid-stream.

### 3. stream=True in requests — chunked transfer
```python
resp = requests.post(url, data=payload, stream=True)
for line in resp.iter_lines():
    # each line arrives as it's sent by the server
```
Without `stream=True`, requests buffers the complete response before returning. With it, `iter_lines()` yields each line as it arrives from the server. This is HTTP chunked transfer encoding — the same mechanism all streaming APIs use.

### 4. TTFT = prefill time + first decode step
On CPU with a 500-token prompt:
- Prefill (run prompt through model once): 6-14s on CPU, 100-300ms on GPU
- First decode step: 50-200ms
- TTFT = prefill + first decode = 7-15s on CPU, 150-500ms on GPU

Prefill dominates on CPU. GPU parallelizes the matrix operations that make prefill slow. TTFT is why GPUs matter for interactive RAG.

### 5. TPS is hardware × model × prompt length
```
Qwen2.5-3B CPU:  1-3 tok/s
Qwen2.5-3B A10:  30-50 tok/s
Claude-3 Haiku:  60-100 tok/s (API)
```
At 2 tok/s, a 100-token answer takes 50 seconds. At 50 tok/s, 2 seconds. The streaming architecture is hardware-agnostic — switch to a GPU and the same code produces 25× better TTFT without changes.

## Interview flashcards

1. **Q:** What is TTFT and why does it matter more than total generation time?
   **A:** Time To First Token — how long before the user sees any output. UX research shows perceived wait time matters more than actual wait time. Streaming with TTFT=200ms feels fast even if total generation takes 10 seconds. Non-streaming with 10 second total feels slow regardless of the answer quality.

2. **Q:** What is SSE and how do you parse it?
   **A:** Server-Sent Events — a simple HTTP streaming format where each event is a `data: {json}` line, lines are separated by empty lines, and the stream ends with `data: [DONE]`. Parse: strip `data: ` prefix, check for `[DONE]` terminator, JSON-decode the remainder, extract `choices[0].delta.content`. Handle JSON decode errors silently — partial buffer flushes produce malformed lines.

3. **Q:** What does stream=True change in your requests call?
   **A:** It enables HTTP chunked transfer encoding. Without it, requests buffers the complete response body before returning. With it, `response.iter_lines()` yields each line as the server sends it. The server is generating and transmitting tokens in real-time; `stream=True` lets your code receive them as they arrive rather than waiting for the complete response.

4. **Q:** TTFT=7.4s on your CPU. What would it be on a T4 GPU?
   **A:** ~200-500ms. Prefill — running the full prompt through the model once to populate the KV cache — requires large matrix multiplications that GPU parallelizes efficiently. On CPU with sequential BLAS operations, a 500-token prefill takes 6-14 seconds. A T4 GPU ($0.35/hr on cloud) cuts this to 100-300ms. For interactive RAG, GPU is architecturally necessary for good UX.

5. **Q:** Your streaming generator is a Python generator (yield). What does this enable for the caller?
   **A:** Incremental processing — the caller can process each token as it arrives rather than waiting for the full response. A FastAPI endpoint can forward tokens to a WebSocket. A CLI can print tokens with `print(token, end="", flush=True)`. A test can count tokens without storing the full response. The generator pattern decouples production from consumption.

## Code walkthrough

*"Walk me through your streaming generator implementation."*

> "The generator wraps the Ollama API with stream=True and iterates over the response line by line. Each line from Ollama has the format `data: {json}` — I strip the `data: ` prefix, check for the `[DONE]` terminator, JSON-decode the rest, and extract the delta content token. Empty lines are separators; malformed lines from partial buffer flushes are silently skipped with try/except. The result is a Python generator that yields tokens one by one — callers can print them, forward to WebSocket, or buffer into a complete answer. The `collect()` method wraps the generator: it starts a timer, iterates the generator recording TTFT on the first token, and returns the complete answer with TTFT, total time, and tokens-per-second. On Qwen2.5-3B CPU, we measured TTFT=7.4s and ~2 tok/s — dominated by prefill time on the 500-token prompt. The same code on a T4 GPU gives ~200ms TTFT and ~40 tok/s without any changes. The Ollama fallback to OpenRouter follows the same SSE format — both APIs are OpenAI-compatible."

## Core concepts

### 1. The complete pipeline in one run
```
Retrieve (2ms) → Rerank (20ms) → Compress (50ms) → Generate (7400ms)
→ Faithfulness NLI (176ms) → Relevance scoring (3000ms async)
```

Every component from M0-M7 executes. The bottleneck is clear: CPU generation at 7.4s TTFT dominates. All quality components (reranking, compression, faithfulness, relevance) add <4s combined.

### 2. Faithfulness=0.00 on a correct answer — the false positive problem
Query 4 ("How is dense retrieval different from BM25?") generated a correct, grounded answer that the NLI checker flagged as unfaithful. The answer paraphrased the chunk rather than quoting it, and the paraphrase fell just below word overlap and NLI thresholds.

Production implication: faithfulness false positives trigger unnecessary human review. Calibrate: track false positive rate on your gold set with human-labeled faithfulness ground truth. Adjust threshold to minimize false positives at acceptable false negative rate.

### 3. Relevance=0.57 for "What is RAG?" — n_questions=1 variance
With n_questions=1, a single reverse question is generated and its similarity to the original is the score. High variance — one poor generation tanks the score. With n_questions=3, the mean is more stable. The RAG query scored 0.57 with n=1 but would likely score 0.70+ with n=3.

### 4. Compression ratio=0.63 — real but modest on small chunks
37% of content removed before generation. On 45-word chunks: saves ~17 words per chunk × 3 chunks = 51 words ≈ 40 tokens. Modest. On 400-word production chunks: saves ~150 words × 3 = 450 words ≈ 340 tokens per query. At $0.001/1K tokens and 10K queries/day: $3.40/day saved. Annual: $1,241.

### 5. The pipeline is a system — upstream quality determines downstream quality
r@1=1.00 → faithfulness is measurable (you retrieved the right chunk to check against)
Compression strips noise → faithfulness checker sees cleaner passages → fewer false positives
Correct chunks → correct generation → relevance scorer produces meaningful scores

You can't improve faithfulness without first fixing retrieval. You can't improve relevance without first fixing generation prompts. The stack is sequential and each layer amplifies or degrades the layer below.

### 6. Full pipeline latency architecture (production)
```
Synchronous (user waits):
  Retrieve:     2ms
  Rerank:      20ms
  Compress:    50ms
  Generate:  7400ms  ← GPU: 500ms
  TTFT:      7472ms  ← GPU: 572ms

Asynchronous (runs after answer returned):
  Faithfulness: 176ms  ← NLI, fast
  Relevance:   3000ms  ← 1 LLM call
  Flagging:     <1ms
```

Return the answer to the user at ~7.5s (GPU: ~0.6s), run quality checks in the background, flag low-quality answers for review.

## Interview flashcards

1. **Q:** Your generation benchmark shows faithfulness=0.80 but the one failure is a correct answer. How do you handle false positives in production?
   **A:** Two approaches. Track false positive rate on a labeled validation set — human-annotated faithfulness ground truth for 100 queries. Tune threshold to minimize FPR at acceptable FNR. Additionally, add a second-pass LLM check when NLI says False: "Is this answer supported by this passage? YES/NO" — if LLM says YES and NLI says NO, trust LLM. Use NLI as a cheap first filter, LLM as override.

2. **Q:** TTFT=7.4s on CPU. What's the realistic production architecture for interactive RAG?
   **A:** GPU inference for generation. A10/T4 GPU on cloud: TTFT ~200-500ms, 30-50 tok/s. For serverless at lower cost: batch inference where multiple queries share GPU time. For very low latency (<100ms TTFT): smaller models (1B parameter) or API (Claude Haiku, GPT-4o-mini). The streaming architecture is hardware-agnostic — switch to GPU, same code, 15× better TTFT.

3. **Q:** The compression mean is 0.63. When does compression provide meaningful cost savings?
   **A:** When average chunk size exceeds ~200 words. On 45-word chunks, 37% compression saves 17 words per chunk. On 400-word chunks, same ratio saves 148 words per chunk × 3 chunks = ~444 words ≈ 333 tokens. At GPT-4 pricing ($0.01/1K tokens), 333 tokens saved = $0.003 per query. At 100K queries/day: $300/day or $109,500/year.

4. **Q:** Answer relevance=0.73 mean across 5 queries with threshold 0.85. What does this tell you about your answers?
   **A:** Answers are on-topic (0.73 is clearly above random ~0.3-0.4) but the threshold 0.85 is too strict. Reverse-generated questions from correct answers naturally score 0.65-0.80 against the original — they're specific sub-questions, not identical phrasings. Recalibrate threshold to 0.60 based on this benchmark. Above 0.60 = relevant; 0.45-0.60 = partially relevant; below 0.45 = irrelevant.

5. **Q:** You run faithfulness and relevance after generation. Should these run synchronously or asynchronously?
   **A:** Asynchronously. Return the answer to the user immediately after generation, run quality checks in the background. Faithfulness takes 176ms (acceptable sync if needed), relevance takes 3s (must be async). Flag low-quality answers retroactively — alert a human reviewer, log for model improvement, or trigger regeneration in a background job. Synchronous quality checking adds 3+ seconds of perceived latency with no user benefit.
