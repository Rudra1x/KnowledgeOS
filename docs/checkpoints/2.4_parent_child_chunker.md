# Checkpoint 2.4 — ParentChildChunker

## What we built
- `ParentChildChunker` — two-pass hierarchical chunking (parent split → child split)
- Every child carries `parent_id`, `parent_content`, `parent_index`, `child_index_in_parent`
- Overlap applied *within* parents only (children don't overlap across parent boundaries)
- Verified 3x context multiplier on real corpus (avg child: 276 chars, avg parent: 827 chars)
- Clean separation: chunker produces artifacts, retrieval strategy (M5) decides how to use them

## Core concepts

### 1. The retrieval-generation tension
**Small chunks** → precise retrieval (tight embeddings, high recall@1)
**Large chunks** → good generation (wide context, coherent answers)

These conflict. A 100-char chunk matches queries precisely but gives the LLM almost no context. A 2000-char chunk gives rich context but dilutes the embedding with multiple topics.

ParentChildChunker resolves this tension with a structural trick: index small, generate large.

### 2. The two-pass split
**Pass 1:** Split document into large parent chunks (~1500 chars) respecting natural boundaries.
**Pass 2:** Split each parent into small child chunks (~300 chars) with overlap.

Children are indexed. When a child matches a query, the retriever substitutes `parent_content` for the generation context instead of the child's own content.

```
Query: "What is hybrid retrieval?"
                     ↓
         Small child matches precisely
                     ↓
         Parent context returned to LLM
              (includes hybrid + adjacent context)
```

### 3. Metadata as the linkage mechanism
Instead of a separate "parent index" data structure, we store `parent_content` directly on each child chunk's metadata:
```python
metadata = {
    "parent_id":      parent_uuid,
    "parent_content": full_parent_text,  # 1500 chars of context
    "parent_index":   0,                 # which parent
    "child_index_in_parent": 2,          # which child within parent
}
```

**Trade-off:** Memory cost (each child stores ~1500 chars of parent text). On a large corpus, this 5-6x increases the metadata store size.
**Benefit:** Zero-join retrieval. At query time, just read `chunk.metadata["parent_content"]`. No second lookup, no parent index to maintain.

For a 1M-chunk index, memory matters. For a 100K-chunk learning project, it's negligible. M9 (Enterprise Platform) is where you'd normalize this into a proper parent store.

### 4. Overlap scope — within parents only
Children overlap with siblings (children of the same parent). They do NOT overlap across parent boundaries. Why:
- Parent boundaries are semantic — crossing them conflates different topics
- Overlap is meant to catch query-relevant sentences at chunk boundaries *within* a coherent section
- Cross-parent overlap would dilute the parent content that the child inherits at generation time

### 5. Orphan parents
When a document doesn't divide evenly, the last parent may be small (sometimes even a single child). This is expected behavior — not a bug. Options:
- **Keep distinct** (current behavior): the last section stays semantically separate
- **Merge into previous parent**: reduces orphans, may exceed parent_size
- **Conditional merge**: merge if len(last_parent) < min_parent_size threshold

Production systems usually add the conditional merge. Our implementation keeps it simple.

### 6. Benchmark result: tied for first
parent_child achieved r@1=1.000, tied with adaptive and metadata_aware. Smaller children (279 avg chars) produced tighter embeddings that precisely matched the gold set's per-paragraph queries. The context multiplier means generation quality would be the differentiator — not visible in recall@1 alone.

## Why the design choices
- **Recursive split for both passes**: consistent natural-boundary behavior at both scales
- **`parent_content` on child metadata**: zero-join retrieval, simpler implementation
- **No cross-parent overlap**: semantic scope preservation
- **`global_child_idx`**: chunk_index is monotonically increasing across the whole document, not per-parent — consistent with all other chunkers

## Interview flashcards

1. **Q:** What problem does parent-child chunking solve?
   **A:** The tension between retrieval precision (small chunks) and generation quality (large context). Small chunks produce tight, focused embeddings that match queries precisely. Large context gives the LLM enough surrounding information to answer well. Parent-child indexes small children but returns large parent context for generation.

2. **Q:** Why store parent_content on each child instead of a separate parent index?
   **A:** Zero-join retrieval. At query time, `chunk.metadata["parent_content"]` gives the full parent context immediately — no second lookup, no cross-reference. The cost is memory: each child duplicates ~1500 chars of parent text. Acceptable at small scale; at large scale you'd maintain a proper parent store keyed by parent_id.

3. **Q:** Where does the parent-child swap actually happen in your architecture?
   **A:** In M5, the retrieval strategy layer. The chunker's job is to produce well-linked children. The retriever's job is to decide whether to return child content (for retrieval scoring) or parent content (for generation). Separating these concerns means you can change the retrieval strategy without touching the chunker.

4. **Q:** Why doesn't overlap cross parent boundaries?
   **A:** Parents are semantic units — boundaries between them represent topic shifts. Overlap across a parent boundary would blend semantically distinct content, diluting both the child embedding and the parent context. Overlap should only help within a coherent section, not across one.

5. **Q:** How does parent-child compare to sentence-window retrieval (LlamaIndex)?
   **A:** Same fundamental pattern. LlamaIndex's SentenceWindowRetriever indexes single sentences and retrieves a window of K surrounding sentences for generation. Parent-child is more flexible: you control both split levels independently, and the parent boundary respects semantic structure rather than a fixed window count.

6. **Q:** Your benchmark shows parent_child tied for first with r@1=1.000. How would you choose between it and, say, recursive for a real deployment?
   **A:** Recall@1 alone doesn't differentiate them here. The distinguishing factor is generation quality (faithfulness, answer completeness) — which requires an LLM eval pass. I'd run a faithfulness benchmark with parent-child (using parent_content for generation) vs recursive (using chunk content directly) and pick based on that result. Parent-child's advantage is invisible in retrieval metrics; it shows in generation quality.

*"Explain parent-child chunking and when you'd use it."*

> "Parent-child chunking has two passes. The first pass splits the document into large parents — targeting 1500 chars, using recursive boundary-respecting splitting. The second pass splits each parent into small children — targeting 300 chars with 40-char overlap between siblings. Every child chunk carries the full parent content in its metadata, linked by a parent_id. The index stores small children, which produce tight, focused embeddings that match queries precisely. At retrieval time, my M5 retrieval strategy substitutes the parent content for generation, giving the LLM 1500 chars of surrounding context instead of 300. The 3x context multiplier means the generator sees 3x more coherent context than a pure small-chunk strategy, at no cost to retrieval precision. I'd use it when: the corpus has coherent long-form sections (reports, articles), queries are factoid but answers require surrounding context, and generation quality matters more than retrieval latency. I wouldn't use it when chunks are already semantically atomic (FAQs, dictionary entries) — the parent context would just add noise."
