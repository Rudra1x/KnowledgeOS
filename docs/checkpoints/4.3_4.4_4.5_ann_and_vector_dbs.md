# Checkpoint 4.3 — FAISS IVF + HNSW (Approximate Nearest Neighbor)

## What we built
- `FaissIVFIndex` — clustering-based ANN, nprobe controls recall/speed
- `FaissHNSWIndex` — graph-based ANN, M + ef_search control recall/speed
- Auto-train on first batch for IVF (HNSW requires no training)
- Over-fetch then filter for tenant isolation
- Demonstrated: all three indexes return identical top-1 on 8 chunks (correct)

## Core concepts

### 1. Why approximate nearest neighbor (ANN)
FAISS Flat does exact brute-force search: compare every query vector to every stored vector. O(N × D) per query. At N=1M, D=384: 384M multiply-adds per query. On modern hardware that's ~10-100ms — too slow for interactive systems.

ANN trades a small recall loss for 10-1000x speedup. The "approximately" matters: top-1 returned by HNSW is the true top-1 ~95% of the time, with ef_search=50. That 5% miss rate is often acceptable; the 100x speedup is always desirable.

### 2. IVF — Inverted File Index (clustering-based)
**Build time:** K-Means clusters vectors into nlist Voronoi cells. Each vector assigned to its nearest centroid.

**Query time:** Find the nprobe nearest centroids to the query, then search only the vectors in those cells.

**Trade-off knob — nprobe:**
- nprobe=1: fastest, highest miss rate (only searches 1/nlist of vectors)
- nprobe=nlist: same as flat exact search, slowest
- Rule of thumb: nprobe=10 gives ~90% recall at ~10x speedup for typical nlist

**Training requirement:** IVF needs a training set of at least 39×nlist vectors for stable k-means. The FAISS warning "clustering N points to K centroids: please provide at least 39K training points" tells you your nlist is too high for your corpus size.

**Rule of thumb for nlist:**
- N=10K: nlist=100-400 (sqrt to 4×sqrt)
- N=1M: nlist=1000-4000
- N=100M: nlist=10000-40000

### 3. HNSW — Hierarchical Navigable Small World
Builds a layered graph where vectors are nodes:
- **Layer 0:** all vectors, dense local connections
- **Layer 1:** subset of vectors, longer-range connections
- **Layer 2+:** progressively fewer nodes, even longer range

Query traversal: enter at the top layer (few nodes, fast global navigation), descend to layer 0 (fine local search). Like a skip list — fast long-range jumps, then precise local refinement.

**Parameters:**
- `M=16`: edges per node. More → better recall, more memory. Default 16 for most workloads.
- `ef_construction=200`: search depth during build. Higher → better quality graph, slower build.
- `ef_search=50`: search depth at query time. Higher → better recall, slower queries.

**No training required:** HNSW builds incrementally as vectors arrive. No corpus-size minimum.

**No deletion support:** Removing a vector requires marking it as deleted (lazy delete) or rebuilding. For corpora with frequent deletions, use a managed vector DB.

### 4. The training warning is your production monitor
```
WARNING clustering 8 points to 4 centroids:
please provide at least 156 training points
```
This tells you nlist=4 needs 156 training points but you have 8. FAISS auto-adapts but the quality degrades. In production, this warning means your index is misconfigured — reduce nlist to sqrt(N) or increase your corpus before switching to IVF.

### 5. Over-fetch for tenant filtering
FAISS has no native tenant concept. Our wrapper searches `top_k * 2` candidates and filters by `tenant_id`. On average, half the over-fetched candidates belong to the right tenant. If one tenant has very few documents, you may need `top_k * 10` or higher.

Production fix: use a vector DB with native pre-filtering (Qdrant, Weaviate, Milvus) that filters before returning, not after.

## Interview flashcards

1. **Q:** What is approximate nearest neighbor search and why do we need it?
   **A:** ANN returns the closest vectors to a query in sublinear time by trading a small recall loss for large speed gains. Exact search at N=1M vectors takes 100ms+; HNSW returns results in <5ms with ~95% recall. For interactive RAG systems where users expect <200ms response, ANN is architecturally necessary beyond ~100K vectors.

2. **Q:** IVF requires training; HNSW does not. What does IVF's training do?
   **A:** IVF runs k-means clustering on the vector set to define Voronoi cells. This is a one-time O(N × nlist × iterations) operation. Without training, IVF doesn't know how to partition the space. HNSW builds its graph incrementally as vectors are added — no global view of the data is needed upfront.

3. **Q:** What does nprobe control in IVF?
   **A:** The recall/speed trade-off. nprobe=1 searches only the nearest cell (fastest, highest miss rate). nprobe=nlist searches all cells (exact, slowest). Each additional nprobe cell searched adds to the recall but also to the latency. nprobe=10 with nlist=100 is a common starting point: searches 10% of cells, achieves ~90% recall vs exact.

4. **Q:** When would you use IVF vs HNSW?
   **A:** HNSW for most production workloads — better recall/speed trade-off, no training needed, simpler to operate. IVF when: memory is constrained (IVF with product quantization uses 8-32x less memory), corpus grows dynamically (incremental IVF is easier to update), or you need exact control over the space partitioning. HNSW doesn't support deletion; IVF does (with lazy marking).

5. **Q:** All three FAISS indexes returned the same top-1 on your 8-chunk corpus. What does that prove?
   **A:** Correctness on small data. With 8 vectors, there's no approximation happening — all three methods exhaustively compare against all 8. The ANN behavior only emerges at scale when the index starts skipping cells (IVF) or pruning graph branches (HNSW). Small corpus tests validate the interface and data flow; you need 100K+ vectors to benchmark the recall trade-off.

## Code walkthrough prompt

*"Explain FAISS ANN indexes and when to use each."*

> "FAISS provides three index types. Flat is exact brute-force — perfect recall, O(N) per query, fine up to ~100K vectors. IVF clusters the vector space into nlist cells using k-means during a training phase, then at query time searches only the nprobe nearest cells — 10-100x faster than flat at the cost of some recall, tunable via nprobe. HNSW builds a layered graph where queries navigate from high-level coarse nodes down to fine-grained leaf nodes — state-of-the-art recall/speed trade-off, no training needed, but doesn't support deletion. The production decision: flat until latency hurts, HNSW for most production workloads, IVF+PQ when memory is the constraint. Both IVF and HNSW require tuning: nprobe for IVF, ef_search for HNSW. The FAISS warning about clustering point counts is a production signal — it tells you nlist is misconfigured for your corpus size."

# Checkpoint 4.4 — ChromaIndex

## What we built
- `ChromaIndex` behind the `Index` ABC
- In-memory (ephemeral) and persistent (DuckDB+Parquet) modes
- Native deletion by chunk_id — 8→7 chunks confirmed
- Persistence across simulated restarts — Written=8, Reloaded=8
- Multi-tenant isolation via one collection per tenant
- Collection name validation guard (≥3 chars, alphanumeric)
- Chroma distance → similarity conversion (1 - distance for cosine)

## Core concepts

### 1. What Chroma adds over FAISS
| Capability | FAISS | Chroma |
|-----------|-------|--------|
| Persistence | Manual (save/load + separate metadata) | Automatic |
| Deletion | Rebuild (HNSW) | Native by ID |
| Metadata filtering | Manual post-filter | WHERE clause support |
| Multi-tenant | Manual wrapper | Native via collections |

The headline: Chroma is a **database**, not a math library. It has a storage layer, a query engine, and a lifecycle management system. FAISS is a pure algorithm library that you build a database around.

### 2. Persistence — automatic vs manual
FAISS flat: `faiss.write_index(index, "file.index")` + separately serialize the `_chunks` list + reload both at startup + handle version mismatches. Total: 50-100 lines of infrastructure code.

Chroma: `PersistentClient(path="./chroma_db")` — done. All vectors, metadata, and documents survive restarts automatically.

The trade-off: Chroma's format (DuckDB + Parquet) is opaque. FAISS binary files are portable across languages (Python, C++, Java). For a Python-only RAG system, Chroma's persistence is the practical choice.

### 3. Deletion — database design vs algorithm design
FAISS HNSW doesn't support deletion because the graph structure is hard to update locally — removing a node can disconnect parts of the graph. The clean solution is rebuilding (expensive) or lazy marking (leaks memory).

Chroma supports deletion natively because it's backed by DuckDB, a relational database that handles deletions trivially. The ACID properties of the storage layer carry over.

### 4. Chroma's cosine distance → similarity conversion
Chroma returns `distance` where lower means more similar (standard distance metric). Our `search()` converts:
```python
score = 1.0 - distance   # for cosine distance
```
Without this conversion, scores are inverted — high distance (low similarity) would rank first. This is a silent semantic error: retrieval returns the *least* similar chunks.

### 5. Collection name constraints
Chroma enforces: 3-512 chars, `[a-zA-Z0-9._-]`, starts/ends with alphanumeric. A tenant_id like "us" (2 chars) or "tenant/A" (invalid char `/`) silently breaks. Our validation guard at `__init__` surfaces this at configuration time rather than at retrieval time.

## Interview flashcards

1. **Q:** When would you choose Chroma over FAISS for a production system?
   **A:** When you need persistence without writing your own serialization, deletion without index rebuilds, or collection-based multi-tenancy. Chroma handles these with zero infrastructure code. FAISS wins when you need maximum performance, portability to non-Python systems, or fine-grained control over the index algorithm.

2. **Q:** Chroma returns "distance" not "similarity" for cosine search. What happens if you don't convert?
   **A:** Retrieval returns the least similar chunks first — catastrophic silent failure. Distance and similarity are inversions: distance=0 means identical (similarity=1), distance=1 means orthogonal (similarity=0). For cosine, `similarity = 1 - distance`. Always check the return semantics when integrating a new vector DB.

3. **Q:** How does Chroma implement multi-tenancy?
   **A:** One collection per tenant. Each collection is an isolated vector store with its own HNSW index. Queries to collection "tenant_A" can only return vectors stored in that collection — native isolation with zero application-level filtering.

4. **Q:** Why does Chroma require a minimum 3-character collection name?
   **A:** Chroma validates collection names against the pattern `[a-zA-Z0-9._-]` with length 3-512. This mirrors constraints from databases it builds on. Short names like "A" or "mt" are rejected. Your application code should validate tenant IDs against these constraints at configuration time — not discover them at runtime.

5. **Q:** What does Chroma's DuckDB+Parquet storage give you that a raw file store doesn't?
   **A:** Transactional writes, concurrent reads, column-oriented storage (fast metadata filtering), and SQL-queryable metadata. You can write `SELECT * FROM embeddings WHERE metadata.date > '2024-01-01'` directly. Raw file stores give none of this.

## Code walkthrough prompt

*"How does Chroma differ from FAISS in your stack?"*

> "Chroma is a managed vector database; FAISS is a pure algorithm library. In practice this means Chroma handles three things I'd otherwise build myself: persistence — `PersistentClient` automatically survives process restarts; deletion — `collection.delete(ids=[...])` removes vectors immediately without index rebuilds; and multi-tenancy — I create one collection per tenant, so queries are natively isolated without any post-retrieval filtering. The interface stays the same: both `FaissFlatIndex` and `ChromaIndex` implement the `Index` ABC with `add()` and `search()`. The difference is Chroma returns a `distance` not a `similarity`, so I convert: `score = 1.0 - distance`. Without that, retrieval would return the least similar chunks — a silent semantic error. I also validate collection names at init because Chroma's constraints (3-512 chars, alphanumeric, etc.) would surface as cryptic errors at runtime otherwise."

# Checkpoint 4.5 — QdrantIndex

## What we built
- `QdrantIndex` — in-memory and persistent modes
- Native `FieldCondition` payload filtering before ANN traversal
- Deletion via `MatchAny` filter on chunk_id payload field
- UUID normalization for Qdrant's point ID requirements
- Updated to `query_points()` API (replaced deprecated `search()`)
- Verified: tenant isolation clean (4 results each, zero cross-tenant leakage)

## Core concepts

### 1. Pre-filter vs post-filter — the architectural distinction at scale
**Post-filter (FAISS):** search all N vectors → get global top-k → filter by tenant_id. On 1M vectors with 1000 tenants (1000 vectors each), you search 1M and discard 99.9%.

**Pre-filter (Qdrant):** apply `FieldCondition(tenant_id == "A")` before ANN traversal → search only tenant A's 1000 vectors → return top-k from that subset. 1000x less work.

Qdrant implements pre-filtering via payload indexing: `tenant_id` is indexed as a payload field, and the HNSW traversal is restricted to nodes matching the filter condition before scoring.

### 2. Payload as first-class citizen
In FAISS, metadata lives in a Python list parallel to the FAISS index — `_chunks[idx]` corresponds to FAISS vector at position `idx`. This parallel structure can go out of sync if documents are deleted, added out of order, or serialized separately.

In Qdrant, payload is stored atomically with the vector — one point contains both. No synchronization problem. No risk of metadata list drifting from index state. This is production-grade design.

### 3. API deprecation — `search()` → `query_points()`
Qdrant deprecated `client.search()` in favor of `client.query_points()`. The new method:
- Returns a `QueryResponse` object: access results via `.points`
- Supports more query types (full-text, sparse, multi-vector)
- Consistent API surface across all query modes

Pattern: always check the return type when an SDK upgrades. `results = client.query_points(...).points` — accessing `.points` is the new pattern.

### 4. `recreate_collection` → `delete + create`
Qdrant deprecated `recreate_collection` (atomic create-or-replace) in favor of explicit `delete_collection` + `create_collection`. Why: the atomic version hid whether a collection existed or not, making reasoning about state harder. Explicit is better than implicit.

Defensive pattern: `try: delete_collection() except: pass` — handles both "collection exists" and "collection doesn't exist" cases cleanly.

### 5. UUID normalization for point IDs
Qdrant requires point IDs to be either integers or UUIDs. Our chunk_ids are UUIDs (from `uuid.uuid4()`). If the chunk_id isn't a valid UUID string (e.g., a custom hash), we derive a deterministic UUID via `uuid.uuid5(NAMESPACE_DNS, chunk_id)`. Always valid, always deterministic for the same input.

## Interview flashcards

1. **Q:** What is the difference between pre-filter and post-filter in vector search?
   **A:** Post-filter retrieves top-k globally then discards non-matching results. Pre-filter restricts the search space before ANN traversal so all returned results already match the filter. At 1M vectors with 1000 tenants, post-filter searches 1M and discards 99.9%; pre-filter searches 1000 and returns all results. Pre-filter is 1000x less work.

2. **Q:** Why is Qdrant's payload-with-vector design better than FAISS's parallel list?
   **A:** Atomicity. FAISS requires maintaining a parallel Python list `_chunks` synchronized with the FAISS integer index. Deletions, updates, and out-of-order inserts can desync them. Qdrant stores payload as part of the point — one atomic unit. No synchronization problem.

3. **Q:** Your Qdrant search method was broken by an API deprecation. How did you handle it?
   **A:** Updated from `client.search()` to `client.query_points()` and accessed `.points` on the result object. Also updated `recreate_collection` to explicit `delete + create`. The pattern: read the migration guide, update the call, check return types. External APIs evolve; the fix is always the same. Defensive code (try/except around delete) handles the collection-not-exists case.

4. **Q:** Tenant A has 4 documents, Tenant B has 4 documents, you query for Tenant A with top_k=5. How many results do you get?
   **A:** 4 — there are only 4 documents in Tenant A's collection. Qdrant's pre-filter restricts the search to Tenant A's vectors, so the result set is bounded by that tenant's document count, not by top_k. FAISS post-filter would also return 4, but only after fetching and discarding Tenant B's results.

5. **Q:** When would you choose Qdrant over Chroma?
   **A:** When you need: pre-filtering (Chroma's filtering is less efficient at scale), native hybrid search (Qdrant supports sparse + dense in one query), disk-based HNSW for large corpora, distributed sharding, or gRPC for high-throughput scenarios. Chroma is simpler to set up and good for smaller production deployments.

## Code walkthrough prompt

*"Why is Qdrant's pre-filtering architecturally better than post-filtering?"*

> "At scale, the difference is dramatic. With FAISS, I search all N vectors globally and filter by tenant_id after — on 1M vectors with 1000 equal-sized tenants, I search 1M and discard 99.9%. Qdrant indexes the tenant_id payload field and restricts the HNSW graph traversal to matching nodes before returning results — I search only the ~1000 vectors belonging to the querying tenant. That's 1000x less work. The payload is also stored atomically with the vector, so there's no parallel metadata list to maintain or synchronize. The API deprecation from search() to query_points() is a versioning lesson: always check the return type after upgrades — query_points() returns a QueryResponse object and you access .points to get the list."
