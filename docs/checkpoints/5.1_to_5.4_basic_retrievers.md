# Checkpoint 5.1 — FilteredRetriever

## What we built
- `FilteredRetriever` — three filter modes: pre, post, boost
- Per-call filter override (dynamic filtering at retrieval time)
- Keyword overlap bonus in boost mode
- Verified: post-filter surfaces only CSV chunks; boost prefers CSV while keeping TXT accessible

## Core concepts

### 1. Metadata is a retrieval signal, not just provenance
`file_type`, `content_type`, `heading_level`, `date`, `section_title` — these aren't just tracking fields. They encode structure that pure semantic similarity cannot capture. "Show me only FAQ rows about evaluation" is a metadata query. Dense retrieval would mix in general evaluation paragraphs from prose documents. Metadata filtering restricts to the right *kind* of document before ranking.

### 2. Three filter modes for three use cases
**Post-filter (rank then restrict):** default. Run full semantic search, then apply metadata filter. Most flexible — never misses semantically relevant chunks in the target type. Over-fetch to account for filtering losses. Use when: filter is selective, most results should survive, recall is the priority.

**Pre-filter (restrict then rank):** narrow the candidate pool first. True pre-filter requires a vector DB with native payload filtering (Qdrant). FAISS simulates it by over-fetching then filtering. Use when: filter eliminates most of the corpus, precision is the priority.

**Boost (soft preference):** matching metadata multiplies the score, non-matching doesn't get zero. Use when: you prefer one type but don't want to exclude others.

### 3. Over-fetching compensates for post-filter losses
If you filter={"file_type": "pdf"} and only 20% of your corpus is PDF, you need to fetch 5× top_k before filtering to get top_k PDF results. `fetch_k = top_k * 5` is our default. If the filter is very selective, increase the multiplier.

### 4. Dynamic per-call filter override
```python
retriever.retrieve(query, filter={"date_after": "2024-01-01"})
```
The retriever uses the call-level filter if provided, falls back to the instance-level default. This pattern — instance default, call override — enables runtime user-driven filtering without rebuilding the retriever object per call.

### 5. Keyword overlap bonus
In boost mode, we add `overlap(query_terms ∩ chunk_terms) * keyword_weight` to the score. This is a hybrid scoring bonus within a single retriever — semantic score + keyword signal. Cheap (no index needed), directionally useful.

## Interview flashcards

1. **Q:** When would you use post-filter vs boost?
   **A:** Post-filter when you need deterministic exclusion ("only show PDF results"). Boost when you want preference without exclusion ("prefer recent docs but show older ones if very relevant"). Post-filter is stricter; boost is more forgiving.

2. **Q:** Why over-fetch in post-filter mode?
   **A:** If filter eliminates 80% of retrieved chunks, top_k results become top_k/5 survivors. Over-fetching (top_k * 5 candidates) ensures enough survivors for the requested top_k.

3. **Q:** How does Qdrant's pre-filter differ from your FAISS simulation?
   **A:** Qdrant applies the filter before ANN traversal — only matching nodes are searched. FAISS searches all N vectors globally and filters after. On 1M vectors with 1000 tenants, Qdrant searches 1K vectors; FAISS searches 1M and discards 999K.

4. **Q:** Your boost multiplier is 2.0. A chunk matching the filter scores 1.91, one not matching scores 0.95. What if all top-5 results are filtered-type?
   **A:** Boost can dominate so completely that the top-k only contains the preferred type — functionally equivalent to post-filter. This is data-dependent. A smaller multiplier (1.3×) would let non-matching chunks appear more often.

5. **Q:** A user wants "only show results from this week's documents." How do you implement this?
   **A:** `retriever.retrieve(query, filter={"date_after": "2025-08-14"})` — per-call filter override. The loader must have captured `date` in document metadata (which our email loader does). If date metadata wasn't captured at ingestion, you'd need to re-ingest.

## Code walkthrough prompt

*"How do you implement metadata filtering in retrieval?"*

> "There are three modes behind one `FilteredRetriever` interface. Post-filter: run full semantic search over-fetching 5× top_k, then discard non-matching results — most flexible, never misses semantically relevant content in the target type. Pre-filter: restrict the candidate pool before ranking — more efficient at scale when the filter is selective, but requires a vector DB with native filtering like Qdrant. Boost: multiply matching chunks' scores by 2× — soft preference that ranks matching content higher without excluding non-matching. The retriever supports per-call filter overrides so a user could dynamically say 'only show me HR documents' without rebuilding the retriever. In production, 'only show PDF results from Q4' is the kind of metadata query enterprise clients ask in the first week after seeing a RAG demo. Having all three modes ready in the same interface means one implementation covers all of them."

# Checkpoint 5.2 — QueryRewritingRetriever

## What we built
- `QueryRewritingRetriever` — reformulate and HyDE modes using LocalLLMGenerator
- Graceful degradation: returns original query if LLM unavailable
- Transparency metadata: `rewritten_query`, `original_query`, `rewrite_mode` on every result
- Empirical finding: reformulate improves r@1 on informal queries vs OpenRouter; HyDE hurts on small corpus

## Core concepts

### 1. The query-document language mismatch
Users write informally: "how does rag work?", "bm25 vs dense", "rag eval metrics". Documents are written formally: "Retrieval-Augmented Generation combines information retrieval with language model generation." Dense retrieval handles paraphrasing reasonably, but style matters — "how does rag work?" embeds slightly farther from "Retrieval-Augmented Generation" than the reformulated "Explain the architecture and mechanism of Retrieval-Augmented Generation."

### 2. Reformulation vs HyDE
**Reformulation:** rephrase the query in document language. "bm25 vs dense which is better" → "Comparison of BM25 sparse retrieval and dense neural embedding retrieval methods." Embeds the query closer to document-style text.

**HyDE (Hypothetical Document Embedding):** generate a fake document that would answer the query, embed that document. A fake document ("BM25 is a sparse retrieval algorithm based on term frequency...") embeds in the same subspace as real documents — same style, vocabulary, density. Published results show 10-30% recall improvement on open-domain QA.

### 3. Local LLM is better than free-tier API for this task
On query 3 ("what metrics to use for rag eval"):
- OpenRouter free-tier: recalled original query verbatim → r@1=0
- Qwen2.5-3B local: reformulated to proper technical language → r@1=1

3B local model beats rotating free-tier cloud model on precise rewriting. Local is also faster (no network RTT) and unlimited.

### 4. Graceful degradation — return original on failure
When the LLM call fails (network, rate limit, empty response), return the original query. The pipeline keeps running at slightly degraded quality. This is mandatory for a component that runs on every query.

### 5. Transparency metadata
Every result carries `rewritten_query`, `original_query`, `rewrite_mode`. When rewriting hurts (HyDE dropped r@1=0.800), you can see exactly what was searched and diagnose whether the rewrite was the problem.

### 6. Rewriting helps on large diverse corpora, hurts on small clean ones
On 8 chunks where informal queries already retrieve correctly, rewriting adds noise. On 100K-document enterprise corpora where users write very differently from documents, rewriting shows measurable improvement. The small corpus result is expected.

## Interview flashcards

1. **Q:** What problem does query rewriting solve?
   **A:** Language mismatch between informal user queries and formal document language. "rag eval metrics" vs "Evaluation metrics for Retrieval-Augmented Generation systems include recall@k, MRR, and nDCG." Dense embeddings are not fully style-invariant — a reformulated query embeds closer to document-style text.

2. **Q:** How does HyDE differ from reformulation?
   **A:** Reformulation changes how the question is phrased. HyDE generates a hypothetical answer document and embeds that instead. A fake document embeds in the same subspace as real documents — same vocabulary, style, density. Reformulation closes the query-document style gap; HyDE closes it by making the query look like a document.

3. **Q:** Your HyDE implementation dropped recall on query 3. Why?
   **A:** The hypothetical answer was verbose and general, embedding near multiple topics rather than the specific metrics paragraph. On a small corpus, slight embedding shifts matter more — there are only 8 candidates, and HyDE pushed the query embedding to an adjacent region. On a large corpus, the hypothetical document would embed near an entire cluster of related content.

4. **Q:** Why use LocalLLMGenerator instead of OpenRouter for query rewriting?
   **A:** Three reasons. Speed: local is ~2-3s vs 1-15s for API. Cost: local is free. Reliability: `openrouter/free` rotates models and one returned the original query verbatim on our test. For a component that runs on every query, stability and speed matter more than model capability — a 3B local model is adequate for rewriting.

5. **Q:** What happens when the rewriting LLM call fails?
   **A:** Return the original query — graceful degradation. The pipeline keeps running at original quality. This is the mandatory production posture for any LLM-dependent component on a critical path.

## Code walkthrough prompt

*"How does your query rewriting retriever work?"*

> "The retriever has two modes. Reformulate rewrites the query to match document language — 'how does rag work' becomes 'Explain the architecture and mechanism of Retrieval-Augmented Generation' — using a local Qwen2.5-3B model via Ollama. HyDE generates a hypothetical answer document instead of rewriting the question, then embeds that document — the embedding of a fake document lands closer to real documents than a short informal query does. Both modes attach transparency metadata: `rewritten_query`, `original_query`, `rewrite_mode` on every result, so you can diagnose exactly what was searched. If the LLM call fails for any reason, the retriever falls back to the original query — mandatory graceful degradation for a component on every query's critical path. In our benchmark, reformulate matched baseline recall at 34s total time vs 0.2s — the cost is only justified on large corpora where users write very differently from documents."

# Checkpoint 5.3 — MultiQueryRetriever

## What we built
- `MultiQueryRetriever` — K variants via LLM, retrieve for each, union + reciprocal-rank aggregation
- Deduplication by chunk_id with aggregated scoring
- Verified: Qwen2.5 generates semantically diverse variants ("chunking" → "segmenting data", "partitioning", "dividing content")
- Empirical finding: r@1=0.800 vs baseline 0.900 — union noise on 8 chunks

## Core concepts

### 1. The union recall advantage
Different phrasings embed in different regions of the vector space. Each region may be adjacent to different relevant chunks. The union of K retrievals has potentially higher recall than any single retrieval.

On 10K chunks: variant 1 retrieves chunk A (BM25 paragraph), variant 2 retrieves chunk B (dense retrieval paragraph), variant 3 retrieves chunk C (hybrid paragraph). Union: all three. Single query: maybe one.

### 2. Reciprocal rank aggregation — reusing the RRF insight
```python
score(chunk) += 1.0 / rank_in_variant_i
```
A chunk ranked #1 by 3 variants scores 3.0. Ranked #2, #3, #1 scores 1/2 + 1/3 + 1 = 1.83. Chunks retrieved consistently across variants naturally rise. This reuses the M4 RRF principle — rank-based aggregation is robust to score scale differences.

### 3. Temperature for variant diversity
`temperature=0.3` — some randomness for diverse phrasings, not so much that variants become nonsensical. Qwen2.5 at 0.3 produces:
- "segmenting data" (not "chunking")
- "partitioning" (different framing)
- "dividing content" (yet another angle)

Genuinely diverse. At temperature=0.0, variants would be nearly identical.

### 4. Multi-query hurts on small corpora — union noise
On 8 chunks: variant phrasings retrieve from the same small pool with shifted emphases. The shift in embeddings can push a correct chunk from rank 1 to rank 2 in the aggregated scoring, losing recall@1. Faithfulness query dropped from r@1=1 to r@1=0 — the variants shifted emphasis toward adjacent content.

The benefit requires corpus diversity (>10K chunks, varied vocabulary) where each variant genuinely retrieves from different regions.

### 5. Original query always included
```python
all_queries = [query] + variants
```
Always include the original. The original query is often the best formulation; variants supplement it, don't replace it.

## Interview flashcards

1. **Q:** How does multi-query retrieval increase recall?
   **A:** Different phrasings embed in different vector space regions adjacent to different relevant chunks. Retrieving for K variants and unioning the results covers more of the relevant space than any single query. On large diverse corpora, different variants consistently retrieve different relevant chunks.

2. **Q:** Why did multi-query hurt recall on your 8-chunk corpus?
   **A:** Small corpora have no room for variant benefit — all variants retrieve from the same 8-chunk pool with slightly shifted emphases. The aggregated scoring then reranks based on which chunks appeared across variants, sometimes pushing correct chunks down below their single-query rank.

3. **Q:** How do you aggregate scores across multiple retrievals?
   **A:** Reciprocal rank: `score(chunk) += 1/rank_in_variant_i`. A chunk ranked #1 by 3 variants scores 3.0; ranked #2, #3, #1 scores 1.83. This naturally promotes chunks that consistently rank high across variants. Same principle as M4's Hybrid RRF.

4. **Q:** What temperature do you use for variant generation and why?
   **A:** 0.3 — enough randomness for genuinely diverse phrasings without producing nonsensical variants. At 0.0, variants are near-identical (deterministic). At 1.0, variants diverge too much and retrieve off-topic content.

5. **Q:** When would you deploy multi-query retrieval in production?
   **A:** When: the corpus is large (>10K chunks), users type short ambiguous queries, vocabulary mismatch is high between user language and document language. Not when: corpus is small, queries are already precise, or latency is a constraint (3 LLM calls + 3 retrievals per query adds ~30-60s total).

## Code walkthrough prompt

*"Explain your multi-query retriever."*

> "It generates K variants of the original query using a local Qwen2.5-3B model, always including the original as variant 0. For 'How does chunking affect retrieval quality?' the variants might be 'What is the impact of segmenting data on information recall accuracy?' and 'How does partitioning content influence search result effectiveness?' — genuinely different phrasings that embed in different vector space regions. For each variant including the original, it retrieves top-k candidates. Then it deduplicates across all retrievals by chunk_id and scores each chunk by summing 1/rank across all variants it appeared in — same reciprocal rank principle as Hybrid RRF. On our 8-chunk corpus, multi-query scored r@1=0.800 vs baseline 0.900 — the union introduced noise on a small corpus where all variants retrieve from the same limited pool. On large corpora with vocabulary diversity, I'd expect the union to cover more relevant content than single-query retrieval."

# Checkpoint 5.4 — MultiHopRetriever

## What we built
- `MultiHopRetriever` — iterative retrieval, LLM generates follow-up queries
- Hop decay scoring: hop 1 = 1.0×, hop 2 = 0.7×, hop N = 0.7^(N-1)
- Early stop condition: "STOP" sentinel or empty response
- Hop-tagged metadata: `hop`, `hop_query`, `hop_weight` on every result
- Empirical: both test queries stopped at hop 1 — LLM correctly judged sufficient context

## Core concepts

### 1. The information dependency problem
Multi-query generates parallel variants of the same question. Multi-hop generates sequential questions where each answer enables the next. "What is the FAISS index type that combines well with BM25?" requires:

Hop 1: "FAISS" → dense vector search
Hop 2: "What combines dense vector search with BM25?" → Hybrid retrieval

No single chunk answers both. The answer to hop 1 provides the vocabulary for hop 2.

### 2. The stop condition is the most critical design
Without a stop condition, multi-hop generates queries forever. The "STOP" sentinel:
- Case-insensitive match: "stop", "STOP", "Stop." all work
- First-line extraction: LLM preamble before STOP is ignored
- Fallback: empty response → STOP

On our corpus, the LLM correctly stopped at hop 1 for both queries — the retrieved context already contained enough. This is correct behavior, not a failure.

### 3. Hop decay prevents hop 3 from outranking hop 1
```
hop 1 score: original × 1.00
hop 2 score: original × 0.70
hop 3 score: original × 0.49
```
A tangentially-related chunk found at hop 3 should not outrank a directly-relevant chunk from hop 1. Decay enforces this priority ordering.

### 4. Context window management — windowed history
```python
hop_context[-3:]  # last 3 snippets only
```
Sending all previous hops to the follow-up LLM would eventually exceed the context window. Windowing to the last 3 snippets keeps the prompt compact while preserving recent context.

### 5. True multi-hop requires genuine information dependency
"What combines FAISS with BM25?" looks multi-hop but isn't — FAISS and BM25 co-appear in adjacent chunks on our corpus. True multi-hop queries: "Who invented the technique used by the system that outperforms FAISS at scale?" — where the answer to hop 1 (HNSW) provides the subject for hop 2 (who created HNSW) which you couldn't formulate without hop 1.

## Interview flashcards

1. **Q:** What is the difference between multi-query and multi-hop retrieval?
   **A:** Multi-query generates parallel phrasings of the same question. Multi-hop generates sequential questions where earlier answers inform later ones. Multi-query increases recall on ambiguous queries by covering different semantic regions. Multi-hop handles information dependency — questions that require chaining two or more facts from different parts of the corpus.

2. **Q:** Your multi-hop stopped at hop 1 for both test queries. Is that a failure?
   **A:** No — the stop condition worked correctly. The LLM judged that hop 1's retrieved context was sufficient to answer the question. On our 8-chunk corpus, each hop retrieves from a limited pool, and the first hop often gets enough. The architecture is correct; larger corpora with genuinely separate topic regions would trigger multiple hops.

3. **Q:** Why decay hop scores instead of treating all hops equally?
   **A:** Earlier hops are closer to the original question. A chunk from hop 1 directly answers "What is hybrid retrieval?"; a chunk from hop 3 answers a derived question that emerged from prior context. Hop decay reflects this decreasing directness — later hops contribute supporting context, not primary answers.

4. **Q:** When does multi-hop retrieval clearly win over single-hop?
   **A:** Questions with explicit information dependency: "What is the latency of the method that Elasticsearch uses by default?" requires hop 1 (BM25 is Elasticsearch's default) then hop 2 (BM25 latency characteristics). Customer support chains (symptom → diagnosis → resolution), legal reasoning (precedent → principle → application), and research chains (paper → method → evaluation) are natural multi-hop scenarios.

5. **Q:** How do you prevent infinite loops in multi-hop?
   **A:** Two mechanisms: `max_hops` cap (hard limit regardless of LLM output), and the STOP sentinel (LLM signals it has enough). Both must be present — the STOP sentinel can fail if the LLM never generates it; max_hops provides the guaranteed termination.

## Code walkthrough prompt

*"Explain multi-hop retrieval and when you'd use it."*

> "Multi-hop retrieval runs an iterative loop. Hop 1 retrieves for the original query. The retrieved context is fed back to the LLM with the question 'given this context, what additional information do we still need?' If the LLM returns a follow-up query, hop 2 retrieves for that. If it returns STOP — case-insensitive, checked on the first line — the loop terminates. Results accumulate across hops with decay weighting: hop 1 at 1.0×, hop 2 at 0.7×, so early results always outrank later ones. Context sent to the follow-up LLM is windowed to the last 3 snippets to avoid overrunning the context window. In our test, both queries stopped at hop 1 — the LLM correctly judged the context sufficient. That's correct behavior, not failure. True multi-hop scenarios have genuine information dependency: 'who authored the technique FAISS uses for large-scale search?' requires retrieving HNSW first (hop 1), then retrieving who created HNSW (hop 2). I'd use multi-hop for customer support chains, legal reasoning, and research synthesis tasks where the answer to one question becomes the subject of the next."
