# Checkpoint 0.2 — Interfaces, Data Models, Config

## What we built
- `core/models.py` — `Document` and `Chunk` dataclasses
- `core/interfaces.py` — 7 Abstract Base Classes: `Loader`, `Chunker`, `Embedder`, `Index`, `Retriever`, `Reranker`, `Generator`
- `core/config.py` — YAML → dataclass config with dot-path lookup
- `configs/default.yaml` — the pipeline blueprint

## Core concepts

### 1. Abstract Base Classes (ABCs) enforce contracts
An ABC declares abstract methods that subclasses **must** implement. If a subclass forgets to implement one, Python raises `TypeError` at instantiation — not silently at runtime deep in the pipeline.

```python
class Chunker(ABC):
    @abstractmethod
    def chunk(self, document: Document) -> list[Chunk]: ...
```

Every future chunker (`FixedChunker`, `SemanticChunker`, `RecursiveChunker`) inherits from `Chunker`. This is the plugin backbone.

### 2. Data contracts via dataclasses
`Document` and `Chunk` are the two data types that flow through the entire pipeline. Every component takes one and produces the other. Fixing the shape in `dataclass` means:
- Autocomplete in IDE
- Type checking (mypy)
- Immutable-ish semantics (fields are declared, not magic dict keys)

### 3. `tenant_id` as first-class field
Multi-tenancy — the ability to serve multiple isolated customers from one deployment — cannot be bolted on later. If a `Chunk` doesn't carry a `tenant_id`, then no downstream component (index, retriever) can enforce isolation without a schema migration. We put it in day 1, default it to `"default"`, and enforce it at every retrieval boundary. **This is the difference between a demo and a product.**

### 4. Config-driven assembly
`default.yaml` names which component to use at each stage:
```yaml
pipeline:
  chunker: fixed
  embedder: bge_small
```

Swap `fixed` → `semantic` and the entire chunking behavior changes with zero code edits. This is how production platforms (LlamaIndex, Haystack) work internally.

### 5. Dot-path config lookup
`cfg.get("chunker", "fixed", "chunk_size")` safely navigates nested YAML. The alternative — `cfg["chunker"]["fixed"]["chunk_size"]` — crashes with `KeyError` on missing keys. Defensive lookup with a default is what production configs need.

## Why the design choices

- **`Chunk.embedding` as `list[float]` not `np.ndarray`**: dataclasses serialize cleanly to JSON when embeddings are plain lists. Numpy arrays need custom serialization. We only convert to numpy at the FAISS boundary.
- **`metadata: dict[str, Any]`**: escape hatch for per-chunk arbitrary info (page number, source URL, timestamp, similarity score). Not every field deserves its own column.
- **`start_index` and `end_index`**: enables reconstructing the original text position for highlighting in the UI later (M11).
- **`Reranker` type in `PipelineConfig` is `str | None`**: reranking is optional. `None` means "skip this stage."

## Interview flashcards

1. **Q:** Why use ABCs instead of just duck typing?
   **A:** Enforcement. Duck typing catches missing methods at runtime when the code path is exercised. ABCs catch it at instantiation time. In a multi-plugin system, that's the difference between a clear `TypeError` and a mysterious 3-layer-deep `AttributeError`.

2. **Q:** Why is `tenant_id` on the dataclass from day one?
   **A:** Multi-tenancy is an architectural invariant, not a feature. Every index and retrieval boundary needs it. Retrofitting means a schema migration and audit of every filter operation. Cheap now, expensive later.

3. **Q:** Explain your config system.
   **A:** YAML file names each component and its parameters. A `PipelineConfig` dataclass captures which named components form the pipeline, and a nested `settings` dict holds per-component params. Dot-path lookup with defaults makes missing keys safe.

4. **Q:** What's the difference between a dataclass and a regular class?
   **A:** Dataclasses auto-generate `__init__`, `__repr__`, and `__eq__` from field declarations. Less boilerplate, IDE-friendly, and immutable variants (`frozen=True`) are one flag away.

5. **Q:** Why not use Pydantic instead of dataclasses?
   **A:** Pydantic gives runtime validation (parse-don't-validate) but pulls in a heavy dependency and slower object creation. Dataclasses are stdlib and enough for internal data contracts. Pydantic makes sense at API boundaries (M9); dataclasses are fine internally.

6. **Q:** What happens if a subclass of `Chunker` forgets to implement `chunk()`?
   **A:** `TypeError: Can't instantiate abstract class ... with abstract method chunk` at object construction time. Enforced by the `ABC` metaclass.

7. **Q:** Why is `metadata` a plain dict and not more fields?
   **A:** Extensibility. Every loader has different metadata (PDF has page numbers, HTML has URLs, email has headers). A dict is the pragmatic escape hatch. Structured fields for what's common; dict for what varies.

## Code walkthrough prompt

*"How does a component get plugged into your pipeline?"*

> "Every component subclasses one of the seven ABCs in `core/interfaces.py`. The `default.yaml` config names which subclass to instantiate at each pipeline stage, along with its constructor parameters. A pipeline builder reads the config, imports the named class, instantiates it with the config params, and wires it into the flow. To add a new chunker, I write a subclass of `Chunker`, register it under a name, and add one line to the YAML. Downstream stages don't know or care which chunker they got — they only see `list[Chunk]` on the input."
