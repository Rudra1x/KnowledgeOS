# Checkpoint 1.5 — Email Loader

## What we built
- `EmailLoader` using stdlib `email` module — no third-party deps for parsing
- MIME-aware body extraction with `text/plain` preferred over `text/html`
- HTML fallback via BeautifulSoup when plain text is absent
- Rich header metadata: from, to, cc, date (parsed to ISO), subject, message_id
- Attachment inventory (names, content-types, sizes) without content extraction
- Subject prepended to content — retrieval boost for the most search-relevant phrase

## Core concepts

### 1. MIME is a multi-format container
One `.eml` file can carry:
- `text/plain` (unformatted body)
- `text/html` (rich formatting)
- `text/calendar` (invites)
- `application/pdf` (attachment)
- `image/png` (inline image)
- Signed cryptographic parts (S/MIME)

Extracting "the email" means choosing *which* part to prioritize. Naive extractors embed both plain and HTML → duplicate content, poisoned embeddings.

### 2. Prefer plain over HTML
- Plain: already clean text
- HTML: needs boilerplate stripping (`<style>` blocks, signature images, tracking pixels)
- HTML fallback only when plain is missing/empty

Same content, different representation. Never embed both.

### 3. Headers are metadata gold
Every enterprise email query requires filtering:
- "What did Alice send Bob about the Q4 review last month?" → filter on `from`, `to`, `date`, then semantic search on content
- "Show me all emails from the CFO in November" → pure metadata filter
- "Which threads mention 'churn'?" → semantic + subject filter

If headers aren't in metadata, you can't do any of this without a full re-index later.

### 4. Attachments are recursive routing hooks
A production email loader doesn't try to extract PDFs itself — it stores attachment info and delegates. In a full system:
- `.pdf` attachment → route to `PDFLoader`
- `.docx` → route to `DOCXLoader`
- Image → route to VLM captioner or OCR

We stub this correctly: `attachments` list is populated, but content extraction is delegated. The routing hook is in place; the routing logic is a follow-up.

### 5. Subject-in-content
The subject line is often the most retrieval-relevant phrase in the entire email. Including it at the top of `content` means:
- Semantic search matches on subject phrases
- Body content still fully searchable
- Metadata still has the raw subject for exact filtering

Cost: near zero. Recall improvement on subject-line queries: substantial.

## Why the design choices

- **Stdlib `email` module**: 20 years of production use, no third-party dep risk
- **`policy.default`**: modern MIME handling — the older `policy.compat32` has broken multi-part handling
- **`text/plain` first**: cleaner input, no HTML boilerplate to strip
- **ISO 8601 date format**: sortable, timezone-aware, unambiguous — the standard for machine-readable dates
- **Attachments as metadata only**: keeps this loader focused; recursive routing is a router-level concern
- **Subject in both content and metadata**: content for semantic search, metadata for exact filtering

## Interview flashcards

1. **Q:** What's the trickiest part of parsing emails?
   **A:** MIME multi-part. One email carries plain text, HTML, calendar invites, attachments, and cryptographic parts simultaneously. You have to choose which body to use (plain if present, HTML fallback), skip attachments, and be defensive about malformed structure. Stdlib `email` with `policy.default` handles most of it, but the decision of *which part to use* is yours.

2. **Q:** Why prefer text/plain over text/html?
   **A:** The plain text version is already clean; the HTML version has style blocks, tracking pixels, signature images, and boilerplate that need stripping. Both contain the same content — embedding both is redundant and poisons retrieval.

3. **Q:** Why is the subject line in both content and metadata?
   **A:** Content for semantic search — subject phrases are often the most search-relevant text in the whole email. Metadata for exact filtering — "give me all threads with subject 'Q4 planning'." Both use cases need it, and duplication is essentially free.

4. **Q:** How do you handle attachments?
   **A:** For M1, I inventory them — capture filename, content-type, size — but don't extract content. A production system routes attachments recursively: PDF attachments to `PDFLoader`, images to a VLM captioner or OCR. The routing hook is in place (metadata contains full attachment info); the routing logic itself is a follow-up.

5. **Q:** How would you enable "find all emails from CFO in November mentioning churn"?
   **A:** Two-stage retrieval. First a metadata filter on `from` (matching CFO's addresses) and `date` (November range) — this cuts the candidate set to a few hundred emails. Then a semantic search on "churn" over that subset. That's a hybrid retrieval pattern and it's exactly what enterprise email search does under the hood.
