# Checkpoint 0.3 — TXT Loader & Fixed Chunker

## What we built
- `loaders/txt_loader.py` — reads a UTF-8 text file into a `Document`
- `chunkers/fixed_chunker.py` — splits text into overlapping fixed-size character windows
- `scripts/sample.txt` — small test corpus
- First end-to-end data flow: file → `Document` → `list[Chunk]`

## Core concepts

### 1. The unified `Document` abstraction
Every loader — PDF, DOCX, HTML, YouTube transcript — emits the same `Document` shape. Downstream chunkers don't care what the source was. This is called a **normalization boundary**: heterogeneous inputs converge into one canonical form.

### 2. Fixed chunking mechanics
Fixed chunking slices text at regular character intervals:

chunk_size = 512 # each chunk is 512 chars
chunk_overlap = 50 # each chunk shares last 50 chars with next
step = 512 - 50 = 462

Chunk boundaries: `[0..512], [462..974], [924..1436], ...`

The overlap ensures a sentence split across a boundary appears in at least one chunk *intact*. Without overlap, a query matching the split sentence retrieves nothing.

### 3. Why fixed chunking despite being "naive"
- **Deterministic** — same input, same output, always. Reproducible experiments.
- **Fast** — no embedding calls, no NLP parsing. Constant time.
- **Baseline** — every other chunker gets measured against fixed. If semantic chunking doesn't beat fixed on your data, you don't need it.

Its weakness: it splits mid-sentence. That's exactly what M2 (semantic, recursive, parent-child chunkers) will address, and we'll measure the lift.

### 4. UUID chunk IDs
Every chunk gets a `uuid.uuid4()` — globally unique with astronomical collision probability. This is critical for:
- Deduplication across re-indexing runs
- Citation linking (answer says "[abc123]", UI resolves it to a chunk)
- Audit trails (which chunk was retrieved for which query when)

Alternative: hash the content. Content-based IDs are stable across re-runs but lose ordering info.

### 5. Metadata propagation
`FixedChunker` copies `document.metadata` into every `Chunk`, plus adds `chunk_index`. This means a chunk can trace back to its parent document *and* know its position within it — needed for parent-child retrieval (M4) and citations.

## Why the design choices

- **`snippet.strip()` skip**: empty or whitespace-only chunks pollute the index and waste embedding compute
- **`range(0, len(text), step)` not `while`**: idiomatic Python, generator-friendly, no off-by-one bugs
- **`min(end, len(text))`**: last chunk's `end_index` should be the actual text length, not the theoretical past-the-end value
- **`document.tenant_id` propagated**: chunks inherit tenant isolation from their parent document — no way to accidentally leak

## Interview flashcards

1. **Q:** What's the risk of chunking without overlap?
   **A:** A sentence spanning a chunk boundary gets split into two halves, neither of which independently answers the query. The retriever misses relevant content that *is* in the corpus. Overlap of 10–20% of chunk size fixes this cheaply.

2. **Q:** How do you choose chunk_size?
   **A:** Two constraints. Upper bound: the embedding model's max sequence length (BGE-small is 512 tokens ≈ 2000 chars). Lower bound: chunks big enough to be semantically self-contained. Typical range: 256–1024 tokens. Depends on the corpus — dense technical text wants smaller chunks, narrative text tolerates larger.

3. **Q:** Why UUIDs for chunk IDs vs. sequential integers?
   **A:** Uniqueness across re-indexes and across distributed workers. Sequential IDs collide when two processes ingest concurrently. UUIDs are collision-free without coordination.

4. **Q:** Your fixed chunker splits mid-sentence. Is that a problem?
   **A:** Sometimes — mostly not, because overlap catches most of it and embeddings are robust to partial context. It becomes a problem for citation quality (the cited span looks weird) and for very short semantic units (definitions, code snippets). That's why recursive and semantic chunkers exist. But fixed is the right baseline: cheap, fast, and often within 5–10% of the best chunker on many corpora.

5. **Q:** What happens if chunk_overlap > chunk_size?
   **A:** `step` becomes negative or zero. Infinite loop or crash. Should be validated in the constructor — good catch for a code review.

6. **Q:** How would you extend this to preserve sentence boundaries?
   **A:** That's recursive chunking. Split on `\n\n` first (paragraphs). If a paragraph exceeds `chunk_size`, split on `. ` (sentences). If a sentence still exceeds, fall back to fixed-character split. It respects natural boundaries when possible and gracefully degrades when not.

## Code walkthrough prompt

*"Walk me through how a text file becomes searchable chunks."*

> "The TXTLoader opens the file, reads it as UTF-8, strips whitespace, and returns a single Document with a UUID, the content, the source path, and a metadata dict tagging the file type. That Document flows into FixedChunker, which slides a 512-character window with 50-character overlap across the content. Each window becomes a Chunk with its own UUID, a back-reference to the parent doc_id, the tenant_id inherited from the document, start/end character offsets, and inherited metadata plus a chunk_index. Empty or whitespace-only windows are skipped. The output is a list of Chunks ready to embed."
