# Checkpoint 2.1 — OverlappingChunker (Formalized Baseline)

## What we built
- Renamed `FixedChunker` → `OverlappingChunker` (backward-compatible alias preserved)
- Added `NAME = "overlapping"` class attribute — shared contract for the benchmark
- Added `chunker_name` to per-chunk metadata — every chunk knows its strategy
- Added constructor guard: `chunk_overlap >= chunk_size` raises `ValueError` at init
- Switched to `.env` loading via `python-dotenv` — API keys in one place, git-ignored

## Core concepts

### 1. Why rename matters
"Fixed" describes one property (size). "Overlapping" describes two (size + overlap). When you have 6 chunkers in a benchmark table, names should tell you the *mechanism*, not an implementation detail. Precise naming is professional hygiene.

### 2. The shared contract — NAME + chunker_name metadata
Every chunker in M2 follows the same pattern:
```python
class SomeChunker(Chunker):
    NAME = "some_name"
    ...
    # Every chunk gets:
    metadata = { "chunker_name": self.NAME, "chunk_index": i, "chunk_size_chars": len(piece) }
```

This makes the benchmark aggregator trivial: `group by chunker_name`. Without it, you'd need 6 special-case aggregators.

### 3. Constructor guards — fail loud at init
```python
if chunk_overlap >= chunk_size:
    raise ValueError(f"chunk_overlap ({chunk_overlap}) must be < chunk_size ({chunk_size})")
```

If `chunk_overlap >= chunk_size`, the `step = chunk_size - chunk_overlap` becomes zero or negative — infinite loop at runtime, or zero-length chunks forever. This is the difference between a cryptic `RecursionError` at 3am and a clear `ValueError` at object construction. **Fail at init, not at runtime.**

### 4. Overlapping chunker mechanics (recap)
```
chunk_size = 512, chunk_overlap = 50
step = 512 - 50 = 462

Chunk 0: text[0:512]
Chunk 1: text[462:974]
Chunk 2: text[924:1436]
...
```
The 50-char overlap means a sentence split at a boundary appears in at least one chunk *intact*. Without overlap, split sentences are unretrievable.

### 5. .env pattern
`load_dotenv(override=False)` loads `.env` at module import time. `override=False` means real environment variables (CI/CD, production secrets managers) take precedence. The `.env` file is for local development only — never committed (`.gitignore`).

This is the 12-factor app pattern: configuration separate from code.

## Why the design choices
- **Backward-compatible alias**: `FixedChunker = OverlappingChunker` — existing scripts don't break
- **`NAME` as class attribute not instance attribute**: shared by all instances, usable without instantiation (e.g., `OverlappingChunker.NAME` for a registry)
- **`chunk_size_chars` in metadata not just `chunk_size`**: the actual size of *this* chunk (last chunk may be shorter), not the configured target

## Interview flashcards

1. **Q:** Why add `chunker_name` to every chunk's metadata?
   **A:** Provenance. When debugging why a specific chunk retrieved poorly, you need to know which strategy produced it. When running a benchmark across 6 chunkers, you need to group results by strategy. Metadata carries decisions downstream — always tag with the decision maker.

2. **Q:** Why does `chunk_overlap >= chunk_size` cause an infinite loop?
   **A:** `step = chunk_size - chunk_overlap`. If overlap ≥ size, step ≤ 0. `range(0, len(text), step)` with step=0 raises `ValueError`; step<0 iterates backward infinitely. Failing at constructor init with a clear message is the professional choice.

3. **Q:** What's the 12-factor app pattern for configuration?
   **A:** Store configuration in environment variables (not code). `.env` files are a local-dev convenience — the application reads from `os.environ`. Production uses a secrets manager. `override=False` on `load_dotenv` ensures the prod env variable wins over a local `.env`.

4. **Q:** Why is `chunk_size_chars` the actual size, not the configured target?
   **A:** The last chunk is always shorter than `chunk_size` (it's the tail of the document). If `chunk_size_chars = chunk_size` everywhere, you'd think every chunk is full-size and miss the tail. Metadata should describe what was produced, not what was intended.

5. **Q:** Why keep `FixedChunker` as an alias after the rename?
   **A:** Backward compatibility. Any existing script importing `FixedChunker` keeps working without changes. You ship the rename without breaking downstream code — the standard pattern for Python deprecation.

> "Every chunker subclasses `Chunker` from core and implements one method: `chunk(document) → list[Chunk]`. The contract enforced by the ABC means I can't accidentally deploy a broken chunker — Python raises at instantiation if the method is missing. Each chunker has a `NAME` class attribute used as a metadata tag on every chunk it produces: `chunker_name: 'overlapping'`, `chunk_index: 3`, `chunk_size_chars: 412`. This metadata is what makes benchmarks, debugging, and per-strategy diagnostics possible downstream. Constructor guards catch impossible configurations — overlap >= size would cause a silent infinite loop — and raise `ValueError` with a clear message at object creation time, not 3 layers deep at runtime. The `FixedChunker` alias preserves backward compatibility while the class is properly renamed to reflect both its properties: fixed size AND overlap."
