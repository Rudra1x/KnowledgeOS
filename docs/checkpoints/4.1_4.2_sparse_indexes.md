# Checkpoint 4.1 — TF-IDF Index (from scratch)

## What we built
- `TFIDFIndex` — inverted index with normalized TF and smoothed IDF
- Two-pass indexing: collect doc_freq in pass 1, compute TF-IDF in pass 2
- Tenant-scoped search via `chunk.tenant_id` filter
- `vocab_size`, `stats()` for observability
- Demonstrated: FAISS and TF-IDF used same term (FAISS query → FAISS chunk ranked #1, score gap 5x)

## Core concepts

### 1. The inverted index — the data structure behind every search engine
Rather than scanning every document for each query term, an inverted index flips the relationship: for each term, store which documents contain it and their scores.

```
"retrieval" → {chunk_0: 0.045, chunk_3: 0.031, chunk_7: 0.022}
"BM25"      → {chunk_2: 0.089, chunk_5: 0.041}
"FAISS"     → {chunk_6: 0.112}
```

Query time: look up each query term, accumulate scores, sort. O(|query| × avg_posting_length) — much faster than O(N × doc_length) brute force scan.

### 2. TF — normalized term frequency
```
TF(t, d) = count(t in d) / total_terms(d)
```
Normalization by document length prevents longer documents from winning just by having more words. A 10-word document with "BM25" twice (TF=0.2) is more focused than a 1000-word document with it 20 times (TF=0.02).

### 3. IDF — inverse document frequency
```
IDF(t) = log((1 + N) / (1 + df(t))) + 1   [smoothed]
```
"The" appears in every document → IDF ≈ 1. "FAISS" appears in 1 of 8 docs → IDF ≈ log(9/2)+1 = 2.5. Rare terms carry more signal — this is Shannon's information theory applied to text retrieval.

### 4. Why two-pass indexing
You cannot compute IDF for a term until you've seen all documents (to count how many contain it). TF can be computed per-document, but IDF requires the full corpus. This is why streaming indexing is hard — you need the whole corpus to compute weights.

Pass 1: tokenize all documents, count `df[term]` across the corpus.
Pass 2: for each document, compute TF-IDF for each term using the now-complete `df`.

### 5. Score gaps as diagnostic
FAISS query produced score gap 5x (0.30 vs 0.06) — high confidence. BM25 query produced 1.6x gap — lower confidence because the chunk boundary diluted the BM25 content. Score distribution tells you which queries TF-IDF is confident on. Large gap → strong keyword match. Small gap → ambiguous.

### 6. TF-IDF's fundamental limitation
TF-IDF cannot match synonyms. "Automobile" and "car" share no tokens — TF-IDF scores them as unrelated. This is exactly the gap dense retrieval fills, and the reason hybrid wins on paraphrase queries.

## Interview flashcards

1. **Q:** What is an inverted index and why is it faster than a document scan?
   **A:** An inverted index maps terms to the documents containing them, with pre-computed relevance scores. Query time is O(query_length × avg_posting_list_length) instead of O(N × avg_doc_length). For a 1M-document corpus, a query matching 3 terms from posting lists of 1000 each takes 3000 lookups instead of scanning 1M full documents.

2. **Q:** Why normalize TF by document length?
   **A:** Without normalization, longer documents accumulate more term occurrences just by having more words. A 10,000-word document with "retrieval" appearing 50 times (TF=0.005) would beat a 100-word focused summary with it appearing 3 times (TF=0.03). Length normalization ensures the focused summary wins.

3. **Q:** Why does IDF use a smoothed formula (1 + N) / (1 + df)?
   **A:** Smoothing prevents two edge cases. First, if a term appears in every document (df=N), the original formula gives log(N/N) = 0, making the term useless. Smoothing gives log(2/N+1)+1 > 0 — still low weight but not zero. Second, if a term appears in no document (df=0), division by zero is avoided.

4. **Q:** Why can't TF-IDF match "automobile" with "car"?
   **A:** TF-IDF is purely lexical — it matches on exact token overlap. "Automobile" and "car" are different tokens regardless of semantic equivalence. Dense retrieval embeds both in a shared semantic space where synonyms land nearby. This is the fundamental limitation of sparse retrieval and the motivation for hybrid.

5. **Q:** Your TFIDFIndex requires two passes over the corpus. What breaks with streaming ingestion?
   **A:** IDF requires knowing the total document count and per-term document frequencies for the whole corpus. In streaming ingestion, you don't have the full corpus upfront. Solutions: (1) incremental IDF update (recompute IDF when new documents arrive), (2) approximate IDF from a sample, (3) fixed IDF from a training corpus. All three involve trade-offs between accuracy and complexity.

## Code walkthrough prompt

*"Walk me through how TF-IDF retrieval works."*

> "TF-IDF uses an inverted index — for each term, I store which chunks contain it and their pre-computed TF-IDF scores. TF is the term's normalized frequency in the document: count divided by total document length, so a focused 50-word chunk scores higher than a diffuse 1000-word chunk for the same raw count. IDF is the log-ratio of total documents to documents containing the term — rare terms like 'FAISS' score 2.5x while common terms like 'the' score near 1.0. These multiply to give TF-IDF. At query time, I tokenize the query, look up each term in the inverted index, and accumulate scores. The whole query is served by index lookups — no document scanning. The limitation is lexical: two tokens must share surface form to score. 'Dense retrieval' and 'neural search' are semantically identical but score zero overlap, which is why hybrid retrieval adds a dense leg."

# Checkpoint 4.2 — BM25 Index (from scratch)

## What we built
- `BM25Index` from scratch — Robertson-Sparck Jones IDF, TF saturation (k1), length normalization (b)
- Two-pass indexing: corpus stats in pass 1, BM25 scores in pass 2
- Parameter sensitivity grid: k1 × b → monotonic on small uniform corpus
- Direct comparison with TF-IDF: identical rankings on 8 chunks with uniform length

## Core concepts

### 1. BM25 = TF-IDF + two key improvements

**Improvement 1 — TF saturation via k1:**
```
TF_BM25 = tf × (k1 + 1) / (tf + k1 × (1 - b + b × |d| / avgdl))
```
As tf → ∞, TF_BM25 → (k1 + 1). With k1=1.5, the cap is 2.5 — the 100th mention scores no more than the 10th. TF-IDF grows linearly: 100 mentions score 100× the first. BM25 models diminishing returns.

**Improvement 2 — Length normalization via b:**
```
b=0   → ignore document length completely
b=0.75 → partial normalization (production default)
b=1   → full normalization (short docs always win)
```
b=0.75 means a chunk 33% longer than average has its TF counts penalized by ~25%. A longer document saying "retrieval" 10 times is treated more like a shorter document saying it 7.5 times.

### 2. Robertson-Sparck Jones IDF — the stable version
```
IDF(t) = log((N - df(t) + 0.5) / (df(t) + 0.5) + 1)
```
The original BM25 IDF uses `log(N/df)`. This becomes negative when df > N/2 — a common term hurts query scores rather than simply contributing less. Robertson's IDF is always positive: adds 1 before taking the log.

### 3. Pre-computing scores at index time
We compute BM25 scores during `add()` — O(1) lookup at query time (just read pre-computed values), O(N×V) at index time. Alternative: store raw TF, compute BM25 at query time — faster indexing, slower retrieval.

The right choice depends on your query/index ratio. Read-heavy (many queries, rare updates): pre-compute. Write-heavy (frequent updates): compute at query time.

### 4. BM25 and TF-IDF tied on small uniform corpus
On 8 chunks with avgdl=51 tokens and little length variance, BM25's length normalization doesn't change rankings — all chunks are roughly the same length, so b has no effect. On a real corpus with document lengths varying from 50 to 5000 tokens, BM25 consistently outperforms TF-IDF by 5-15% on standard benchmarks (BEIR, MS MARCO).

### 5. Parameter values — industry defaults
- `k1=1.5`: good for long documents with repeated key terms
- `k1=1.2`: Elasticsearch's historical default, good for shorter passages
- `b=0.75`: industry consensus for mixed-length corpora
- `b=0`: when document length is irrelevant (titles, product names, single-sentence passages)

## Interview flashcards

1. **Q:** What does BM25's k1 parameter control?
   **A:** TF saturation. At k1=1.5, the maximum TF contribution is 2.5 regardless of raw term count — the 100th occurrence adds essentially nothing. Higher k1 allows more linear TF growth (less saturation). k1=0 gives binary presence/absence scoring. Default k1=1.5 is the industry consensus for general text.

2. **Q:** What does BM25's b parameter control?
   **A:** Document length normalization. b=0 ignores length (raw counts win). b=1 fully normalizes (short documents always win for the same relative frequency). b=0.75 is the industry default: partially penalizes longer documents without making short documents always win.

3. **Q:** Why is Robertson-Sparck Jones IDF preferred over the original BM25 IDF?
   **A:** The original IDF = log(N/df) goes negative when df > N/2 (very common terms). A negative IDF would reduce a query's score when a common term appears in the document — semantically wrong. Robertson's formula adds 0.5 and a +1 constant that makes IDF always positive and bounded away from zero.

4. **Q:** BM25 and TF-IDF produced identical rankings on your corpus. Is BM25 not better?
   **A:** BM25 is better on large corpora with length variance. Our corpus has 8 chunks of ~50 tokens each — no length variance, so b=0.75 has no effect. No repeated terms to saturate, so k1=1.5 has no effect. The parameters only manifest on realistic data. On BEIR and MS MARCO benchmarks, BM25 outperforms TF-IDF by 5-15%.

5. **Q:** You pre-compute BM25 scores at index time. What breaks when a new document is added?
   **A:** avgdl changes, which changes every document's length normalization. IDF changes for any term in the new document. The cleanest fix is a full rebuild of the inverted index after adding. For incremental indexing, you can approximate: keep old IDF scores and only recompute for terms appearing in the new document. This is what Elasticsearch's segment-based architecture does.

6. **Q:** When would you use BM25 over dense retrieval?
   **A:** For exact keyword queries, rare entity names, product SKUs, error codes, and any query where the user expects exact match behavior. "Error code 0x80070005" is a BM25 query — no paraphrase needed, exact token match is the right answer. "How do I fix permission denied?" is a dense query — semantic understanding needed.

## Code walkthrough prompt

*"Walk me through your BM25 implementation."*

> "BM25 improves on TF-IDF in two ways. First, TF saturation: the term frequency contribution is bounded by k1+1 via a saturation formula, so the 100th mention of a term contributes essentially nothing beyond the 10th. Second, length normalization: longer documents have their TF counts penalized proportionally to how much longer they are than the corpus average, controlled by parameter b=0.75. I use Robertson-Sparck Jones IDF rather than the original formula because the original goes negative for very common terms — Robertson's always stays positive. Indexing is two-pass: first collect document frequencies and document lengths, then compute final BM25 scores using the complete corpus statistics. On our 8-chunk corpus, BM25 and TF-IDF produce identical rankings because the corpus is too uniform — no length variance means b has no effect, no repeated terms means k1 has no effect. On real corpora with length variance, BM25 outperforms TF-IDF consistently."
