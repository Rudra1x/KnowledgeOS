## Core concepts

### 1. Environment isolation
An isolated Python env prevents dependency conflicts between projects. Your NestOpt-Q project runs on Python 3.14 in the `sovereign` env; RAG libraries (torch, faiss) lag behind cutting-edge Python releases and would fail to install. Isolation is a professional habit, not paranoia.

### 2. Why Python 3.11 (not 3.14)
- `torch` publishes prebuilt wheels ~6 months after each new Python
- `faiss-cpu` publishes wheels even slower
- New Python releases break C-extension packages until the maintainers catch up
- 3.11 is the current sweet spot: modern (structural pattern matching, better error messages) and universally supported

### 3. Folder structure as architecture
Each top-level folder is a Python package (`__init__.py`) and represents one plugin category:

core/ → interfaces, dataclasses, config
loaders/ → ingestion plugins
chunkers/ → splitting plugins
embedders/ → embedding backends
indexes/ → vector/keyword indexes
retrievers/ → retrieval algorithms
rerankers/ → reranking plugins
generation/ → LLM generation
eval/ → metrics + runner
configs/ → YAML pipeline configs
tests/ → unit tests
docs/ → checkpoint/milestone documentation
scripts/ → runnable entry points
results/ → benchmark outputs


When you build a second chunker later, it goes in `chunkers/`. When you swap FAISS for Qdrant, it goes in `indexes/`. The structure enforces separation of concerns before you write a line of code.

## Why the design choices

- **Conda over venv**: conda handles binary dependencies (faiss, torch CUDA) better than pip alone
- **`__init__.py` in every folder**: makes each folder a proper Python package so imports like `from core import Document` work
- **Dependency validation as a step**: verifying imports on day 1 costs 2 minutes; discovering a broken env on day 10 costs a day of debugging

## Interview flashcards

1. **Q:** Why not use the same Python env as your other projects?
   **A:** Dependency conflicts. Each project has its own version pinning. Isolation prevents "works on my machine" issues and lets you upgrade one project without breaking others.

2. **Q:** Why Python 3.11 for an ML project in late 2026?
   **A:** Binary-dependency lag. Libraries like torch, faiss, and vector DB clients publish wheels for older Python versions first. Choosing the latest Python guarantees you'll fight build errors instead of learning RAG.

3. **Q:** What's the difference between conda and venv?
   **A:** venv only manages Python packages; conda manages Python itself plus non-Python binaries (CUDA, MKL, faiss C++ libs). For ML workloads, conda is more robust.

4. **Q:** What does `__init__.py` do?
   **A:** Marks a folder as a Python package. Without it, imports like `from core import Document` fail. It can also expose selective names via `__all__`.

5. **Q:** Why separate `scripts/` from `core/`?
   **A:** Scripts are entry points (run once, produce output). Core modules are library code (imported everywhere). Mixing them tempts you to put business logic in scripts, which is untestable and unreusable.
