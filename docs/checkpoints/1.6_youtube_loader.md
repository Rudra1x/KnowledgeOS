# Checkpoint 1.6 — YouTube Transcript Loader

## What we built
- `YouTubeLoader` with `segment` and `full` modes
- URL parser handling all 4+ YouTube URL formats (watch, youtu.be, shorts, raw ID)
- Language fallback list — auto-picks the best available caption track
- Graceful handling of 3 failure modes: transcripts disabled, no matching language, unavailable video
- Timestamp formatting (H:MM:SS / M:SS) + deep-link URL generation
- Preservation of `start_time_seconds` and `duration_seconds` for temporal reasoning

## Core concepts

### 1. Temporal metadata unlocks precise citations
Traditional citations point to "this document." Video citations point to "this exact moment." A user asks "what did the speaker say about attention?" and the answer comes with `[at 3:42]`, clickable to jump straight there.

The deep-link URL is built at ingestion time — `https://youtu.be/VIDEO_ID?t=222` — so every downstream stage gets citation-ready URLs for free.

### 2. Segment vs full mode
- **Segment**: one Document per transcript segment (~1 sentence each). Preserves timestamps. Best for "when did X happen" queries.
- **Full**: one Document containing the whole transcript. Timestamps lost. Best for "what does this video cover" queries.

Same shape as CSV row-vs-file trade-off: match the mode to the query pattern.

For M1, `segment` is the default because timestamps are the unique value proposition of video RAG.

### 3. External APIs fail often
YouTube transcripts fail in three ways in production:
- `TranscriptsDisabled` — the uploader turned captions off
- `NoTranscriptFound` — no captions in your requested languages
- `VideoUnavailable` — deleted, private, or geo-blocked

A production loader treats these as *normal* outcomes, logs them, and returns an empty list — not a crash. Your ingestion pipeline shouldn't fall over because one URL out of 10,000 was pulled.

### 4. URL parsing needs a decision tree
YouTube alone has 4+ URL formats:
- `https://www.youtube.com/watch?v=VIDEO_ID`
- `https://youtu.be/VIDEO_ID`
- `https://youtube.com/shorts/VIDEO_ID`
- Raw 11-char ID

Pragmatic approach: `urlparse()` first, then branch by netloc/path pattern. This structure generalizes to every SaaS URL you'll parse in your career (Zoom recordings, Slack messages, Notion pages).

### 5. Language fallback list
`["en", "en-US", "en-GB"]` — try each in order. If the video has any of them, use it. If not, return empty (graceful degradation). This matches how browsers do content negotiation.

## Why the design choices

- **Segment mode by default**: timestamps are the unique value proposition of video RAG
- **`youtube-transcript-api` (unofficial)**: uses the same public endpoint YouTube's own web player uses, no API key or quota
- **Deep-link URL pre-built at ingestion**: every downstream stage inherits it for free
- **Language list, not single value**: matches how content-negotiation should work in general
- **Exception-per-failure-mode logging**: users see *why* a specific video failed, can decide whether to retry / skip / report

## Interview flashcards

1. **Q:** Why is video RAG different from document RAG?
   **A:** Temporal metadata. Every transcript segment has a start time, which lets citations reference the exact moment. That "jump to this second" capability transforms the UX — users don't have to trust the RAG, they can verify in one click. No document format offers this.

2. **Q:** How do you handle videos with disabled or missing transcripts?
   **A:** Catch the specific exceptions — `TranscriptsDisabled`, `NoTranscriptFound`, `VideoUnavailable` — log them clearly, and return an empty list. External APIs fail often; the ingestion pipeline shouldn't crash on the 47th URL out of 10,000.

3. **Q:** Segment mode or full mode — how do you pick?
   **A:** Same principle as CSV row-vs-file. Segment mode when the query pattern is "when did X happen" — needs timestamp granularity. Full mode when the query is "what does this cover" — needs the whole thing as context. Real systems support both and let the query router decide.

4. **Q:** Why build the deep-link URL at ingestion time?
   **A:** Ingestion runs once; UI runs every session. Computing `?t={seconds}` at ingestion means every retrieval, every citation, every UI render gets it for free. Computing it lazily means rebuilding the same string thousands of times.

5. **Q:** What breaks if a video's transcript is machine-generated versus human-authored?
   **A:** Nothing structural, but quality drops significantly. ASR (auto-captions) mis-hears technical terms — "attention mechanism" becomes "attention mechanism-ism," or proper nouns get mangled. Downstream, retrieval on those garbled terms fails. In production, you'd flag `is_generated=True` in metadata (the API exposes this) and either downweight in retrieval or route through a text-cleaning pass.

## Code walkthrough prompt

*"How would you RAG a corpus of training videos?"*

> "I use youtube-transcript-api, which pulls captions from the same public endpoint YouTube's web player uses — no API key, no quota. The URL parser handles all four common YouTube URL shapes and raw video IDs, so users don't have to normalize before calling. Transcripts come back as a list of segments, each with text, start-time, and duration. I emit one Document per segment by default because timestamps are the unique value of video RAG — every citation can jump to the exact second via a deep-link URL that I pre-build at ingestion (`https://youtu.be/VIDEO_ID?t=222`). For queries where timestamps don't matter, there's a `full` mode that concatenates all segments into one Document. Failures are common — transcripts disabled, no matching language, video unavailable, geo-blocked — and each has its own exception; I catch them cleanly, log which video failed and why, and return an empty list rather than crash the ingestion. In production, this is what separates a pipeline that ingests a 3,000-video corpus reliably from one that dies at video 47 and taught you nothing."
