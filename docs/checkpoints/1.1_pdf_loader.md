# Checkpoint 1.1 — PDF Loader

## What we built
- `PDFLoader` using `pdfplumber` (layout-aware, table-capable)
- Per-page `Document` emission — preserves page metadata for citations
- Table extraction as separate `Document`s with `content_type: "table"`
- Image-only page detection with `ocr_needed` flag — never silently loses data
- Noise-table filter (≥2 rows, ≥2 meaningful columns)

## Core concepts

### 1. PDFs are layout formats, not text formats
A PDF describes where to *draw* glyphs on a page, not what the semantic text is. Any text you extract is *reconstructed* from the visual layout. This is why the same PDF can look perfect in one library and garbage in another — different reconstruction heuristics.

### 2. Five categories of PDF content
| Category | pypdf handles? | Real fix |
|----------|----------------|----------|
| Plain paragraphs | ✅ | pypdf is fine |
| Multi-column layouts | ⚠️ reads across columns | pdfplumber / pymupdf with layout detection |
| Tables | ❌ | pdfplumber.extract_tables() or camelot |
| Images / diagrams | ❌ silently skipped | Extract images → caption via VLM (M12) |
| Scanned PDFs | ❌ returns empty | OCR (pytesseract / easyocr, M12) |

### 3. Per-page vs whole-document
We emit one `Document` per page. Why:
- Preserves page-number metadata for citations ("see page 42")
- Enables page-level filtering downstream
- Chunker still runs across pages independently

Alternative (whole-doc) loses page provenance — chunks span pages ambiguously.

### 4. Precision-vs-recall in table extraction
`pdfplumber` casts a wide net for tables — high recall but low precision. It found 3 "tables" in your NestOpt-Q PDF, and all 3 were false positives (layout artifacts, not real tabular data). `pypdf` had zero recall on tables (missed everything). Neither is objectively right; you pick based on downstream tolerance and add filters.

Our filter: require ≥2 rows AND ≥2 non-empty header columns. This eliminated the 3 false positives on your test PDF while preserving real tables on other documents.

### 5. `content_type` metadata as the extensibility hook
By tagging each `Document` with `content_type: "text" | "table" | "ocr_needed"`, downstream stages can:
- Filter (drop tables if they're mostly noise on a given corpus)
- Boost or downweight at retrieval time
- Route type-specific queries differently

If we'd concatenated tables into page text, we'd have lost the ability to make any of these decisions later without a reprocess.

## Why the design choices

- **`pdfplumber` over `pypdf`**: layout awareness, native table extraction, better multi-column handling
- **Per-page docs, not one-doc-per-file**: preserves page provenance for citations
- **Tables as separate `Document`s**: keeps prose retrieval clean; table queries can be routed differently
- **`ocr_needed` sentinel content**: image-only pages are flagged, not silently dropped — a user asking "why isn't page 7 searchable?" gets an answer
- **Noise filter**: pdfplumber is high-recall/low-precision; the filter shifts the balance toward usable output

## Interview flashcards

1. **Q:** Why is PDF extraction harder than text extraction?
   **A:** PDF is a layout format — glyphs positioned on a page — not a semantic text format. Text is *reconstructed* from spatial coordinates, and different extractors use different heuristics. Multi-column layouts, tables, and scanned images all break naive extraction.

2. **Q:** Why per-page instead of one Document per PDF?
   **A:** Citation quality. Users want to know *which page* a claim came from. Per-page preserves that provenance. Chunking still happens across all pages, so it doesn't compromise retrieval.

3. **Q:** How does your loader handle image-only PDF pages?
   **A:** It detects them (empty text extraction + present images) and emits a placeholder Document with `content_type: "ocr_needed"`. This ensures the page is visible in the corpus inventory even though its content isn't searchable yet. OCR would be a follow-up loader stage.

4. **Q:** Your table extractor found 3 tables that were false positives. How would you handle this in production?
   **A:** Two levers. First, the noise filter (≥2 rows, ≥2 meaningful cols) rejects layout artifacts. Second, per-document routing — a router inspects the PDF first (is it a paper, a slide deck, a scanned form?) and picks the right extractor. `pdfplumber` for narrative reports, `camelot` for complex tables, OCR for scans.

5. **Q:** What's the failure mode of extracting tables *inline* with text instead of as separate documents?
   **A:** You lose the ability to distinguish table content from prose downstream. If you later want to boost table matches for factoid queries, or filter them out for narrative queries, you can't — the type information is gone. Splitting them at ingestion is cheap; merging them later is impossible without reprocessing.

## Code walkthrough prompt

*"Walk me through how you'd RAG a corpus of PDFs."*

> "The loader uses pdfplumber, which is layout-aware. For each page, I extract prose text and any detected tables separately, emitting them as distinct Documents with a `content_type` metadata field — `'text'`, `'table'`, or `'ocr_needed'` for image-only pages. Each Document carries its page number so citations can reference the source location. Tables get a noise filter — real tables have at least 2 rows and 2 meaningful columns — because pdfplumber's default heuristic is high-recall/low-precision and picks up layout artifacts. Image-only pages aren't silently dropped; they're flagged for OCR follow-up. Downstream stages can filter or route by `content_type`, which is the extensibility hook that lets a production system add VLM captioning or OCR without reprocessing the whole corpus."
