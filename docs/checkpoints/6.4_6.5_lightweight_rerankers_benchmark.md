# Checkpoint 6.4 — SimilarityReranker + MetadataReranker

## What we built
- `SimilarityReranker` — re-scores with a different embedder or averaged query expansion
- `MetadataReranker` — multiplicative boosts by recency, source, content type, keywords
- Recency test: exponential decay correctly orders 2025 doc before 2020 doc
- Key finding: E5 re-scoring of BGE retrievals = 0.500 (cross-embedding-space corruption); keyword boost = 0.700 (query-agnostic); recency boost = valid

## Core concepts

### 1. Embedding spaces are model-specific — mixing them is wrong

BGE-small and E5-small have different embedding geometries. BGE's training objective produces one geometry; E5's dual-prefix training produces another. A BGE-embedded chunk vector and an E5 query vector are not in the same space — their dot product is meaningless as a similarity score.

This is why the similarity reranker scored 0.500 when re-scoring BGE retrievals with E5:
```
BGE corpus vectors (from retrieval):   [0.31, -0.12, 0.08, ...]  [BGE space]
E5 query vector (from reranker):       [0.22, 0.09, -0.15, ...]  [E5 space]
dot product:                           meaningless geometric operation
```

**The fix:** the corpus must be embedded with the same model used for re-scoring. SimilarityReranker is only valid when re-scoring with the same embedder family used at indexing time — or as a query expansion tool (average multiple query phrasings before scoring).

### 2. Query expansion via averaging
```python
all_queries  = [query] + self.query_expansion
query_vecs   = [embedder.embed_query(q) for q in all_queries]
query_vec    = mean(query_vecs)  # averaged embedding
```
Averaging K query phrasings in embedding space produces a centroid that's closer to all relevant documents than any single phrasing alone. This is valid within one embedding model — you're averaging vectors in the same space. It's the geometric version of multi-query retrieval.

### 3. Metadata boosts — query-agnostic vs query-sensitive

**Query-agnostic boost (wrong for precision):**
```python
keyword_boost = {"retrieval": 1.2, "BM25": 1.3}
```
Always boosts chunks containing "retrieval" or "BM25", regardless of the query. For "What is RAG?", this incorrectly promotes the BM25 chunk above the RAG chunk — because BM25 chunk also contains the word "retrieval."

**Query-sensitive boost (correct pattern):**
```python
def boost(chunk, query):
    for kw, multiplier in keyword_boost.items():
        if kw.lower() in query.lower() and kw.lower() in chunk.content.lower():
            return multiplier
    return 1.0
```
Only boost when the keyword appears in both the query AND the chunk. This is a precision gain: we boost chunks that specifically match the query's vocabulary.

### 4. Recency is query-agnostic and always valid

Unlike keyword boosts, recency doesn't depend on the query. A 2025 document is always preferred over a 2020 document with identical content. The exponential decay model:

```python
decay = exp(-0.693 * age_days / half_life)
boost = 1.0 + (max_boost - 1.0) * decay
```

At age=0: boost = max_boost (e.g., 2.0). At age=half_life: boost = 1.5 (halfway). At age=∞: boost = 1.0 (no boost). Exponential decay is the right model because the information value of a document decays faster when recent — a 2-week-old document is much more relevant than an 18-month-old one, but the difference between 5-year-old and 6-year-old is negligible.

### 5. Multiplicative boosting — why multiply, not add
```python
final = base_score * boost
```
Multiplicative boosting preserves the relative ordering of the original scores while shifting all scores by a consistent factor. Additive boosting (`final = base + 0.1`) would change rankings differently for high-scoring vs low-scoring chunks. Multiplicative is the right formulation for "prefer this type by X%."

## Interview flashcards

1. **Q:** Why did the similarity reranker score 0.500 when you re-scored BGE retrievals with E5?
   **A:** BGE and E5 have different embedding geometries — different training objectives produce different vector spaces. Re-scoring BGE corpus vectors with an E5 query vector computes a dot product between vectors in incompatible spaces. The result is geometric noise, not similarity. The similarity reranker is only valid when the reranking embedder matches the indexing embedder.

2. **Q:** Your metadata keyword boost hurt recall (0.700 vs 0.900 baseline). What's the fix?
   **A:** Make it query-sensitive. The current boost fires when a keyword appears in the chunk, regardless of the query. The fix: only boost when the keyword appears in BOTH the query and the chunk. This ensures "retrieval" gets boosted only for queries that ask about retrieval — not for "What is RAG?" queries where the RAG chunk is the correct answer.

3. **Q:** Why is recency boost valid to apply unconditionally while keyword boost is not?
   **A:** Recency is query-agnostic — a newer document is almost always preferred regardless of what's being asked. Keyword preference is query-dependent — "BM25" is relevant for BM25 queries but not for RAG queries. Unconditional application of keyword boosts changes rankings for queries that don't need the boost.

4. **Q:** Why exponential decay for recency instead of linear?
   **A:** Linear decay would make very old documents negative (if age > max_value). Exponential decay is always positive and asymptotes to 1.0 (no boost) for very old documents. It also better models information relevance: the difference between a 1-week-old and 3-week-old document is more significant than between a 2-year-old and 3-year-old document.

5. **Q:** When would SimilarityReranker genuinely help?
   **A:** Two valid use cases. (1) Query expansion: average the embeddings of 3 query phrasings, re-score with the averaged vector — this works within one embedding model and is the geometric equivalent of multi-query retrieval. (2) Upgrading the retrieval embedder: if you indexed with BGE-small (fast) and want to rerank with BGE-large (higher quality), re-index the top-20 candidates with BGE-large queries and re-rank.

## Code walkthrough prompt

*"Explain SimilarityReranker and MetadataReranker and when they're appropriate."*

> "SimilarityReranker re-scores candidate chunks using a potentially different embedder or a query expansion average. The key constraint: the reranking embedder must be in the same embedding space as the corpus vectors — you can't re-score BGE-indexed chunks with E5 queries because they live in different geometric spaces. We proved this empirically: E5 re-scoring of BGE retrievals dropped recall to 0.500 — the dot products were computing meaningless cross-space similarity. The valid use case is query expansion: average the embeddings of 3 query phrasings (all from the same model) to produce a centroid vector that's geometrically closer to more relevant chunks than any single phrasing. MetadataReranker applies multiplicative boosts — multiply the base score by a factor based on metadata. Recency boost is valid unconditionally: newer documents are always preferred. Keyword boost is not valid unconditionally — boosting 'retrieval' for all queries promotes the BM25 chunk even when the query asks about RAG. The production pattern: apply keyword boosts only when the keyword appears in both the query and the chunk. Our benchmark showed query-agnostic keyword boost scored 0.700 — worse than the 0.900 baseline. Recency boost correctly ordered 2025 documents before 2020 documents with identical content."

# Checkpoint 6.5 — Reranking Benchmark

## Benchmark results

| Rank | Pipeline | recall@1 | recall@3 | MRR | time/10q |
|------|----------|----------|----------|-----|----------|
| 1 | Vector + MS-MARCO | 1.000 | 1.000 | 1.000 | 3.2s |
| 2 | Vector + BGE | 1.000 | 1.000 | 1.000 | 16.6s |
| 3 | Hybrid + MS-MARCO | 1.000 | 1.000 | 1.000 | 1.9s |
| 4 | Hybrid + BGE | 1.000 | 1.000 | 1.000 | 10.8s |
| 5 | Vector (no rerank) | 0.900 | 1.000 | 0.950 | 0.5s |
| 6 | Hybrid (no rerank) | 0.900 | 1.000 | 0.950 | 0.6s |
| 7 | Vector + LLM | 0.900 | 1.000 | 0.950 | 360.0s |
| 8 | Vector + Metadata | 0.700 | 1.000 | 0.850 | 0.5s |

## Core concepts

### 1. The central finding: reranking outperforms better retrieval

```
Vector alone:          r@1=0.900  0.5s/10q
Vector + MS-MARCO:     r@1=1.000  3.2s/10q   ← +2.7s for +11% recall
Agentic retriever:     r@1=1.000  230s/10q   ← +229.5s for same +11% recall
```

A 22MB cross-encoder closes the recall gap that required a 23s/query agentic retriever — at 72× lower latency. The retrieve-then-rerank pipeline is the production standard because it's the most economical path to perfect recall.

### 2. Hybrid + MS-MARCO: the fastest perfect-recall pipeline

```
Hybrid + MS-MARCO:  r@1=1.000  1.9s/10q  ← fastest
Vector + MS-MARCO:  r@1=1.000  3.2s/10q
```

Hybrid retrieval fetches candidates via both BM25 and dense in one pass (fast). MS-MARCO reranks in 2ms/query. Total: 1.9s for 10 queries = 190ms/query. At this latency, you can serve 5+ concurrent users with a single CPU core.

### 3. The LLM reranker is definitively outclassed

```
Vector + LLM:     r@1=0.900  360s/10q  ← same recall as baseline, 720× slower
Vector + MS-MARCO: r@1=1.000  3.2s/10q ← better recall, 112× faster
```

LLM reranking is only justified for custom ranking criteria that no cross-encoder can express. For semantic relevance reranking, the cross-encoder wins on every dimension.

### 4. Metadata reranker is the worst performer

```
Vector + Metadata:  r@1=0.700  0.5s/10q
Vector alone:       r@1=0.900  0.5s/10q
```

Query-agnostic keyword boosts hurt precision by promoting chunks that contain the boosted keyword even when it's not relevant to the query. The metadata reranker is only valid for recency/source boosts applied as a second layer after a neural reranker, or with query-sensitive keyword logic.

### 5. The complete quality/latency frontier

```
0.5s,  r@1=0.900: Vector (baseline)
1.9s,  r@1=1.000: Hybrid + MS-MARCO  ← best real-time option
3.2s,  r@1=1.000: Vector + MS-MARCO  ← close second
10.8s, r@1=1.000: Hybrid + BGE       ← GPU: use this; CPU: use MS-MARCO
230s,  r@1=1.000: Agentic retriever  ← async only
```

The production deployment decision is now simple: pick the point on this frontier that matches your latency SLA.

### 6. The M0-M6 arc complete

M0 established the baseline: vector retrieval, recall@1=0.900. Every milestone since was a path to closing the 0.1 recall gap:
- M2-M3: better chunking and embedding didn't fully close it (small corpus)
- M4: better indexing didn't close it (same failure mode for all methods)
- M5: agentic retrieval closed it at 23s/query
- M6: cross-encoder reranking closed it at 0.02s/query

The journey from M0 to M6 proves the architectural principle: **recall@3 is a retrieval problem; recall@1 is a reranking problem.**

## Interview flashcards

1. **Q:** Your benchmark showed agentic retrieval and cross-encoder reranking both achieve r@1=1.000. Which do you deploy?
   **A:** Cross-encoder reranking. Same recall, 72× lower latency (3.2s vs 230s for 10 queries), simpler architecture, lower operational complexity. Agentic retrieval is justified for async workflows where latency doesn't matter and complex multi-step reasoning is required. For real-time RAG, cross-encoder wins by every metric except interpretability.

2. **Q:** Why is Hybrid + MS-MARCO the fastest perfect-recall pipeline?
   **A:** Hybrid retrieval fetches candidates via BM25 + dense in parallel — fast, no LLM calls. MS-MARCO is the lightest cross-encoder (22MB, 6 layers). Together they produce 1.9s for 10 queries = 190ms/query. Vector retrieval is slightly slower because it only uses one retrieval method; hybrid's dual-method candidate set sometimes skips the re-scoring work by providing better initial candidates.

3. **Q:** The LLM reranker scored the same as the baseline at 720× the cost. Why did you include it in the benchmark?
   **A:** To make the comparison definitive. "LLM reranking is too slow" is an intuition; "720× slower for no quality gain" is a number that ends the discussion. Benchmark results replace intuition. The LLM reranker has one valid use case (custom criteria) that the benchmark doesn't test — but for semantic relevance reranking, the data is unambiguous.

4. **Q:** Metadata reranker scored 0.700 — worst result. Would you ever use it?
   **A:** Yes, in two scenarios. (1) Recency boost on top of a neural reranker — always valid, improves freshness without hurting precision. (2) Query-sensitive keyword boost: only boost when the keyword appears in both query and chunk — avoids the query-agnostic precision problem we measured. Never use query-agnostic keyword boost as the sole reranker.

5. **Q:** The benchmark shows recall@3=1.000 for every pipeline. What does that tell you?
   **A:** The correct chunk is always in the top 3 from retrieval. Reranking's job is to move it from rank 2 or 3 to rank 1. This confirms the architectural principle: retrieval is a recall@3 problem (get the right chunk into the candidate set); reranking is a precision@1 problem (put the right chunk first). Both stages are necessary; neither alone is sufficient.
