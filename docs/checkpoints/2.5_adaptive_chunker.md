# Checkpoint 2.5 — AdaptiveChunker

## What we built
- `AdaptiveChunker` — density-driven variable chunk sizes per paragraph
- Three fast text statistics: avg word length, sentence density, special char ratio
- Weighted density score (0.0–1.0) → linear interpolation to target size
- Per-chunk `density_score` and `target_size` metadata (visible, debuggable)
- Empirically verified: code (0.87 density, 311 avg target) vs prose (0.53 density, 495 avg target) — 37% difference

## Core concepts

### 1. The core insight — information density varies within documents
A technical documentation file might have:
- Dense API reference (function signatures, types, parameters) → should chunk small
- Prose explanation paragraphs → can chunk larger
- Code examples → very dense, chunk small

One global `chunk_size` serves neither well. Adaptive sizing per paragraph gives each content type its appropriate granularity.

### 2. Three density signals
```python
# Signal 1: avg word length (shorter = denser)
# Rationale: code uses short tokens (k1, tf, n), prose uses long words (retrieval, normalization)
avg_word_len_score = (10 - avg_word_len) / 8   # normalize to [0,1]

# Signal 2: sentence density (sentences per 100 words)
# Rationale: definitions and code comments have many short sentences; prose has few long ones
sent_density_score = sentence_count_per_100_words / 10

# Signal 3: special char ratio (colons, brackets, equals)
# Rationale: code, formulas, structured data use : = () [] {} heavily; prose doesn't
special_score = special_char_count / len(text) / 0.15
```

These are *model-free* — no embeddings, no NLP. Three character-level statistics in O(N) time.

### 3. Weighted combination
```python
density = 0.5 * word_len_score + 0.3 * sent_density_score + 0.2 * special_score
```

Word length gets the highest weight (0.5) because it's the most discriminative single signal across prose vs code. Sentence density is secondary (0.3). Special chars are tertiary (0.2) — informative for code but noisy on some prose.

These weights are heuristic. In production, you'd validate on a labeled sample: does the density score correctly predict human judgment of "this is dense technical content"?

### 4. Linear interpolation to target size
```python
target = max_chunk_size - density * (max_chunk_size - min_chunk_size)
# density=0.0 → target = max_chunk_size (sparse → big chunks)
# density=1.0 → target = min_chunk_size (dense → small chunks)
```

Simple, interpretable, invertible. If you want to understand why a chunk got a specific target size, you can compute it by hand.

### 5. Target is a ceiling, not a floor
When the source content is shorter than the target, the chunk is just the content. `target_size=495` doesn't mean chunks are padded to 495 chars — it means chunks are allowed to grow up to 495 before splitting. On the code sample, target=311 but actual=131-251 because the code paragraphs themselves were short.

### 6. Observability: density_score + target_size in metadata
```python
metadata = {
    "density_score":  0.725,
    "target_size":    356,
    "chunk_size_chars": 203,
}
```

When debugging "why is this chunk small?", `density_score=0.725` and `target_size=356` immediately explain the decision. Without this, you'd have to rerun the density calculation yourself to understand the output.

### 7. Benchmark: tied for first
adaptive achieved r@1=1.000 in the benchmark. Smaller average chunk sizes (291 chars) vs overlapping (454 chars) produced tighter embeddings that matched per-paragraph gold set queries more precisely.

## Why the design choices
- **Model-free statistics**: no embedding cost at chunking time; adaptive sizing is a free improvement
- **Per-paragraph density**: density is a local property; a whole-document average would miss intra-document variation
- **Linear interpolation**: simple, interpretable, debuggable; non-linear curves add complexity without clear benefit
- **Weights as class constants not parameters**: good defaults for most text; expose as constructor params only if users ask

## Interview flashcards

1. **Q:** Why does adaptive chunking use character statistics instead of embeddings?
   **A:** Cost. Embeddings are expensive. We already doubled ingestion cost in semantic chunking. Character statistics — word length, sentence density, special char ratio — are computed in O(N) with no model calls. They're "cheap signals before expensive ones" — the engineering principle of using the simplest tool that works.

2. **Q:** Why is avg word length a density signal?
   **A:** Code and technical formulas use short tokens: `k1`, `tf`, `idf`, `n`, `b`, `v`. Prose uses long descriptive words: `retrieval`, `normalization`, `similarity`. Short avg word length is a reliable, fast proxy for "this is dense technical content."

3. **Q:** Target size is 495 but actual chunk is 280 chars. Is that a bug?
   **A:** No. Target is a ceiling for splitting, not a floor for padding. If the source content is shorter than the target, the chunk is just the content. Padding to hit a target would add meaningless whitespace that corrupts embeddings.

4. **Q:** How would you validate the density scoring weights in production?
   **A:** Label a sample of 100 paragraphs as "dense technical" or "sparse prose" (1 hour of human work). Compute the three signals on each. Tune weights to maximize the AUC of the binary classifier. Alternatively, correlate density score with retrieval quality per chunk — dense content should benefit more from smaller targets.

5. **Q:** Where does adaptive chunking outperform recursive?
   **A:** On mixed corpora — documentation with code blocks, technical reports with prose + formulas, API references with descriptions + signatures. Recursive uses one global chunk_size; adaptive scales each section to its content density. The quality gap widens as the corpus becomes more heterogeneous.

6. **Q:** How is adaptive chunking different from semantic chunking?
   **A:** Semantic chunking uses embeddings to find *where* to split (topic shift detection). Adaptive chunking uses statistics to determine *how large* splits should be (density-based sizing). They're orthogonal — you could combine them: use semantic splits for *where*, adaptive for *how big*.

## Code walkthrough prompt

*"How does your adaptive chunker decide chunk size?"*

> "It computes a density score per paragraph using three model-free statistics. First, average word length — short words (code tokens like k1, tf, n) signal dense content; long words (retrieval, normalization) signal sparse prose. Second, sentence density — many sentences per 100 words means dense definitional content; few long sentences means flowing prose. Third, special character ratio — colons, brackets, equals, and braces are heavy in code and formulas, light in prose. These three combine into a weighted score between 0 and 1. The score maps linearly to a target chunk size: density=0 gets the max size (900 chars for sparse prose), density=1 gets the min size (200 chars for dense code). Each paragraph is split with its own target, and the final chunk carries both `density_score` and `target_size` in metadata so you can understand exactly why any chunk has its size. In our benchmark, code averaged density=0.75 and target=311 chars, while prose averaged density=0.53 and target=495 — a 37% difference. The chunker is entirely model-free, adding zero embedding cost."
