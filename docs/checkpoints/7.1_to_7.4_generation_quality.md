# Checkpoint 7.1 — Prompt Engineering + Citation

## What we built
- `build_prompt()` — grounded system prompt with three faithfulness rules + numbered context passages
- `extract_citations()` — parses [N] from generated answers, returns {N: Chunk} lookup
- Updated LocalLLMGenerator and OpenRouterGenerator to use the new prompt builder
- Verified: all three test answers cited correctly, grounded in retrieved context

## Core concepts

### 1. The system prompt is the faithfulness contract
Three rules that prevent hallucination:
```
1. Cite every factual claim using [N] where N is the passage number.
2. If the answer is not in the context, say: "The provided context does not contain..."
3. Do not add facts from your own knowledge — only use the context.
```

Without these, Qwen2.5-3B supplements retrieved facts with parametric memory. "BM25 was developed by Robertson" may be correct, but if it's not in the retrieved chunks, the model shouldn't say it. The system prompt makes this the default behavior.

### 2. Numbered passages make citation trivial
```
[1] (source: corpus.txt, chunk_id: abc12345)
BM25 is a sparse retrieval algorithm...

[2] (source: corpus.txt, chunk_id: def67890)
Dense retrieval uses neural embeddings...
```

The model learned from pretraining that `[N]` after a claim means "passage N supports this." This formatting elicits citation without fine-tuning. The `chunk_id` in the passage header enables downstream traceability — every cited claim maps to an exact source document.

### 3. extract_citations() — the traceability layer
```python
cited = extract_citations(answer, reranked_chunks)
# → {1: chunk_for_BM25, 2: chunk_for_dense}
```
Every `[N]` in the answer maps to the exact `Chunk` object with `chunk_id`, `doc_id`, `source`, and `metadata`. You can trace any generated claim back to the source document. This is the foundation for compliance auditing, debugging, and user trust.

### 4. Grounded prompts don't eliminate hallucination entirely
The system prompt dramatically reduces hallucination but doesn't eliminate it. The model may:
- Paraphrase chunks in ways that introduce subtle inaccuracies
- Cite a passage that doesn't actually support the claim
- Add connective tissue between chunks that's not grounded

This is why faithfulness checking (7.3) exists — the prompt is the first defense, NLI checking is the second.

### 5. The verbose answer problem
Query 2 ("How does hybrid retrieval work?") produced a multi-sentence answer that directly quoted the passage. Technically faithful but verbose. Fix: add "Be concise, paraphrase rather than quote" to the system prompt rules. The prompt is tunable — treat it as a parameter, not a constant.

## Interview flashcards

1. **Q:** Why do you use a numbered context format [1], [2] instead of chunk IDs?
   **A:** Numbered references are in the model's pretraining distribution — academic papers, Wikipedia footnotes, legal documents all use [N] notation. The model already knows [N] means "this is supported by reference N." Chunk IDs like `abc12345` are not in pretraining data. Numbered format elicits reliable citation without fine-tuning.

2. **Q:** What three rules does your system prompt enforce?
   **A:** Cite every factual claim with [N]. If the answer isn't in context, say so explicitly. Don't add facts from parametric knowledge. Together these rules constrain the model to the retrieved context.

3. **Q:** extract_citations() returns {1: Chunk}. What does this enable downstream?
   **A:** Complete claim traceability. Every cited number maps to the exact chunk with chunk_id, doc_id, source, and metadata. A compliance auditor can say "show me the source for claim [2]" and get the exact passage. A debugger can say "why did the model cite [1] for this claim?" and examine the chunk.

4. **Q:** Your system prompt says "do not add facts from your own knowledge." Is this reliably enforced?
   **A:** Mostly, not perfectly. The model respects the instruction 80-90% of the time. Edge cases: when context is ambiguous, when the model is very confident in parametric knowledge, when the prompt is long and the instruction gets deprioritized. Faithfulness checking (checkpoint 7.3) catches the remaining violations.

5. **Q:** How would you modify the prompt for a legal research use case?
   **A:** Add domain-specific rules: "Always cite the specific statute or case number when available." "When citing legal precedent, include the jurisdiction." "If the context contains conflicting legal positions, present both." The prompt is the primary control surface — tune it for your domain.

## Code walkthrough

*"Walk me through your prompt engineering design."*

> "The prompt has two parts. The system message establishes the faithfulness contract: three explicit rules — cite every claim with [N], say 'not in context' if the answer isn't there, don't add parametric knowledge. The user message presents numbered context passages: [1] (source + chunk_id)\ncontent, [2] content, then the question. The numbered format is in the model's pretraining distribution from academic papers and footnotes, so it reliably produces [1] and [2] citations without fine-tuning. `extract_citations()` then parses these numbers and maps them back to the exact Chunk objects, enabling complete traceability from generated claim to source document. The prompt is a parameter, not a constant — 'be concise, paraphrase rather than quote' can be added if the model is verbose. The system prompt is the first faithfulness layer; NLI checking is the second."

# Checkpoint 7.2 — Context Compression

## What we built
- `ContextCompressor` — three strategies: similarity, LLM, budget
- Similarity: sentence-level cosine scoring, removes low-relevance sentences
- LLM: extracts only relevant sentences via Qwen2.5-3B (expensive, accurate)
- Budget: keep-until-N-words (instant, cost-controlled)
- Verified: similarity correctly removed "ses embedding similarity" boundary artifact at ratio=0.578

## Core concepts

### 1. Why compress before generation
Retrieved chunks contain the answer plus surrounding context. For "What is BM25?", a 400-word chunk might have 80 words directly about BM25 and 320 words about adjacent topics. Sending all 400 to the generator:
- Costs more tokens (API cost)
- Distracts the model (surrounding context competes for attention)
- May cause the model to address tangential content

Compression extracts the 80 relevant words, reducing cost and improving focus.

### 2. Compression value scales with chunk size
On 45-word chunks: similarity compression achieves ratio=0.578, saving 19 words. Modest.
On 400-word chunks: ratio=0.578 saves 168 words × 3 chunks = 504 words ≈ 378 tokens.
At $0.001/1K tokens (GPT-4): $0.38 saved per query × 10K queries/day = $3,800/day.

### 3. Similarity compression — unsupervised noise removal
Split chunk into sentences → embed each sentence → cosine similarity to query → keep top_k by score.

The BM25 chunk's first sentence ("ses embedding similarity to detect topic shifts") scored low against "What is BM25?" — correctly dropped. The BM25 content sentences scored high — kept. This is unsupervised noise removal via embedding geometry.

### 4. The three strategies serve different needs
```
Similarity: fast (419ms), accurate, needs embedder — production default for quality
LLM:        slow (21s/chunk), most accurate, needs Ollama — async/offline only
Budget:     instant (0ms), no model, deterministic — use when speed is critical
```

### 5. Compression metadata for monitoring
```python
chunk.metadata["compression_ratio"]  # 0.578 → 42% of content removed
chunk.metadata["original_length"]    # 45 words before
chunk.metadata["compressed_length"]  # 26 words after
```

A consistently low ratio (0.3) means chunks are dense and compression is earning its cost. A consistently high ratio (0.95) means chunks are already focused — compression adds overhead with no benefit.

## Interview flashcards

1. **Q:** What is context compression and what problem does it solve?
   **A:** Context compression extracts only the sentences from each retrieved chunk that are relevant to the query, discarding surrounding context. It reduces token cost (API savings at scale), reduces model distraction (surrounding content competes for attention), and improves answer conciseness.

2. **Q:** Your similarity compressor removed a boundary artifact sentence. How?
   **A:** The sentence "ses embedding similarity to detect topic shifts" scored low cosine similarity against "What is BM25?" — different semantic regions. The BM25 sentences scored high. By keeping only top-k sentences by similarity score, the compressor removed noise that originated from chunking overlap.

3. **Q:** Why does the LLM compressor return ratio=1.0 on your 45-word chunks?
   **A:** The LLM sees a 45-word BM25 chunk and judges all sentences relevant to a BM25 question. Correct behavior — there's nothing to remove. On a 400-word chunk with mixed content, the LLM would extract the BM25-specific sentences and discard the rest.

4. **Q:** Budget compression keeps the first N words regardless of relevance. What's the failure mode?
   **A:** The relevant content may appear late in the chunk. A 400-word chunk where the answer is in the last 100 words would have the answer budget-compressed away. Budget compression assumes sentence relevance correlates with position, which is often false for technical documents.

5. **Q:** How do you decide which compression strategy to use in production?
   **A:** Similarity as default — fast, accurate, no LLM cost. Budget as fallback when latency is critical and chunk quality is high (answer tends to be near the top). LLM for offline quality auditing where latency doesn't matter. Measure compression ratio on your corpus — if ratio > 0.9, compression isn't helping and adds latency for no benefit.

## Code walkthrough

*"How does your context compressor work?"*

> "Three strategies behind one interface. Similarity: split each chunk into sentences, embed them with the same BGE embedder, score each by cosine similarity to the query, keep top_k. It removes sentences that don't match the query's semantic region — we saw it drop a boundary artifact sentence that scored low against 'What is BM25?' while keeping the actual BM25 content. LLM: ask Qwen2.5-3B to extract only the relevant sentences verbatim — most accurate but costs one Ollama call per chunk, too slow for real-time. Budget: keep sentences until a word count threshold is hit — instant, no model, deterministic. Every compressed chunk carries metadata: original_length, compressed_length, compression_ratio. A 0.63 mean compression ratio means we sent 37% less content to the generator. On 45-word chunks that's modest. On 400-word production chunks, similarity compression saves ~450 tokens per query. At scale, that's real API cost savings."

# Checkpoint 7.3 — Faithfulness Checker

## What we built
- `FaithfulnessChecker` — NLI and LLM strategies
- `nli-MiniLM2-L6-H768` — correct model, 176ms vs 37s LLM strategy
- Word overlap fallback (≥0.85 → score=1.0) handles near-verbatim claims NLI underscores
- `_clean_passage()` — removes boundary artifact sentences before NLI scoring
- Perfect discrimination: faithful answer=1.000, hallucinated answer=0.333

## Core concepts

### 1. Faithfulness ≠ correctness
"BM25 was invented by Robertson in 1994 at Cambridge" is factually correct — and scored 0.00. The checker doesn't know if it's true; it only knows if it's in the retrieved context. This is the right behavior: RAG should produce claims grounded in retrieved sources, not in the model's parametric memory.

### 2. The three-layer NLI stack
```
Claim extracted from answer
        │
        ▼
word_overlap(cleaned_passage, claim) >= 0.85?
        │ YES → score=1.0 (verbatim support)
        │ NO  ↓
        ▼
_clean_passage() strips boundary artifacts
        │
        ▼
NLI model predict(clean_passage, claim)
        │
        ▼
entailment score vs threshold=0.25
```

Each layer catches what the previous misses. Word overlap catches near-verbatim claims that NLI underscores. Cleaning catches boundary artifact noise that confuses NLI. NLI catches semantic paraphrases.

### 3. NLI model selection matters enormously
```
nli-deberta-v3-small:   entailment=0.0013 on clear entailment → useless
nli-MiniLM2-L6-H768:    entailment=0.7958 on clear entailment → production-ready
```

Same architecture class, different training. Model behavior on short technical sentences varies dramatically across NLI models. Always benchmark on your domain before deploying.

### 4. NLI underscores near-verbatim hypotheses
When hypothesis ≈ premise (near-copy), NLI models often output low entailment scores. These models were trained on textual entailment where hypothesis is typically shorter and more abstract than premise. The word overlap fallback (≥0.85 → 1.0) compensates.

### 5. 176ms vs 37s — the NLI advantage
```
LLM strategy: 6 Ollama calls × 3s each = 37s total
NLI strategy: 1 batch call → 176ms total
```
209× faster. Same discrimination quality. NLI is the production default; LLM is for complex multi-sentence claims that NLI can't model.

## Interview flashcards

1. **Q:** What's the difference between faithfulness and correctness in RAG?
   **A:** Faithfulness: every claim in the answer is supported by retrieved context. Correctness: every claim is factually true. A hallucinated but factually true claim is unfaithful. A grounded but factually wrong claim is faithful but incorrect. RAG quality requires faithfulness (grounding in retrieved sources) as the first check; factual correctness is a separate evaluation against ground truth.

2. **Q:** Why does the NLI model score near-verbatim claims poorly?
   **A:** NLI models were trained on datasets where the hypothesis is shorter and more abstract than the premise. When hypothesis ≈ premise (near-copy), the training distribution is violated and the model outputs uncertain scores. The word overlap fallback (≥85% of content words match → automatically supported) compensates for this calibration gap.

3. **Q:** nli-deberta-v3-small gave 0.001 while nli-MiniLM2-L6-H768 gave 0.796 on the same pair. What does this tell you about NLI model selection?
   **A:** NLI model calibration varies dramatically on short technical sentences. Models trained on academic NLI benchmarks (SNLI, MultiNLI) may not transfer to technical domain retrieval evaluation. Always benchmark candidate models on a sample of your actual (passage, claim) pairs before committing. Model size alone doesn't predict calibration quality.

4. **Q:** Your faithfulness checker returned False for "How is dense retrieval different from BM25?" with a correct, grounded answer. How do you handle this in production?
   **A:** Two approaches. (1) Raise the word overlap fallback to 0.90 and run both NLI and word overlap, accepting either signal. (2) Add a second-pass LLM check when NLI says False — LLM confirms or overrides. In production, faithfulness=False triggers human review, so false positives create unnecessary work. Tune the thresholds based on your false positive rate.

5. **Q:** Claim-level faithfulness vs answer-level faithfulness — which do you implement and why?
   **A:** Claim-level. Answer-level is too coarse — one hallucinated sentence in a five-sentence answer marks the whole answer as unfaithful. Claim-level tells you exactly which sentences to flag, redact, or regenerate. The score (e.g., 0.333 = 1 of 3 claims supported) quantifies the degree of hallucination.

## Code walkthrough

*"Walk me through your faithfulness checker and how you made it production-ready."*

> "The checker extracts individual claims from the answer by splitting on sentence boundaries after stripping citation markers. For each claim, it evaluates support against each retrieved chunk using a three-layer approach. First, word overlap: if 85% of content words in the claim appear in the passage, it's automatically supported — this handles near-verbatim claims that NLI underscores paradoxically. Second, `_clean_passage` strips leading boundary artifact sentences that share no content words with the claim — these confused the NLI model in testing. Third, NLI inference with nli-MiniLM2-L6-H768, which we validated scores 0.80 on clear entailment and 0.001 on hallucination. The model selection was non-trivial — nli-deberta-v3-small scored 0.001 on clear entailment, useless for this task. The final latency: 176ms for 2 claims × 3 chunks = 6 NLI calls, vs 37s for the LLM strategy. Production deployment: NLI as default, LLM as override for complex multi-sentence claims the NLI model can't handle."

# Checkpoint 7.4 — Answer Relevance Scorer

## What we built
- `AnswerRelevanceScorer` — reverse question generation + embedding similarity (RAGAS-inspired)
- n_questions=3 for stable mean, n_questions=1 for speed
- Correct gradient: direct answer (0.662) > evasive answer (0.517) > wrong topic (0.427)
- Three verdicts: relevant (≥0.85), partially_relevant (≥0.65), irrelevant (<0.65)

## Core concepts

### 1. Reverse question generation — the RAGAS insight
If an answer truly addresses a question, questions generated from that answer should resemble the original question.

```
Original: "What is BM25 and how does it score documents?"
Answer:   "BM25 is a sparse retrieval algorithm based on TF-IDF..."
Generated: "What type of algorithm is BM25?" / "How does BM25 weight terms?"
Similarity(original, generated) → 0.70 → partially_relevant
```

No labeled data required. The reverse-generation proxy is self-supervised.

### 2. Score gradient reveals the ordering
```
Direct BM25 answer:   0.662  (on-topic sub-questions generated)
Evasive answer:       0.517  (generic retrieval questions generated)
Wrong-topic answer:   0.427  (FAISS questions generated, not BM25)
```

The ordering is correct — direct > evasive > wrong topic — even if absolute scores need calibration.

### 3. Threshold calibration is required
The "relevant" threshold of 0.85 is too strict — a correct, direct answer scored 0.662 (partially_relevant). Generated sub-questions are on-topic but more specific than the original, so embedding similarity naturally caps around 0.65-0.75. Calibrate to your data: run on 100 queries with human labels, find the threshold that minimizes false negatives.

### 4. n_questions controls precision vs speed
```
n=1: 3× faster, higher variance (one noisy question)
n=3: 3× more stable, 3× slower
```
For production real-time scoring: n=1. For offline quality auditing: n=3.

### 5. Answer relevance + faithfulness = complete quality signal
```
Faithful=True  + Relevant=high → trustworthy answer
Faithful=False + Relevant=high → correct but hallucinated → flag for review
Faithful=True  + Relevant=low  → grounded but evasive → regenerate with better context
Faithful=False + Relevant=low  → bad retrieval → fix upstream
```

The 2×2 matrix diagnoses the failure mode, not just the symptom.

## Interview flashcards

1. **Q:** What is the RAGAS approach to answer relevance and why doesn't it require labels?
   **A:** Generate questions from the answer using an LLM, then measure cosine similarity between the original question and each generated question. If the answer addresses the question, generated questions should resemble it. No labeled data: the LLM-generated questions and embedding similarity provide the supervision signal. It's self-supervised evaluation.

2. **Q:** A correct BM25 answer scored 0.662 (partially_relevant) with threshold=0.85. Is the answer bad or the threshold?
   **A:** The threshold. Generated sub-questions from a BM25 answer ("What type of algorithm is BM25?") are on-topic but more specific than the original ("What is BM25 and how does it score documents?"). Embedding similarity between specific sub-questions and the original naturally caps around 0.65-0.75. The threshold 0.85 assumes near-identical questions — too strict for real reverse-generation. Calibrate to 0.60 based on your data.

3. **Q:** Why does the wrong-topic answer (FAISS for faithfulness) score lower than the evasive answer?
   **A:** The evasive answer generates generic retrieval questions that share some embedding space with BM25-related questions. The wrong-topic FAISS answer generates FAISS-specific questions that are completely orthogonal to the faithfulness question. The embedding distance from completely different domains is larger than from tangentially related topics.

4. **Q:** How does answer relevance scoring help you diagnose pipeline failures?
   **A:** The 2×2 faithfulness × relevance matrix diagnoses failures: faithful+relevant = good, faithful+irrelevant = retrieval failed (got context about a different topic), unfaithful+relevant = model hallucinated (knows the answer but added parametric facts), unfaithful+irrelevant = both retrieval and generation failed.

5. **Q:** You use BGE embeddings for relevance scoring. Should it be the same model as retrieval?
   **A:** Yes — consistency matters. If you use BGE for retrieval and E5 for relevance scoring, the embedding spaces differ and similarity scores are incomparable. Using the same model ensures the similarity measurement is in the same geometric space as your retrieval decisions.

## Code walkthrough

*"How does your answer relevance scorer work?"*

> "It's a RAGAS-inspired approach using reverse question generation. Given an answer, I ask Qwen2.5-3B to generate N questions that the answer could be responding to — at temperature=0.3 for diversity. Then I embed the original question and all generated questions using BGE-small, normalize the vectors, and compute cosine similarity between original and each generated question. The mean similarity is the relevance score. The intuition: if the answer truly addresses the question, you should be able to reconstruct a similar question from the answer alone. A direct BM25 answer generates BM25-specific questions — high similarity to 'What is BM25?' An evasive answer generates generic retrieval questions — lower similarity. A wrong-topic FAISS answer generates FAISS questions — near-zero similarity to a faithfulness question. In our benchmark: 0.662 for direct, 0.517 for evasive, 0.427 for wrong topic — correct ordering. The threshold 0.85 for 'relevant' is too strict — calibrate to 0.60 based on your labeled data. Combined with faithfulness checking, the 2×2 matrix diagnoses failure modes: faithful+relevant is trustworthy, faithful+irrelevant means retrieval failed, unfaithful+relevant means hallucination."
