# Checkpoint 4.6 — RAPTOR Index

## What we built
- `RAPTORIndex` — K-Means clustering + LLM summarization + recursive tree
- All nodes (leaves + summaries) indexed in one flat FAISS index
- Direct API summarization call (bypassing RAG prompt builder)
- Empirically verified: specific queries → L0 leaves, thematic queries → L1 summaries
- Tree stats: 8 leaves + 1 summary = 9 total nodes

## Core concepts

### 1. The multi-granularity problem standard RAG can't solve
Standard RAG retrieves at one granularity — the chunk. If a user asks "what is paragraph 3 about?" a chunk answers it. If they ask "what is this document about?" — no chunk answers it. That's a summary-level question.

RAPTOR adds summary nodes above the leaves:
```
Level 0 (leaves): original 8 chunks — specific facts
Level 1 (clusters): 3 summary nodes — cluster themes
Level 2 (root): 1 global summary — document theme
```

All levels are indexed in one flat FAISS index. Retrieval searches all levels simultaneously and returns results from whichever level best matches the query.

### 2. K-Means on embedding space = unsupervised topic detection
K-Means clusters vectors by cosine proximity. Chunks about similar concepts land near each other in embedding space. The cluster boundaries emerge from the semantic structure of the content — no document structure, no headers, no metadata required.

With n_clusters=3 on 8 chunks, RAPTOR might discover:
- Cluster A: retrieval fundamentals (RAG, BM25, dense)
- Cluster B: evaluation and metrics (recall@k, faithfulness, MRR)
- Cluster C: infrastructure (FAISS, Chroma, Qdrant)

These emerge automatically. The LLM then summarizes each cluster into one rich paragraph.

### 3. LLM summaries create semantic compression
The summary of cluster A — "Retrieval-Augmented Generation combines information retrieval with LLM generation. BM25 provides sparse keyword retrieval while dense embeddings capture semantic meaning..." — captures the cluster's theme in one embedding. A thematic query "How does retrieval work?" embeds near this summary, not near any individual chunk.

This is the core mechanism: summaries are semantically richer than individual chunks for thematic queries because they explicitly capture the cluster's theme.

### 4. Direct API summarization bypasses the RAG prompt builder
Our first attempt passed the summarization request through `generator.generate(query, [chunk])` — the RAG prompt builder formatted it as a grounded-answer prompt, so the model answered the instruction instead of summarizing. Fix: call the API directly with a plain summarization prompt:

```
"Summarize the following text passages into one coherent paragraph.
Preserve all key facts and technical details.

{passages}

Summary:"
```

The lesson: the RAG prompt format is designed for Q&A from retrieved context. For summarization, document writing, or any other task, bypass the prompt builder and use a task-appropriate prompt directly.

### 5. Score patterns validate the tree
```
Specific: "What is BM25?"  →  L0 (leaf)    score=0.7094
Thematic:  "How does retrieval work?" → L1 (summary) score=0.8433
```

The summary scores *higher* than leaves on thematic queries because the summary embeds the aggregate theme. This 0.8433 > 0.7094 comparison is the quantitative proof that RAPTOR's multi-level structure works.

### 6. RAPTOR in production — the real costs
- **Summarization API calls:** O(n_clusters × max_levels) LLM calls at index time. For 1000 clusters across 2 levels, that's 1000+ calls — a real cost and latency concern.
- **Index rebuild on corpus update:** adding new chunks may shift cluster assignments, requiring a full RAPTOR rebuild.
- **Summary quality:** the summaries are only as good as the LLM. A model that produces generic summaries creates generic embeddings that match too broadly.

RAPTOR is most valuable for: large corpora (>100K chunks), multi-level documents (books, reports, codebases), and applications where thematic queries are common (executive Q&A, document exploration).

## Interview flashcards

1. **Q:** What problem does RAPTOR solve that standard RAG can't?
   **A:** Multi-granularity retrieval. Standard RAG retrieves at one level — the chunk. Thematic queries ("what is this document about?") can't be answered by any individual chunk; they need a summary-level representation. RAPTOR builds summary nodes above the leaves via LLM summarization of clusters. Specific queries match leaves; thematic queries match summaries.

2. **Q:** How does RAPTOR use K-Means clustering?
   **A:** K-Means clusters chunks by cosine proximity in embedding space — semantically similar chunks land in the same cluster without any structural guidance. The cluster membership emerges from the content's semantic structure. Each cluster is then summarized by an LLM to create a summary node one level above the leaves.

3. **Q:** Why did your first RAPTOR summarization return the model's meta-commentary instead of a summary?
   **A:** The RAG prompt builder formats inputs as grounded Q&A — "Answer using ONLY the provided context." When we passed the summarization request through this format, the model answered the Q&A instruction rather than summarizing. Fix: call the API directly with a plain summarization prompt that doesn't have the RAG scaffolding.

4. **Q:** Thematic queries scored higher on summary nodes (0.84) than specific queries on leaf nodes (0.71). Why?
   **A:** Summary nodes embed the aggregate theme of a cluster — the summary of "BM25 + dense retrieval + hybrid" explicitly captures the retrieval theme. A thematic query embeds near that theme. Individual leaf chunks embed specific details; thematic queries are farther from any single detail but close to the aggregate. The summary's embedding is semantically richer for theme-level queries.

5. **Q:** When would you not use RAPTOR?
   **A:** When summarization API cost is prohibitive, when the corpus is small (few chunks don't need cluster summarization), when all queries are specific factoid queries (no benefit from summary nodes), or when corpus updates are frequent (each update may require full RAPTOR rebuild). RAPTOR pays off on large stable corpora with mixed specific/thematic query patterns.

# Checkpoint 4.7 — Index Benchmark + Hybrid RRF

## What we built
- `HybridRetriever` — RRF from scratch, configurable k, per-leg weights, fetch_k
- A 4-way benchmark: BM25, Dense (FAISS), Hybrid (RRF), RAPTOR
- Per-query diagnostic showing exactly which query each method misses
- Honest interpretation: all tied at 0.900 — documented why and what conditions would show divergence

## Benchmark result

| Rank | Index | recall@1 | recall@3 | MRR |
|------|-------|----------|----------|-----|
| 1 (tie) | BM25 (sparse) | 0.900 | 1.000 | 0.950 |
| 1 (tie) | Dense (FAISS) | 0.900 | 1.000 | 0.950 |
| 1 (tie) | Hybrid (RRF) | 0.900 | 1.000 | 0.950 |
| 1 (tie) | RAPTOR | 0.900 | 1.000 | 0.950 |

**The one miss:** "How is dense retrieval different from BM25?" → all methods fail at rank 1. Chunk boundary artifact — the correct chunk starts mid-sentence due to recursive chunking overlap.

## Core concepts

### 1. Reciprocal Rank Fusion — scale-agnostic list merging
BM25 scores are ~4.5, 3.2, 2.1. Cosine scores are ~0.71, 0.53, 0.47. Different scales — you can't add them directly.

RRF uses only the rank, not the score:
```
RRF(chunk) = 1/(k + rank_bm25) + 1/(k + rank_dense)
```

Where k=60 (from the original Cormack et al. paper) dampens the impact of very high ranks. A document ranked #1 in both lists: `1/61 + 1/61 = 0.033`. Ranked #1 in BM25 but absent from dense: `1/61 = 0.016`. The document present in both lists always wins over one present in only one.

**Why k=60:** the constant prevents a rank-1 item from dominating too strongly. Without it, a rank-1 item would score 1/1 + 0 = 1.0, which would dominate regardless of how everything else ranked. k=60 is the empirically-validated value from the original paper.

### 2. When hybrid wins — and when it doesn't
**Hybrid wins when:** BM25 hits what dense misses (exact keyword, rare entity, acronym) AND dense hits what BM25 misses (paraphrase, synonym, rephrasing). These are the divergent failure modes.

**Hybrid doesn't win when:** both legs fail on the same query (same chunk boundary artifact, same missing content). RRF cannot rescue a query that both legs miss — the fused score is simply the sum of two zeros.

On our corpus: the one miss is a chunk boundary artifact that equally hurts keyword and semantic matching. Both see the same partial chunk content, both rank it lower than ideal. RRF has no new information to contribute.

### 3. Hybrid advantage requires diverse query types
Literature shows hybrid outperforms either alone by 5-15% on BEIR benchmark (diverse 18-dataset benchmark). The key: BEIR includes keyword queries (entity search, exact match) AND semantic queries (paraphrase, inference). On that diversity, divergent failure modes appear reliably.

On a corpus of 8 clean technical chunks with 10 straightforward queries, the diversity isn't there to reveal the divergence.

### 4. Per-query diagnostic is more valuable than aggregate metrics
Aggregate recall@1=0.900 tells you "one query is failing." The per-query table tells you exactly which one and that all methods fail identically. That's immediately actionable: the fix is upstream (chunking strategy, corpus quality) not in the retrieval method.

This is the mature engineering posture: aggregate metrics for tracking, per-query diagnostics for debugging.

### 5. The benchmark infrastructure is the asset, not the result
The specific result (all tied at 0.900) will change when:
- The corpus grows to 100K+ chunks
- The gold set includes paraphrase queries (dense wins) AND exact-match queries (BM25 wins)
- Documents vary in length (BM25's length normalization matters)

What transfers: the benchmark script, the RRF implementation, the per-query diagnostic. These are reusable across any corpus. The infrastructure was built in ~100 lines. Running it on a new corpus takes 5 minutes.

## Interview flashcards

1. **Q:** What is Reciprocal Rank Fusion and why is it better than score normalization?
   **A:** RRF merges ranked lists using rank positions rather than raw scores: `RRF(doc) = 1/(k + rank_list1) + 1/(k + rank_list2)`. Score normalization requires knowing the min/max of each list — one outlier shifts the whole scale. RRF is robust to score distribution shape: it only needs to know where each document ranked, not how highly it scored. The k=60 constant from the original paper prevents rank-1 items from dominating.

2. **Q:** BM25 and dense retrieval both failed on the same query. Why didn't hybrid help?
   **A:** Hybrid's advantage requires divergent failure modes — BM25 hitting what dense misses, and vice versa. When both legs fail on the same query (chunk boundary artifact in our case), RRF fuses two zero scores and returns zero. Hybrid cannot create signal from two sources of absence.

3. **Q:** Your benchmark shows all four indexes tied at 0.900. How do you interpret this result?
   **A:** The corpus (8 chunks) and gold set (10 specific factoid queries) are too uniform to reveal retrieval method differences. All methods fail on the same one query for the same reason. The benchmark infrastructure is correct; the test conditions don't exercise the cases where methods diverge. On a larger corpus with diverse query types, I'd expect: hybrid to beat either alone by 5-15%, RAPTOR to improve thematic query recall, and BM25 to outperform dense on exact-entity queries.

4. **Q:** What query types would show hybrid beating dense-only?
   **A:** Exact entity queries ("error code 0x80070005", "ISO-8601 date format", "RFC 2616") where BM25's exact token match wins. Mixed with semantic queries where dense wins. On a corpus with both types, BM25 and dense fail on complementary subsets, and RRF captures the union of their wins.

5. **Q:** How would you extend the HybridRetriever to support three legs (BM25 + dense + sparse learned)?
   **A:** Add a third index to the constructor, add a third weight parameter, and add a third RRF accumulation pass. The formula extends naturally: `RRF(doc) = w1/(k + rank1) + w2/(k + rank2) + w3/(k + rank3)`. The weights allow asymmetric emphasis: boosting the sparse leg for entity-heavy queries, boosting dense for semantic queries.

6. **Q:** The per-query diagnostic showed all methods failing on "How is dense retrieval different from BM25?" Diagnose the root cause.
   **A:** Chunk boundary artifact. The recursive chunker created a chunk starting mid-sentence (with overlap text from the previous chunk) that contains the answer but is harder to match because the most discriminative tokens ("dense retrieval", "BM25") appear after the overlap region. Fix options: adjust chunk_overlap, use a larger chunk_size to keep the full paragraph, or use MetadataAwareChunker with heading-level awareness.
