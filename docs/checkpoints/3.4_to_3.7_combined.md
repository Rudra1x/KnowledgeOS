# Checkpoint 3.4 — APIEmbedder

## What we built
- `APIEmbedder` — OpenAI-compatible `/v1/embeddings` client
- Batch chunking (100 texts per call — respects rate limits)
- Index-sorted result assembly (API returns results in arbitrary order)
- Dimension inference from first call
- Matryoshka dimension truncation support
- Graceful `RuntimeError` with actionable message when key is missing

## Core concepts

### 1. The OpenAI-compatible embedding API spec
Most embedding providers expose the same endpoint format:
```
POST /v1/embeddings
{
  "model": "text-embedding-3-small",
  "input": ["text1", "text2", ...],
  "dimensions": 256   // optional, for Matryoshka models
}
```
Response:
```json
{
  "data": [
    {"index": 0, "embedding": [...]},
    {"index": 1, "embedding": [...]}
  ]
}
```

Our `APIEmbedder` works with OpenAI, Voyage, Cohere (slightly different schema), and local vLLM/Ollama servers by changing `base_url` alone.

### 2. Sort by index — the non-obvious requirement
The API specification says results may be returned in any order. Embeddings in a batch may be processed out of order and returned as they complete. If you assemble the output matrix without sorting by `index`, embedding[0] may correspond to text[3]. Every downstream operation — FAISS indexing, chunk linkage — would be silently wrong.

```python
items = sorted(data["data"], key=lambda x: x["index"])
```
This one line is mandatory and non-obvious. It's the kind of thing that works 99% of the time (because small batches happen to return in order) and fails catastrophically at scale (when large batches return out of order).

### 3. Matryoshka Representation Learning
OpenAI's text-embedding-3-small supports a `dimensions` parameter — you can request 256, 512, or 1536-dim embeddings from the same model. The first N dimensions of the full 1536-dim vector are independently useful (nested representation). This is Matryoshka Representation Learning (Kusupati et al., 2022).

Practical implication: you can choose quality/cost/storage operating points from one model:
- 256-dim: 6x cheaper storage, 6x faster search, moderate quality loss (~5%)
- 512-dim: 3x cheaper, 3x faster, small quality loss (~2%)
- 1536-dim: full quality, full cost

### 4. API vs local — the cost breakeven
At $0.02/1M tokens (text-embedding-3-small):
- 100K chunks × 400 chars/chunk × 0.75 tokens/char = 30M tokens
- Cost: $0.60 per full corpus embed

At 20ms/chunk (BGE-small local):
- 100K chunks × 20ms = 33 minutes

API wins for: prototypes, low volume (<100K chunks/day), no GPU, need best model immediately.
Local wins for: sustained high volume (>100K chunks/day), cost-sensitive, latency-sensitive, offline.

### 5. Dimension inference at init
Different models have different dimensions (1536 for text-embedding-3-small, 3072 for text-embedding-3-large, 1024 for Voyage-3). Rather than hardcoding, we call the API once with a dummy text at init and read the dimension from the response. This makes `APIEmbedder` work correctly with any OpenAI-compatible model without configuration.

## Interview flashcards

1. **Q:** Why sort API embedding results by index?
   **A:** The OpenAI embedding API spec allows results to be returned in any order — batches may process items concurrently. Without sorting by `index`, your embedding matrix may be permuted: embedding[0] corresponds to text[3], etc. Every downstream FAISS operation would silently use wrong vectors. The fix is one line: `sorted(data["data"], key=lambda x: x["index"])`.

2. **Q:** What is Matryoshka Representation Learning?
   **A:** A training technique that makes the first N dimensions of an embedding independently useful, for any N up to the full dimension. text-embedding-3-small produces 1536-dim vectors where the first 256 dims are already a good embedding. You can request 256-dim and get 6x storage/speed savings at ~5% quality cost. Named after Russian nested dolls — smaller representations are nested inside larger ones.

3. **Q:** When would you switch from APIEmbedder to BGEEmbedder?
   **A:** When sustained volume makes API cost significant. At $0.02/1M tokens, 1M chunks/day costs ~$6/day. BGE-small on a GPU costs ~$0.10/hour (AWS g4dn.xlarge), handles ~500 chunks/sec = 43M chunks/hour. The breakeven is roughly 300K chunks/day. Below that: API. Above that: local.

4. **Q:** How does your APIEmbedder handle rate limiting?
   **A:** Currently it doesn't — it relies on the `batch_size=100` default to stay within typical rate limits, and `requests` will raise an HTTPError on 429 responses. Production upgrade: wrap `_call_api()` in a retry loop with exponential backoff and jitter. The `tenacity` library handles this in 5 lines. Rate limit handling belongs in the transport layer, not the business logic.

5. **Q:** How would you switch from OpenAI to Voyage embeddings?
   **A:** Change two lines in `configs/default.yaml`:
   ```yaml
   base_url: "https://api.voyageai.com/v1"
   model:    "voyage-3"
   ```
   And set `VOYAGE_API_KEY` in `.env`. The `APIEmbedder` code changes nothing. That's the whole point of the interface layer.

# Checkpoint 3.5 — CachedEmbedder

## What we built
- `CachedEmbedder` — transparent wrapper around any `Embedder`
- L1 (memory dict): 788x speedup, process-scoped, LRU eviction
- L2 (SQLite): 2.6x speedup, persistent across restarts
- Write-through: L2 hit populates L1 for subsequent calls
- Batch-aware miss identification: only embeds uncached texts
- `stats()` and `clear()` for observability and maintenance
- Correctness verified: identical vectors from cache vs recomputation (diff=0.00e+00)

## Core concepts

### 1. Content-addressed caching
Cache key = SHA-256(model_name + "::" + text). Not time-based — content-based. If the text changes, the key changes and a new embedding is computed. If the text is identical, the cached embedding is correct forever (for the same model). This is fundamentally different from a TTL cache — there's no expiry, because embeddings are deterministic.

Including `model_name` in the key is mandatory: the same text produces different vectors with different models. A BGE-small vector returned for an E5 query would silently corrupt retrieval.

### 2. Two-tier rationale
| Tier | Speed | Scope | Use case |
|------|-------|-------|----------|
| L1 (memory) | 788x | Process | Repeated queries, hot documents |
| L2 (SQLite) | 2.6x | Persistent | Corpus re-indexing, daily updates |

L1 survives only within a process. L2 survives process restarts. The combination covers both hot-path performance and incremental ingestion economics.

### 3. Write-through from L2 to L1
When a vector is found in L2 (SQLite), it's immediately written to L1 (memory) before returning. This means:
- First request after restart: L2 hit (2.6x speedup)
- All subsequent requests for the same text: L1 hit (788x speedup)

Without this write-through, every request after restart would be an L2 hit regardless of how many times that text had been seen before.

### 4. Batch miss identification
```python
for i, (key, text) in enumerate(zip(keys, texts)):
    vec = self._l1_get(key)
    if vec is None:
        vec = self._l2_get(key)
        if vec is not None:
            self._l1_set(key, vec)
    if vec is not None:
        result[i] = vec
    else:
        misses.append((i, key, text))

# Only embed the true misses
if misses:
    new_vecs = embedder.embed([m[2] for m in misses])
```

On a corpus update where 90% of documents are unchanged, only 10% of texts hit the embedder. The 90% are served from cache in milliseconds. This is the economic justification: 90% reduction in embedding calls = 90% reduction in API cost or compute time.

### 5. The numpy bool() bug — and the general lesson
```python
# Wrong — numpy arrays raise ValueError on bool()
vec = self._l1_get(key) or self._l2_get(key)

# Right — explicit None check
vec = self._l1_get(key)
if vec is None:
    vec = self._l2_get(key)
```

Python's `or` operator calls `bool()` on the left operand. For numpy arrays, `bool()` raises `ValueError: The truth value of an array with more than one element is ambiguous`. The fix is always an explicit `is None` check. This bug appears wherever numpy arrays are used with Python's boolean operators (`and`, `or`, `not`). Knowing this in advance saves hours of debugging.

## Interview flashcards

1. **Q:** Why is `model_name` part of the cache key?
   **A:** The same text produces different vectors with different models — BGE-small 384-dim vs E5-small 384-dim vectors are not interchangeable. Without model_name in the key, a BGE embedding might be returned for an E5 query, silently corrupting retrieval. Content-addressed caches must include every dimension that affects the output.

2. **Q:** Why does your cache use SQLite instead of Redis?
   **A:** SQLite is zero-dependency — it's in Python's stdlib. Redis requires a running server, a client library, and network connectivity. For a single-process learning project, SQLite is the right choice. For multi-worker production, SQLite's single-writer lock becomes a bottleneck — that's when you upgrade to Redis or Memcached.

3. **Q:** A corpus update changes 10% of documents. How does the cache help?
   **A:** Only the 10% changed documents produce cache misses and hit the embedder. The 90% unchanged documents are served from L2 (SQLite, 2.6x speedup) or L1 (memory, 788x speedup) without any model calls. On a 100K-document corpus updated daily, you embed 10K documents instead of 100K — 90% cost reduction.

4. **Q:** What's the numpy `or` bug and how did you fix it?
   **A:** Python's `or` calls `bool()` on its left operand. Numpy raises `ValueError: The truth value of an array with more than one element is ambiguous` because it's unclear whether a multi-element array is "truthy." The fix is explicit None checks: `if vec is None: vec = fallback`. This applies to any Python boolean operator (`and`, `or`, `not`) used with numpy arrays.

5. **Q:** How would you extend this cache to work across multiple workers?
   **A:** Replace SQLite with Redis or Memcached for L2. SQLite's single-writer model serializes concurrent writes and can deadlock under high write load. Redis supports atomic SET operations and is designed for shared-memory use. The `CachedEmbedder` interface stays identical — swap the `_l2_get` and `_l2_set` implementations.

# Checkpoint 3.6 — BatchEmbedder + Normalization Utilities

## What we built
- `normalize_vectors()` — L2 normalization with zero-vector safety
- `verify_normalization()` — returns `max_dev` and `n_outliers` before indexing
- `BatchEmbedder` — chunked processing with progress, normalization verification, skip-on-error
- Demonstrated: un-normalized vectors have max_dev=19.76 — silently wrong FAISS scores without correction

## Core concepts

### 1. Un-normalized vectors silently corrupt retrieval
FAISS `IndexFlatIP` computes raw dot products. For unit-normalized vectors, `dot(a, b) = cos(a, b)`. For un-normalized vectors, `dot(a, b) = |a||b|cos(a, b)`. A vector with norm=20 will dominate every similarity comparison regardless of semantic content — the top retrieval results become "longest vectors," not "most semantically similar."

In our test: un-normalized vectors had max_dev=19.76 (norms ranged from ~0.2 to ~20.7). This is catastrophic for retrieval. After normalization: max_dev=5.96e-08 (machine precision).

### 2. Verify, don't assume
All our current embedders normalize. But:
- A future embedder might not
- A raw HuggingFace model used directly won't normalize
- Float64→float32 conversion shifts norms slightly
- Cached vectors from a different code path may skip normalization

`verify_normalization()` is a 2-line audit before indexing that catches any of these:
```python
check = verify_normalization(vectors)
if not check["normalized"]:
    vectors = normalize_vectors(vectors)
```

This pattern — verify before use, correct if needed — is defensive programming applied to numerical correctness.

### 3. Batch size as a memory dial
At batch_size=64 with BGE-small:
- 64 texts × 400 chars × 4 bytes/float × 384 dims ≈ 40MB peak memory

At batch_size=1024:
- 1024 texts × ... ≈ 640MB peak memory

Batch size controls the throughput/memory trade-off. On a 32GB server, batch_size=1024 is fine. On a 4GB instance, batch_size=64 is safer. The parameter belongs in config — not hardcoded.

### 4. skip_on_error — a production posture choice
Two legitimate patterns:
- `skip_on_error=True`: nightly batch jobs, large corpora. One malformed document shouldn't abort 6 hours of ingestion. Log the failure, flag for review, continue.
- `skip_on_error=False`: interactive ingestion, small corpora. Fail fast. Fix the input. Don't silently miss documents.

Neither is universally correct. The configuration parameter makes the posture explicit rather than hiding it in error-handling code.

### 5. Throughput as a first-class metric
29 chunks/sec on BGE-small CPU. What this means:
- 100K corpus: 57 minutes (acceptable for nightly batch)
- 1M corpus: 9.5 hours (borderline — consider GPU or API)
- 10M corpus: 4 days (definitely need GPU or distributed API)

Knowing your throughput number before production is the difference between "ingestion takes 3 hours" being a plan vs a surprise.

## Interview flashcards

1. **Q:** A colleague says "all our embedders normalize, so we don't need verify_normalization()." What's your response?
   **A:** That's true today. Tomorrow someone adds a raw HuggingFace model, or float64→float32 conversion introduces small deviations, or a cached vector from a different code path skips normalization. `verify_normalization()` is a 2-line guard before indexing — the cost is negligible, the protection is real. The mantra is "verify, don't assume" for numerical correctness.

2. **Q:** Un-normalized vectors have max_dev=19.76. What does retrieval look like?
   **A:** Terrible. FAISS computes raw dot products. A vector with norm=20 scores `20 × cos(θ)` while a unit vector scores `1.0 × cos(θ)`. The norm-20 vector wins every similarity comparison regardless of semantic content. Top retrieval results are the "biggest" vectors, not the most relevant ones. This is completely silent — no error, no warning, just wrong rankings.

3. **Q:** Why is there a `skip_on_error` parameter on BatchEmbedder?
   **A:** It makes the error posture explicit and configurable. For nightly ingestion of 1M documents, one malformed document shouldn't abort the entire run — use `skip_on_error=True`. For interactive ingestion of a 1K corpus, fail fast and fix the input — use `skip_on_error=False`. Both are legitimate production postures depending on context.

4. **Q:** How do you handle zero vectors in normalize_vectors()?
   **A:** Divide by 1.0 instead of 0.0 — the zero vector stays zero rather than producing NaN. `norms = np.where(norms < eps, 1.0, norms)`. A zero embedding vector would never match any query anyway (zero dot product everywhere), so preserving it as zero is correct and safe.

5. **Q:** Your throughput is 29 chunks/sec. A client needs to ingest 100M documents. What do you recommend?
   **A:** 100M documents / 29 chunks/sec = ~40 days on CPU. Options: GPU (500+ chunks/sec on a V100), API embedding (100+ chunks/sec with batching), or distributed processing across multiple GPU instances. For 100M docs, I'd recommend API embedding (OpenAI text-embedding-3-small at $0.02/1M tokens = ~$2,000 total, done in hours) for the initial load, then switch to local BGE for ongoing updates.

# Checkpoint 3.7 — Embedding Benchmark

## What we built
- Complete head-to-head embedding benchmark: 3 backends, same corpus, same gold set
- Quality (recall@1, MRR), latency (ms/chunk), cost model (hours + GB for 1M chunks)
- Auto-appended RESULTS.md entry
- `copy.deepcopy(chunks)` — critical for fair benchmarks

## Benchmark results

| Rank | Embedder | dim | recall@1 | recall@3 | MRR | ms/chunk |
|------|----------|-----|----------|----------|-----|----------|
| 1 | e5-small | 384 | 1.000 | 1.000 | 1.000 | 64.1 |
| 2 | instr-bge-b | 768 | 1.000 | 1.000 | 1.000 | 183.6 |
| 3 | bge-small | 384 | 0.900 | 1.000 | 0.950 | 20.0 |

**Cost model (1M chunks):**
- bge-small: 5.6h, 1.5GB
- e5-small: 17.8h, 1.5GB
- instr-bge-b: 51.0h, 3.1GB

## Core concepts

### 1. The key finding: E5 closes BGE's gap at 3x cost
BGE-small's one recall failure was the persistent "What is hybrid retrieval?" miss. E5's dual-prefix training closed it. The cost: 3.2x more compute for the same dimension and similar quality elsewhere. On a corpus where that one recall failure matters, E5 is worth it. On a latency-sensitive deployment, BGE-small is defensible.

### 2. InstructionBGEb doesn't justify its cost on in-distribution corpora
InstructionBGEb (768-dim) tied E5 at perfect recall but at 9.2x the compute of BGE-small and 2x the index size. The instruction prefix helps most on out-of-distribution corpora — domain-specific content the base model hasn't seen much of. On a clean English technical corpus (in-distribution for all three models), instruction tuning adds noise, not signal.

### 3. Dimension doesn't predict quality on in-distribution content
E5-small (384-dim) = InstructionBGEb (768-dim) = 1.000 recall. The 2x dimension didn't buy any quality. Dimension matters when:
- The semantic space is genuinely complex (highly multilingual, highly technical)
- The corpus is out-of-distribution for the base model
- The query-document relationship requires fine-grained discrimination

For most English technical content, 384 dims is more than sufficient.

### 4. deepcopy is mandatory for fair benchmarks
Without `copy.deepcopy(chunks)`:
- Embedder 1 sets chunk.embedding = bge_vector
- Embedder 2 finds chunk.embedding already set, may skip embedding
- FAISS for embedder 2 indexes bge_vectors with e5 queries = silent mismatch = garbage results

This is a real benchmark validity bug that produces confidently wrong numbers. The fix is explicit: deep-copy the chunks before each embedder run.

### 5. The benchmark is more valuable than the result
On this 2478-char, 10-paragraph corpus, E5 wins. On a 10GB legal corpus with long documents and specialized vocabulary, the winner changes. The benchmark infrastructure — same corpus, same gold set, same eval harness, auto-RESULTS.md — is what transfers. The specific winner doesn't.

## Interview flashcards

1. **Q:** E5 and InstructionBGEb tied at recall@1=1.000. Which would you deploy?
   **A:** E5-small. Same quality, 2.9x faster, same index size (384-dim vs 768-dim). InstructionBGEb's advantage is domain specificity — custom instructions help on out-of-distribution corpora. On this in-distribution technical corpus, the advantage is zero and the cost is real.

2. **Q:** BGE-small has one recall failure that E5 closes. Is the 3x compute worth it?
   **A:** Depends on the use case. If that query type is 10% of user traffic, 0.1 × 3x compute premium = 0.3x effective premium. If it's 1% of traffic, 0.01 × 3x = 0.03x effective premium — probably worth it. The business logic matters: what's the cost of a missed retrieval in your application vs the cost of extra compute?

3. **Q:** Why did you deepcopy chunks before each embedder run?
   **A:** Without deepcopy, the first embedder sets `chunk.embedding = bge_vector`. The second embedder sees the embedding already set and may skip re-embedding. The FAISS index for the second embedder would store BGE vectors while the retriever uses E5 for queries — a silent vector space mismatch that produces garbage rankings with no error. Deepcopy guarantees each run starts from scratch.

4. **Q:** How would you extend this benchmark to 10 embedders?
   **A:** Add the embedder to the `EMBEDDERS` list with its name and instance. The benchmark loop handles the rest — same corpus, same chunking, same eval, same RESULTS.md update. The infrastructure cost of adding an embedder is one line. That's the whole point of the `NAME` + `last_embed_ms` contract.

5. **Q:** The benchmark shows bge-small takes 5.6h for 1M chunks. A client needs to re-embed daily. What's your recommendation?
   **A:** Three options. If daily re-embedding is a full corpus rebuild: too slow — use the embedding cache (90% cached = 0.56h for 10% updates). If it's incremental updates of 10K chunks/day: 33 minutes, acceptable. If fresh corpus daily is unavoidable: use API embedding (parallel batch calls, 100+ chunks/sec). The cache is almost always the right first answer.
