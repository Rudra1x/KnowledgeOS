# Checkpoint 2.6 — MetadataAwareChunker

## What we built
- `MetadataAwareChunker` — structure-preserving chunker that reads Document metadata
- Three behaviors: split (text, heading-sized), atomic (table — never split), passthrough (ocr_needed)
- Heading-level size map: H1=1200, H2=600, H3=300 (configurable)
- `split_reason` in metadata — visible, self-documenting decisions
- Verified: tables emit 1 chunk (atomic_table), OCR pages emit 1 chunk (passthrough), H1 gets 4x the target of H3

## Core concepts

### 1. The payoff for M1's structured extraction
Every loader in M1 worked to preserve structure:
- DOCX: `heading_level`, `section_title`, `content_type`
- PDF: `content_type: "text"` vs `"table"` vs `"ocr_needed"`
- MD: `heading_level`, `section_title`
- Email: `content_type: "email"`

Without MetadataAwareChunker, all of that structure is thrown away — every Document is just a string to slice. MetadataAwareChunker is the bridge that turns M1's structural extraction into chunking intelligence.

### 2. Atomic content types — never split
```python
ATOMIC_TYPES = {"table"}
```

A Markdown table:
```
| model | recall@1 | latency |
| BGE   | 0.82     | 12ms    |
| E5    | 0.85     | 18ms    |
```

Split mid-table, a chunk might get:
```
| BGE   | 0.82     | 12ms    |
```

With no headers. The numbers are meaningless without the column names. The embedding of a headerless table fragment is semantically different from the embedding of the full table.

**Tables are atomic — they get one chunk, always, regardless of size.** If a table is very large, the alternative is summarization (M7), not splitting.

### 3. Passthrough — preserve, don't drop
```python
PASSTHROUGH_TYPES = {"ocr_needed", "attachment_needs_processing"}
```

`"[Image-only page — OCR required for content extraction]"` is not content — but it shouldn't disappear. A user searching for "what's on page 7" should find something that tells them "this page exists but needs OCR." Silently dropping unsupported content is the wrong engineering choice.

Passthrough emits the sentinel text as-is. The user discovers the gap and can address it (add OCR, skip the page, mark as known gap).

### 4. Heading-level size map — author's hierarchy as context budget
```python
heading_size_map = {
    0: base * 2,   # preamble — no heading, keep wide
    1: base * 2,   # H1 — top-level concept, widest context
    2: base,       # H2 — standard section
    3: base // 2,  # H3 — subsection, tighter
    4: base // 2,
}
```

H1 sections introduce top-level concepts — wider context helps the LLM answer high-level questions. H3 subsections cover specific details — tighter chunks give more precise retrieval.

This uses the author's own document hierarchy as a proxy for "how much context does this content need?" It's free, model-independent, and almost always directionally correct.

### 5. `split_reason` metadata
```python
"split_reason": "atomic_table"   # never split this
"split_reason": "passthrough"    # no-op, emit as-is
"split_reason": "split"          # normal recursive splitting
```

When debugging: "why is this 500-char chunk not being split?" → `split_reason: "atomic_table"`. The decision is self-documenting. Without it, you'd have to inspect content_type and re-trace the logic.

### 6. Graceful fallback
If a Document has no `content_type` or `heading_level` metadata (e.g., loaded by TXTLoader which doesn't set them), the chunker defaults to `content_type="text"` and `heading_level=2` — standard recursive splitting at base_chunk_size. No crash, no special case required.

## Why the design choices
- **`ATOMIC_TYPES` and `PASSTHROUGH_TYPES` as class constants**: configurable per-subclass, clear separation of behaviors
- **`heading_size_map` as constructor parameter**: default is sensible, but real corpora may need different ratios — expose as override
- **Same recursive split/merge/overlap as other chunkers**: code reuse, consistent behavior at text boundaries
- **`split_reason` not `split_type`**: "why was this decision made" is more actionable than "what type is this"

## Interview flashcards

1. **Q:** Why is MetadataAwareChunker the "payoff" for M1?
   **A:** M1's loaders spent significant effort preserving structure — heading levels, content types, table boundaries. Every other chunker in M2 ignores that structure entirely. MetadataAwareChunker is the first one that reads it and makes chunking decisions based on it. M1's metadata investment pays off here.

2. **Q:** Why are tables atomic — never split?
   **A:** Splitting a table mid-row produces fragments without column headers. The embedding of a headerless row is semantically divorced from its meaning. A query about data in the table can't match a fragment that lost its context. Tables are atomic units that must be retrieved whole.

3. **Q:** What's the difference between passthrough and dropping unsupported content?
   **A:** Passthrough preserves the sentinel text in the index — "this page exists but needs OCR." A user searching for content on that page gets a result that explains the gap. Dropping means no result, no explanation. Transparent gaps are better than silent gaps — the user can decide what to do about them.

4. **Q:** How does heading level drive chunk size?
   **A:** A heading-level size map translates H1-H3 to target chunk sizes (H1=largest, H3=smallest). This uses the author's own document hierarchy as a proxy for content importance and context need. H1 sections introduce broad concepts; wide chunks preserve context. H3 subsections cover specific details; tight chunks give precise retrieval.

5. **Q:** A Document loaded by TXTLoader has no content_type or heading_level. What does MetadataAwareChunker do?
   **A:** Graceful fallback. `content_type` defaults to `"text"` (normal splitting), `heading_level` defaults to `2` (base_chunk_size). No crash, no special case. The chunker is designed to degrade gracefully when metadata isn't present.

6. **Q:** When would you use MetadataAwareChunker over RecursiveChunker?
   **A:** Any structured document corpus — DOCX reports, Markdown documentation, PDFs with tables. When your loaders have put structure in Document metadata, MetadataAwareChunker harvests it. On plain text with no structure metadata, it's equivalent to RecursiveChunker.

## Code walkthrough prompt

*"How does your metadata-aware chunker use the structure from M1's loaders?"*

> "It reads two fields from every Document's metadata: `content_type` and `heading_level`. Content type drives the splitting decision first. Tables — tagged `content_type: 'table'` by the PDF and DOCX loaders — are treated as atomic: emit one chunk, never split, always. Splitting a table mid-row loses column header context and makes the embedding meaningless. Documents tagged `content_type: 'ocr_needed'` are passthrough — emit as-is, so gaps are transparent rather than silent. For text content, heading level determines the target chunk size: H1 sections get 2x the base size for wide context, H3 subsections get half for tight retrieval. The split itself uses the same recursive boundary-respecting algorithm as RecursiveChunker, just with a heading-appropriate target. Every chunk carries a `split_reason` field — `atomic_table`, `passthrough`, or `split` — so debugging is self-documenting. When a Document has no metadata (TXTLoader, for example), everything defaults gracefully: `content_type=text`, `heading_level=2`, standard recursive split."
