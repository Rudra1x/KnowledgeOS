# Checkpoint 0.4 — BGE Embedder & FAISS Flat Index

## What we built
- `embedders/bge_embedder.py` — text → 384-dim normalized vectors using BAAI/bge-small-en-v1.5
- `indexes/faiss_index.py` — FAISS flat index with tenant-scoped search
- First working semantic search: a natural language query found the most relevant chunk with cosine similarity 0.8761

## Core concepts

### 1. Embeddings — text as geometry
An embedding model maps text into a fixed-dimensional vector space where **semantically similar texts land close together**. "The cat sat on the mat" and "A feline rested on the rug" are far in edit-distance but close in embedding space.

The key property is **compositional semantics**: the model has learned that meaning is a function of context, not surface tokens. That's what makes RAG work when the query and the document don't share literal words.

### 2. Bi-encoders vs cross-encoders
- **Bi-encoder** (what BGE is): query and document are embedded *independently*. Fast at query time (only embed the query, compare against pre-computed doc vectors). This is the workhorse of retrieval.
- **Cross-encoder** (M6): query and document are fed *together* into a transformer that outputs one relevance score. Much more accurate, but O(N) transformer calls per query — too expensive for the whole corpus. Used for reranking a small candidate set.

Retrieval = bi-encoder. Reranking = cross-encoder. This split is why modern RAG has two stages.

### 3. Asymmetric retrieval — the query prefix trick
BGE was trained with **asymmetric objectives**: queries and passages play different linguistic roles. To capture this, BGE expects a prefix on queries only:

"Represent this sentence for searching relevant passages: {query}"

Passages get no prefix. Skipping this prefix measurably hurts recall (5–15% in published benchmarks). Our `embed_query()` method handles it automatically.

Not all embedders are asymmetric — sentence-transformers' MiniLM family doesn't need prefixes. Instructor and E5 do. This is model-specific knowledge you need when swapping backends.

### 4. Normalization + inner product = cosine similarity
Cosine similarity between vectors `a` and `b` is `(a·b) / (||a|| ||b||)`. If both vectors are pre-normalized to unit length, `||a|| = ||b|| = 1`, so cosine reduces to just the dot product `a·b`.

We tell BGE to normalize embeddings (`normalize_embeddings=True`) and use FAISS's `IndexFlatIP` (Inner Product). This gives cosine similarity at the speed of dot product with none of the runtime overhead of computing norms. Standard production trick.

### 5. FAISS flat vs approximate indexes
- **`IndexFlatIP`** (what we use): exact brute-force search. Every query compared to every vector. Guarantees perfect recall. O(N) per query. Fine up to ~1M vectors.
- **`IndexIVF`**: clusters vectors, only searches the nearest clusters. ~10–100x faster, small recall loss.
- **`IndexHNSW`**: navigable small-world graph. State-of-the-art for large scale. ~100x faster than flat, tunable recall.

Choose based on scale: flat until you feel the latency pain, then approximate.

### 6. Tenant isolation lives in the wrapper, not the index
FAISS itself has no concept of tenants. Our `FaissFlatIndex` wrapper:
1. Retrieves top-k globally from FAISS
2. Filters results by `chunk.tenant_id == query_tenant_id`
3. Returns filtered list

This works for a demo but has two production problems:
- Filtering *after* retrieval means top-k might all belong to another tenant → zero results for the querying tenant
- Not scalable — needs per-tenant sub-indexes for large deployments

The fix (M9): partition the index per tenant, or use a vector DB with built-in filtering (Qdrant, Milvus). For now, the design *supports* multi-tenancy correctly; scale is a separate concern.

## Why the design choices

- **BGE-small over MiniLM**: better MTEB benchmark scores at similar speed
- **`show_progress_bar=False`**: silences the progress bar in library code — noisy in production logs
- **Parallel `_chunks` list**: FAISS returns integer indices; we translate them back to `Chunk` objects. Alternative is FAISS's `IDMap` wrapper, but a plain list is simpler at this scale.
- **`score` stored on `metadata`**: keeps the `Chunk` dataclass clean; scoring is a per-retrieval property, not intrinsic to the chunk

## Interview flashcards

1. **Q:** What's the difference between a bi-encoder and a cross-encoder?
   **A:** Bi-encoder embeds query and document independently, enabling pre-computation of document vectors and fast nearest-neighbor search. Cross-encoder feeds query and document jointly through a transformer, producing one relevance score. Bi-encoder is O(1) per query lookup; cross-encoder is O(N) transformer forward passes. Bi-encoder retrieves, cross-encoder reranks.

2. **Q:** Why normalize embeddings?
   **A:** To reduce cosine similarity to a simple inner product. FAISS's `IndexFlatIP` computes dot products very fast; if vectors are unit-normalized, that dot product *is* cosine similarity. No division, no norm computation at query time.

3. **Q:** Why does BGE use a query prefix?
   **A:** Asymmetric retrieval. BGE was trained with different objectives for queries vs passages. The prefix signals to the model which role the text is playing. Skipping the prefix on queries drops recall measurably.

4. **Q:** When would you switch from FAISS Flat to HNSW?
   **A:** When query latency on your flat index exceeds SLA. Rough rule: flat is fine up to ~1M vectors on modern hardware. Beyond that, HNSW gives you 100x speedup with a small recall trade-off you can tune via `ef_search`.

5. **Q:** How does your system prevent tenant A from seeing tenant B's documents?
   **A:** Every Chunk carries a `tenant_id`. The retriever passes the requesting `tenant_id` to the index, which filters results after FAISS retrieval. This is correct but not scalable — for high tenant counts, the right architecture is per-tenant sub-indexes or a vector DB with native filtering.

6. **Q:** What's the embedding dimension of BGE-small, and does it matter?
   **A:** 384. Trade-off: smaller dim = faster search, less memory, but potentially lower recall. BGE-large is 1024-dim with better recall. For most production RAG, 384–768 dim is the sweet spot. Higher dims help for very large or very nuanced corpora.

7. **Q:** Why `IndexFlatIP` instead of `IndexFlatL2`?
   **A:** L2 distance and inner product are related but not equivalent for retrieval. Since we normalize vectors, inner product equals cosine similarity, which is the standard similarity for semantic search. L2 works too but interprets differently — smaller is better in L2, larger is better in IP.

8. **Q:** What happens if you index 100k documents but query for one that's very different from all of them?
   **A:** You still get top-k results — FAISS always returns the nearest neighbors, even if all scores are low. That's why you should threshold on similarity, not just return top-k. Below some score (~0.5 for cosine), results are noise.

9. **Q:** How does FAISS know which chunk each vector belongs to?
   **A:** It doesn't. FAISS stores only vectors indexed by integer position (0, 1, 2, ...). We maintain a parallel `list[Chunk]` in our wrapper — position N in FAISS corresponds to position N in the list. The FAISS `search()` returns integer indices, and we translate them to Chunks. For more complex mappings, use `IndexIDMap`.

## Code walkthrough prompt

*"Explain how a query turns into a semantic search."*

> "The query string gets prefixed with the BGE query template — this is because BGE is an asymmetric retriever, trained to expect different framing for queries versus passages. The prefixed query goes through the sentence-transformers model, which produces a 384-dimensional vector, normalized to unit length so that inner product equals cosine similarity. The FaissFlatIndex takes this vector and calls `IndexFlatIP.search`, which computes dot products against every stored chunk vector — brute force, but exact. FAISS returns the top-k integer indices and their scores. My wrapper translates those indices back into Chunk objects using the parallel _chunks list, filters by tenant_id for isolation, attaches the score to each chunk's metadata, and returns the filtered list."
