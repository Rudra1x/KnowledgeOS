# Checkpoint 2.3 — SemanticChunker

## What we built
- `SemanticChunker` — first content-aware chunker; splits where topic actually shifts
- Regex sentence splitter with note on production upgrade path (spaCy/nltk)
- Adjacent-sentence cosine similarity via BGE embeddings (already normalized)
- **Percentile-based breakpoint threshold** — adapts to per-document similarity distribution
- Size enforcement pass (subdivide huge chunks, merge tiny ones)
- Empirical comparison: Recursive=10 uniform chunks, Semantic=5 variable chunks

## Core concepts

### 1. The core intuition — cosine similarity as topic continuity
Two adjacent sentences discussing the same concept have similar embeddings. Two sentences from different topics have dissimilar embeddings. Cosine similarity between adjacent sentence vectors traces topic continuity — the low points are topic shifts.

```
sentence_i  embedding → v_i
sentence_i+1 embedding → v_{i+1}
similarity[i] = dot(v_i, v_{i+1})   # BGE vectors are normalized → cosine
```

Split where `similarity[i] < threshold`.

### 2. Percentile threshold > absolute threshold
Hard threshold (`split if sim < 0.7`) fails on:
- Dense technical documents (all similarities ~0.8 → never splits)
- Loosely connected prose (all similarities ~0.4 → splits every sentence)

Percentile threshold adapts to *this document's* similarity distribution:
```python
threshold = np.percentile(sims, 100 - breakpoint_percentile)
# breakpoint_percentile=95 → threshold at 5th percentile of sims
# → split the 5% most-different adjacent sentence pairs
```

This is a generally applicable ML pattern: use the distribution's own statistics as the threshold rather than a hard-coded absolute.

### 3. Semantic chunking has a real cost — double embedding
At ingestion:
1. Embed every sentence (for breakpoint detection) — extra cost
2. Embed every final chunk (for indexing) — standard cost

On a 100K-document corpus, this is roughly 2x the standard embedding cost. Depending on batch size and hardware, that's 10-30 extra minutes per corpus. For a startup paying per API call, it's a real budget line.

The cost is worth it *when semantic coherence matters* (narrative content, meeting notes, articles). It's overkill for technical reference material (dictionary-style entries that should stay separate) — which is exactly what the benchmark showed.

### 4. Why Semantic ranked last on technical corpus
Our gold set queries target discrete concepts (BM25, dense retrieval, FAISS). Semantic chunking *merged* related paragraphs — "dense retrieval" and "hybrid retrieval" became one chunk because BGE judged them semantically adjacent (they are). But a query "What is hybrid retrieval?" now has to compete against a chunk that embeds both dense AND hybrid content. The match is diluted vs a smaller dedicated chunk.

Semantic chunking wins when:
- Paragraphs form a continuous narrative arc (novels, meeting summaries)
- Topic shifts are real but gradual (research papers)

Semantic chunking loses when:
- Each paragraph is a discrete reference entry (RAG primer, API docs, FAQs)
- Gold set queries map to specific paragraphs (most technical benchmarks)

### 5. Sentence splitting quality matters
Our regex `r"(?<=[.!?])\s+(?=[A-Z])"` is fast but wrong on:
- `Dr. Smith said` (abbreviation)
- `e.g. retrieval` (Latin abbreviation)
- `v1.5 of` (version numbers)
- `Fig. 3 shows` (figure references)

These false splits hurt semantic chunking more than they hurt other chunkers because semantic chunking *depends* on sentence boundaries to compute similarity. Production upgrade: use `spaCy`'s sentence segmenter or `nltk.sent_tokenize`.

## Why the design choices
- **Percentile over absolute**: corpus-adaptive, no per-document tuning
- **`min_chunk_size` + `max_chunk_size`**: percentile thresholds can produce 50-char or 3000-char chunks; size enforcement keeps them usable
- **Same embedder as pipeline**: avoids embedding model inconsistency — if chunks and queries use different embedders, similarity scores are not comparable
- **Non-determinism note in docstring**: API embedders may produce slightly different vectors across calls; determinism requires local embedding models

## Interview flashcards

1. **Q:** How does semantic chunking know where to split?
   **A:** It embeds every sentence, then computes cosine similarity between each adjacent sentence pair. Topic continuity correlates with high similarity; topic shifts produce low-similarity transitions. Split at transitions below a percentile-based threshold — the 5% most-different adjacent pairs.

2. **Q:** Why percentile-based threshold instead of absolute?
   **A:** A hard threshold like 0.7 breaks on dense documents (all sims ~0.8, never splits) and loose prose (all sims ~0.4, splits every sentence). A percentile threshold adapts to the document's own distribution — always produces a sensible number of splits regardless of domain.

3. **Q:** Semantic chunking ranked last in your benchmark. Isn't it supposed to be the best?
   **A:** On technical reference material with one discrete concept per paragraph, it's the worst — it merged related paragraphs into larger chunks that diluted per-concept embeddings. On long-form narrative content (meeting notes, research papers, articles), it would likely win. Chunker quality is corpus-dependent. This is the main lesson.

4. **Q:** What's the computational cost of semantic chunking?
   **A:** Roughly 2x the standard embedding cost — every sentence is embedded once for breakpoint detection, then every final chunk is embedded again for indexing. On large corpora this is a real time and cost consideration.

5. **Q:** How would you improve the sentence splitter?
   **A:** Replace the regex with spaCy's statistical sentence segmenter (`nlp.pipeline["senter"]`) or NLTK's punkt tokenizer. Both handle abbreviations, numbers, and edge cases correctly. The regex is fast and adequate for clean text; it fails on real-world corpora with Dr., e.g., Fig., v1.5, and similar patterns.

6. **Q:** Why use the same embedder for chunking and indexing?
   **A:** Consistency. If chunking uses embedder A to detect topic shifts and indexing uses embedder B to represent chunks, the similarity scores are in different vector spaces. Chunk boundaries optimized for A may be suboptimal for B. Same embedder means same geometric space, same notion of "similar."

## Code walkthrough prompt

*"How does your semantic chunker work?"*

> "It has four steps. First, I split the document into sentences using a regex on sentence-ending punctuation followed by a capital letter — fast and adequate for clean text, with a production upgrade path to spaCy. Second, I embed every sentence using the same BGE embedder as the rest of the pipeline, then compute dot products between adjacent sentence vectors — since BGE normalizes to unit length, this gives cosine similarity directly. Third, I compute a percentile-based breakpoint threshold: at percentile=95, I split at the 5% most-different adjacent transitions. This adapts to the document's own similarity distribution rather than a hard-coded number. Fourth, I group sentences between breakpoints, then enforce size bounds — subdivide groups exceeding max_chunk_size via character slicing, merge groups below min_chunk_size with their neighbor. In our benchmark, semantic chunking scored r@1=0.80 on a technical reference corpus — last among six strategies — because it merged discrete concepts that should have stayed separate. On long-form narrative, I'd expect it to rank first."
