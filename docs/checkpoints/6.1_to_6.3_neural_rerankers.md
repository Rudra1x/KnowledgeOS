# Checkpoint 6.1 — CrossEncoderReranker

## What we built
- `CrossEncoderReranker` — ms-marco-MiniLM-L-6-v2 cross-encoder
- `original_rank`, `rerank_score`, `rerank_model` metadata on every result
- Verified: rank 2→1 on the persistent "dense vs BM25" miss
- Result: recall@1 0.900→1.000 at 197ms total for 10 queries (20ms/query)

## Core concepts

### 1. Bi-encoder vs cross-encoder — the fundamental difference

**Bi-encoder (retrieval):**
```
embed(query)  → q_vec   [384 dims]
embed(chunk)  → c_vec   [384 dims]
score = dot(q_vec, c_vec)
```
Query and chunk are encoded independently. The model never sees them together. Fast (O(1) per comparison after indexing) but loses token-level interaction.

**Cross-encoder (reranking):**
```
encode([CLS] query [SEP] chunk [SEP]) → relevance_score
```
Query and chunk are concatenated as one input. The model computes full self-attention across all tokens of both. Every query token can attend to every chunk token. This cross-attention captures "how does 'dense' in the query relate to 'neural embeddings' in the chunk?" — something the bi-encoder can't express.

### 2. Why cross-encoders can't be used for retrieval
No pre-indexing possible. You'd need to run inference on every (query, chunk) pair at query time — O(N) cross-encoder calls per query. At N=1M chunks: 1M × 20ms = 5.5 hours per query. Completely infeasible.

The two-stage pipeline is the solution:
- Stage 1: Bi-encoder retrieval (fast, ~2ms, gets right chunk into top-20)
- Stage 2: Cross-encoder reranking (slower, ~20ms, moves right chunk to rank 1)

### 3. The rank movement that proves reranking works
```
"How is dense retrieval different from BM25?"
→ Vector retrieval:  correct chunk at rank 2 (cosine similarity insufficient)
→ Cross-encoder:     correct chunk at rank 1 (joint attention captures the distinction)
```
Bi-encoder: "dense retrieval" and "BM25" embed in adjacent regions, causing confusion. Cross-encoder: sees the explicit contrast "different from" between "dense" and "BM25" — joint attention catches this relationship.

### 4. ms-marco-MiniLM-L-6-v2 — the right default
- 22MB, 6-layer MiniLM distilled from a larger model
- Trained on MS MARCO passage ranking (Bing query logs, web passages)
- 20ms/query on CPU — viable for real-time RAG
- Upgrade path: L-12-v2 (33MB, marginally better) → electra-base (110MB, best quality)

### 5. The latency arithmetic
```
Vector retrieval (top-5):   2ms
Cross-encoder rerank (5 pairs): 20ms
Total:                      22ms/query
```
Additive, not multiplicative. The reranker runs after retrieval on a tiny set. Compared to agentic (23s/query) for the same recall, the two-stage pipeline is 1045× faster.

## Interview flashcards

1. **Q:** Why does a cross-encoder outperform a bi-encoder for ranking?
   **A:** Cross-encoders encode query+chunk jointly — every query token attends to every chunk token via self-attention. This captures token-level interactions ("different from" connecting "dense" to "BM25"). Bi-encoders encode separately and compare by dot product — they measure proximity in embedding space but miss specific token-level relationships.

2. **Q:** Why can't cross-encoders be used for retrieval?
   **A:** No pre-indexing. A bi-encoder embeds each chunk once at index time and compares via fast dot product at query time. A cross-encoder requires a full forward pass for every (query, chunk) pair at query time — O(N) inference calls. At 1M chunks × 20ms each = 5.5 hours per query.

3. **Q:** The correct chunk was at rank 2 from vector retrieval. Cross-encoder moved it to rank 1. What happened?
   **A:** The bi-encoder similarity between "dense retrieval different from BM25" and the correct chunk was similar to an adjacent chunk — not enough margin to rank first. The cross-encoder saw the complete query and chunk together, recognized the explicit contrast relationship, and scored the correct chunk significantly higher.

4. **Q:** What metadata does your cross-encoder attach to results?
   **A:** `rerank_score` (cross-encoder relevance score), `rerank_model` (model name for provenance), `original_rank` (where the chunk ranked before reranking). Original rank lets you measure how much the reranker moved each result and diagnose ranking inversions.

5. **Q:** When would you choose ms-marco-MiniLM-L-12-v2 over L-6-v2?
   **A:** When 20ms/query isn't enough and you want marginal quality improvement — L-12-v2 is 1.5× larger, ~2× slower, and marginally better on MS MARCO benchmarks. On a GPU, both run in <2ms and the quality difference matters more than latency. On CPU in production, L-6-v2 is the right default.

## Code walkthrough prompt

*"Walk me through your cross-encoder reranker and why it works."*

> "The cross-encoder takes (query, chunk) pairs and scores them jointly. Unlike the bi-encoder that encodes query and chunk separately and compares by dot product, the cross-encoder concatenates them as `[CLS] query [SEP] chunk [SEP]` and runs full self-attention across all tokens. Every query token attends to every chunk token — this lets the model reason about specific relationships like 'different from' connecting 'dense retrieval' to 'BM25', which the bi-encoder's embedding proximity can't express. We use ms-marco-MiniLM-L-6-v2: 22MB, trained on MS MARCO passage ranking, 20ms per 5-chunk batch on CPU. The reranker fixed our persistent miss — 'How is dense retrieval different from BM25?' had the correct chunk at rank 2 from vector retrieval; cross-encoder moved it to rank 1. Total pipeline: 2ms retrieval + 20ms reranking = 22ms at perfect recall, vs 23s for agentic retrieval at the same recall. The two-stage retrieve-then-rerank is how every major search vendor builds their product."

# Checkpoint 6.2 — BGEReranker

## What we built
- `BGEReranker` — BAAI/bge-reranker-base (278MB)
- Head-to-head vs MS-MARCO: both r@1=1.000
- MS-MARCO: 22ms/query (22MB). BGE-base: 116ms/query (278MB)
- Key finding: 5.3× slower, same recall — MS-MARCO wins on this corpus

## Core concepts

### 1. Same architecture, different training data
Both BGEReranker and CrossEncoderReranker are cross-encoders — same `sentence_transformers.CrossEncoder` class under the hood. The difference is training:

- **MS-MARCO-MiniLM:** trained on Bing query logs + web passages. 22MB distilled model.
- **BGE-reranker-base:** trained on diverse retrieval data including academic, technical, multilingual content. 278MB full BERT-base model.

On English technical corpora, MS-MARCO's web-search training is already a good match. BGE's broader training shows more advantage on domain-specific or multilingual content.

### 2. Model size and latency on CPU — roughly linear
```
ms-marco-MiniLM-L-6-v2:  22MB  → 22ms/query
bge-reranker-base:        278MB → 116ms/query
```
~12.6× size difference → ~5.3× latency difference. Not linear because model complexity (layers, attention heads) matters more than raw parameter count. On GPU: both run in <5ms and the ratio narrows further.

### 3. BGE-v2-m3 for multilingual
`BAAI/bge-reranker-v2-m3` supports 100+ languages in the same model. For multinational enterprise corpora (English + Chinese + Spanish documents), one reranker instead of per-language models. This is the architecturally significant variant of BGE reranker.

### 4. Interchangeable interface — the ABC contract paying off
```python
# Swap in one line
reranker = CrossEncoderReranker("cross-encoder/ms-marco-MiniLM-L-6-v2")
reranker = BGEReranker("BAAI/bge-reranker-base")       # same interface
reranker = BGEReranker("BAAI/bge-reranker-v2-m3")      # multilingual
```
The `Reranker` ABC enforces `rerank(query, chunks, top_k) → list[Chunk]`. Every downstream component — the benchmark script, the generator pipeline — uses this interface and doesn't need to know which model is running.

### 5. When BGE earns its latency premium
- Domain-specific technical corpora where MS-MARCO's web training doesn't transfer well
- Multilingual corpora (use BGE-v2-m3)
- When you need higher recall on specific failure queries that MS-MARCO misses
- Always: validate on a sample of your actual production data before choosing

## Interview flashcards

1. **Q:** BGEReranker and CrossEncoderReranker both achieve r@1=1.000 on your corpus. Which do you deploy?
   **A:** MS-MARCO (CrossEncoderReranker) for English technical content — same quality at 5.3× lower latency. BGE earns its premium when: the corpus is domain-specific (academic, medical, legal) where MS-MARCO's web-search training doesn't transfer, or when multilingual support is needed. Always validate on your actual data.

2. **Q:** BGE-reranker-base is 278MB vs MS-MARCO's 22MB. Why the size difference?
   **A:** MS-MARCO uses MiniLM — a knowledge-distilled model with 6 layers compressed from a larger teacher. BGE uses a full BERT-base architecture (12 layers, 768 hidden dim, 109M parameters). MiniLM trades some quality for 12.6× smaller size. The distillation process preserves most of the ranking quality at a fraction of the model size.

3. **Q:** When would you use BGE-reranker-v2-m3 instead of bge-reranker-base?
   **A:** For multilingual corpora. The v2-m3 variant handles 100+ languages in the same model — a query in English reranks chunks in Chinese, Spanish, or German without per-language models. For a multinational enterprise with documents in multiple languages, this is architecturally necessary.

4. **Q:** How would you validate which reranker is better on your production corpus?
   **A:** Create a gold set of 100 representative queries from your actual user traffic, labeled with relevant document IDs. Run both rerankers on the same retrieval candidates. Compare recall@1, MRR, and latency. The winner on your gold set is the right choice — not the one that wins on MS MARCO benchmarks.

5. **Q:** Both rerankers download models from HuggingFace. What's your production deployment strategy?
   **A:** Bake the model weights into your Docker image at build time (`RUN huggingface-cli download BAAI/bge-reranker-base`). Never download at runtime — cold starts would take minutes. Pin the model revision hash for reproducibility. For low-latency serving, run the reranker on a GPU sidecar with TorchServe or Triton.

## Code walkthrough prompt

*"How does BGEReranker differ from CrossEncoderReranker in your stack?"*

> "They're the same cross-encoder architecture — both use sentence_transformers CrossEncoder, both take (query, chunk) pairs and output a relevance score. The difference is training data and model size. MS-MARCO-MiniLM-L-6-v2 is a 22MB distilled model trained on Bing query logs and web passages — fast, good for general English retrieval. BGE-reranker-base is 278MB, trained on a diverse mix including academic and technical content — broader coverage, 5.3× slower on CPU. On our English technical corpus, both achieve identical recall@1=1.000. BGE's broader training would show advantage on domain-specific or multilingual content where MS-MARCO's web-search distribution doesn't transfer. The Reranker ABC makes them interchangeable — swap the constructor, everything else is unchanged. For production on English technical content, MS-MARCO is the right default. BGE earns its premium when you measure a quality gap on your actual corpus."

# Checkpoint 6.3 — LLMReranker

## What we built
- `LLMReranker` — score mode (1-10 per chunk) and compare mode (rank all at once)
- Score parser: regex extracts integer 1-10 from free-text LLM output
- Compare parser: extracts ranked list from "3, 1, 4, 2" format
- Result: score mode r@1=0.900 (same as baseline), compare mode 0.800; 360s for 10 queries

## Core concepts

### 1. LLM scoring — explicit relevance judgment
Cross-encoders output a raw float (e.g., 7.3) from a sigmoid layer. LLM scoring outputs a human-interpretable 1-10 score with optional explanation:

```
Question: What is BM25?
Passage: BM25 is a sparse retrieval algorithm...
Score: 9
```

The score is interpretable and the prompt can include custom criteria — "prefer passages with specific formulas," "prefer primary sources," etc. No cross-encoder can be instructed at runtime.

### 2. Score mode vs compare mode
**Score mode:** evaluate each chunk independently. O(K) LLM calls for K chunks. More reliable — model only needs to hold one chunk in context. Results: each chunk gets an independent score.

**Compare mode:** evaluate all K chunks at once. O(1) LLM calls. Faster per-query but requires the model to hold all K chunks in context and produce a consistent ranking. Unreliable at 3B scale — model loses track of passages or produces inconsistent orderings.

### 3. The parsing problem
LLM output is free-form. "I would rate this passage a 7 out of 10 because..." needs parsing. Strategy:
```python
match = re.search(r"\b([1-9]|10)\b", response)
score = float(match.group(1)) if match else 5.0  # neutral default on parse failure
```
The neutral default (5.0) prevents complete failure on unparseable responses. Production upgrade: "Answer with ONLY a single integer between 1 and 10" constraint.

### 4. The definitive latency finding
```
Cross-encoder (MS-MARCO): 22ms/query
LLM score mode (Qwen2.5-3B): 3287ms/query  ← 149× slower
```
50 Ollama calls (5 chunks × 10 queries) at ~2-3s each = 360s total. This is not a small-scale issue — it's fundamental to the architecture. Each chunk requires a full LLM inference call. Cross-encoders batch all pairs and use a specialized model 10-100× faster per call.

### 5. Custom criteria — the only production justification
```python
reranker = LLMReranker(
    criteria="Prefer passages that cite peer-reviewed sources or official documentation.",
)
```
No cross-encoder can be told this at runtime. For regulated domains (medical, legal, financial) where source authority matters and can't be encoded in a training objective, LLM reranking with custom criteria is the only option. Accept the latency; run async.

## Interview flashcards

1. **Q:** LLM reranker scored r@1=0.900 (same as baseline) at 360s for 10 queries. When would you still use it?
   **A:** When custom ranking criteria can't be expressed as training data for a cross-encoder: "prefer passages from peer-reviewed papers," "prefer primary official documentation over blog posts," "prefer passages that explicitly state uncertainty." These runtime instructions change the ranking objective. For async research pipelines where 30s/query is acceptable, LLM reranking with custom criteria is the right tool.

2. **Q:** Why is compare mode less reliable than score mode for a 3B model?
   **A:** Compare mode requires holding 5 chunks in context simultaneously and producing a consistent ranked list. A 3B model's context capacity is limited — it may confuse passage indices, skip chunks, or produce inconsistent orderings. Score mode evaluates one chunk at a time — simpler task, more reliable output.

3. **Q:** What's your parser's fallback when the LLM returns unparseable output?
   **A:** Score 5.0 (neutral). The regex `\b([1-9]|10)\b` finds the first integer in range 1-10. If nothing matches, 5.0 is the default — not 0 (which would sink the chunk) and not 10 (which would promote it artificially). Neutral is the right default for parse failures.

4. **Q:** The LLM reranker is 149× slower than the cross-encoder. Is there a way to speed it up?
   **A:** Three options. (1) Batch fewer chunks: fetch 3 instead of 5, reducing LLM calls by 40%. (2) Use a smaller model: a 1B parameter model would be ~3× faster than 3B. (3) Parallelize: run 5 LLM calls concurrently (5 threads) — reduces wall-clock time by ~4× with async I/O. Even parallelized, it's still 10-20× slower than cross-encoder. Accept it or use cross-encoder.

5. **Q:** How do you combine LLM reranking with cross-encoder reranking?
   **A:** Two-stage: cross-encoder reranks the top-20 by semantic quality → LLM reranker applies custom criteria to the top-5. The cross-encoder removes obviously irrelevant candidates cheaply; the LLM applies nuanced criteria to a small, already-quality set. This minimizes LLM calls (5 instead of 20) while still applying custom logic.

## Code walkthrough prompt

*"When and why would you use LLM reranking over a cross-encoder?"*

> "The honest answer is: almost never for real-time RAG. The LLM reranker ran 360s for 10 queries vs the cross-encoder's 3.2s — 149× slower for the same or worse recall. The one legitimate use case is custom ranking criteria that no cross-encoder is trained on. If a client in a regulated domain says 'always prefer passages from peer-reviewed sources over blog posts,' that's a runtime instruction — I can add it to the LLM reranker's prompt as a criteria string. No cross-encoder can be instructed at runtime to apply source authority rules. For that use case, I'd accept the latency and run it async — nightly report generation, research synthesis, document processing pipelines where 30s/query is fine. The implementation has two modes: score mode evaluates each chunk independently at 1-10 with a regex parser that falls back to 5.0 on unparseable output; compare mode asks the LLM to rank all chunks at once, which is faster per-query but unreliable at 3B scale because the model struggles to hold 5 chunks in context simultaneously."
