# Checkpoint 1.2 — DOCX + Markdown Loaders

## What we built
- `MarkdownLoader` — regex-based heading detection, section-per-Document
- `DOCXLoader` — style-based heading detection (`Heading 1-9`), auto-routes `.doc` → `.docx` via LibreOffice
- Table extraction preserved in both formats (Markdown-formatted text)
- Preamble handling for content before the first heading

## Core concepts

### 1. Structure is signal
Headings aren't decoration — they're natural semantic boundaries the author already chose. Throwing them away throws away the document's own organization. Preserving `section_title` and `heading_level` in metadata means retrieval can boost matches whose section headers relate to the query, and citations become more informative ("under 'Methodology'").

### 2. Section-per-Document trade-off
- Bigger unit than a chunk → preserves context
- Smaller unit than the whole file → focused retrieval
- Sections vary in size — some too big (need further chunking), some too small (may not stand alone)
- Downstream chunker handles size normalization

### 3. Legacy formats need routers, not one-size-fits-all loaders
`.doc` (Word 97-2003 binary) is a fundamentally different beast from `.docx` (2007+ XML zip):
- `.docx` → `python-docx` reads it natively
- `.doc` → binary blob, needs LibreOffice conversion or `antiword` on Linux

The professional pattern is to detect the extension and route to the appropriate handler (or convert first, then handle). Our loader auto-converts `.doc` → `.docx` via `soffice --headless --convert-to docx`.

### 4. Graceful degradation
When LibreOffice isn't installed, we raise a clear error with an install hint — not a cryptic library-internal traceback. Users can fix the problem themselves. This is a production hygiene principle: errors should point to solutions.

### 5. Regex vs style-based heading detection
- Markdown: regex `^(#{1,6})\s+(.+?)$` — the format spec is regex-friendly
- DOCX: style name matching against `{"Heading 1", ..., "Heading 9"}` — the format has explicit style metadata

Different formats, same output shape. That's the ABC contract working.

## Why the design choices

- **`python-docx` over `docx2txt`**: preserves heading styles and table structure; `docx2txt` throws all of it away
- **Section-per-Document, not paragraph-per-Document**: paragraphs are too fine-grained; sections are the natural semantic unit
- **LibreOffice for `.doc` conversion**: free, cross-platform, produces valid `.docx`; alternatives (`antiword`) are Linux-only
- **`Preamble` fallback for MD content before H1**: some documents start with prose before any heading; treating it as a section preserves it
- **Tables → Markdown format**: LLMs handle Markdown tables well as context; other serializations (JSON, HTML) waste tokens

## Interview flashcards

1. **Q:** Why is `.doc` harder to load than `.docx`?
   **A:** `.docx` is a ZIP of XML files with a public standard (OOXML) — parseable by any library. `.doc` is a proprietary binary format from 1997. In practice you convert `.doc` to `.docx` first (LibreOffice headless) and then use the same loader.

2. **Q:** Why per-section instead of per-paragraph or whole-file?
   **A:** Sections are the author's natural semantic unit. Paragraphs are too fine — retrieval loses context. Whole-file is too coarse — loses provenance and chunker gets no help from structure. Sections balance both.

3. **Q:** How does your loader handle a `.docx` with no heading styles applied?
   **A:** Everything falls under a default "Introduction" section. It's still retrievable, just without heading-level provenance. Not ideal, but graceful.

4. **Q:** How would you extend this to preserve list structure?
   **A:** `python-docx` exposes paragraph style (`List Bullet`, `List Number`). I'd add a paragraph-level metadata field for list membership. Downstream, the chunker could keep list items together as a unit.

5. **Q:** Why route `.doc` through LibreOffice instead of writing a binary parser?
   **A:** The `.doc` format is 300+ pages of proprietary spec, poorly documented. Writing a parser is months of work for a legacy format that's shrinking in the wild. LibreOffice handles it in one shell command, correctly, forever. Buy vs build — buy.

## Code walkthrough prompt

*"How do you extract structure from Word documents?"*

> "For .docx, I use python-docx which exposes paragraphs with their style. I walk paragraphs, group them under the last-seen heading style — 'Heading 1' through 'Heading 9' — and emit one Document per section. Tables are extracted separately with `content_type: 'table'` so they're addressable independently. Preamble content before the first heading gets an 'Introduction' section as fallback. For .doc, the format is a proprietary binary; I shell out to LibreOffice headless to convert to .docx in a temp directory, then read the converted file with the same code path. If LibreOffice isn't installed, the loader raises with a clear message pointing to the install page rather than a library-internal traceback. Same principle applies to Markdown — I use a heading regex, treat text between headings as sections, and preserve heading level in metadata for downstream boosting."
