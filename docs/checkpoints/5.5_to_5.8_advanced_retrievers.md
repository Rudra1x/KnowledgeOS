# Checkpoint 5.5 — SelfRAGRetriever

## What we built
- `SelfRAGRetriever` — retrieve gate (should we retrieve?) + relevance filter (is each chunk relevant?)
- 6/6 gate accuracy: arithmetic/geography → NO, RAG/FAISS/BM25 → YES
- 2/2 relevance filter accuracy on synthetic tests
- `min_relevant_chunks` fallback — never return empty if candidates exist
- Correct end-to-end: "What is 2+2?" → 0 chunks, "What is BM25?" → 1 chunk (with fallback)

## Core concepts

### 1. Not every query needs retrieval
Roughly 30-40% of real user queries to a knowledge base can be answered from parametric knowledge — the LLM's training data. "What is 2+2?", "What is the capital of France?", "What year was Python created?" — no corpus needed. Retrieving for these wastes compute and can hurt: irrelevant retrieved context confuses the generator even with "only use context" instructions.

### 2. The retrieve gate — binary classification
```
YES: question requires external knowledge base lookup
NO:  question answerable from general knowledge
```

Qwen2.5-3B correctly classified all 6 cases. Binary YES/NO output format is key — it prevents the model from saying "Yes, this question requires retrieval because..." which would be unparseable.

### 3. The relevance filter — per-chunk quality control
After retrieval, each chunk is evaluated: "Is this passage relevant to answering this question?" Irrelevant chunks are dropped before reaching the generator. This prevents the generator from being confused by retrieved content that was semantically adjacent but not actually useful.

### 4. The min_relevant_chunks fallback
If the relevance filter is too aggressive, it could return zero chunks — the generator gets nothing. `min_relevant_chunks=1` ensures at least one chunk always passes through, even marked as low-confidence. This prevents complete retrieval failure from compounding into generation failure.

### 5. Output format is more important than prompt complexity
"Answer with ONLY one word: YES or NO" — this constraint makes parsing trivial and reliable. Without it, the model would produce paragraphs that need sophisticated parsing. Structured output via prompt engineering is the production pattern before fine-tuning or function calling.

### 6. Self-RAG makes retrieval adaptive
- Parametric queries (math, common knowledge) → skip retrieval entirely → lower latency
- Knowledge-intensive queries → retrieve + filter → higher quality
- The pipeline adapts to query type automatically without rule-based routing

## Interview flashcards

1. **Q:** What are the two decision points in Self-RAG?
   **A:** First, the retrieve gate: should we retrieve at all? (parametric questions skip retrieval). Second, the relevance filter: for each retrieved chunk, is it genuinely relevant? Irrelevant chunks are dropped before generation. This prevents both unnecessary retrieval and noise injection.

2. **Q:** Why is "Answer with ONLY one word: YES or NO" important in the prompt?
   **A:** Reliable parsing. Without the constraint, a 3B model produces "Yes, I think retrieval is needed because..." which requires regex parsing that breaks on variations. "YES" or "NO" as the complete output is unambiguous — startswith check, done.

3. **Q:** Your gate classified all 6 test cases correctly with a 3B model. Is the gate reliable in production?
   **A:** On binary classification with clear examples, 3B models are surprisingly reliable. The failure mode is ambiguous queries — "How do I use Python for machine learning?" straddles parametric (Python syntax) and corpus knowledge (ML concepts). For production, validate on 100 representative queries from your actual user base.

4. **Q:** The relevance filter in your end-to-end test returned `relevant=False` but still returned the chunk. Explain.
   **A:** The `min_relevant_chunks=1` fallback fired. The filter judged the BM25 chunk as marginally relevant (starts with embedding-similarity content due to boundary artifact, not just BM25). The fallback prevented zero results — better to return a marginally relevant chunk than nothing.

5. **Q:** Self-RAG adds 30s per 10 queries vs vector's 0.2s. When is that worth it?
   **A:** When: the query mix includes ~30% parametric questions that can be skipped (reduces generator load). When: irrelevant context causes significant faithfulness failures that the relevance filter catches. When: latency budget allows (research assistants, async systems). Not for: real-time chat, simple RAG where all queries are knowledge-intensive.

## Code walkthrough prompt

*"How does Self-RAG work?"*

> "Self-RAG adds two LLM decision gates to standard retrieval. The first is the retrieve gate: before doing any retrieval, I ask the LLM 'does answering this question require looking up specific facts from an external knowledge base?' For arithmetic or capital cities, it says NO and we return empty — the generator answers from parametric knowledge. For BM25 or FAISS questions, it says YES and we proceed. The second is the relevance filter: after retrieving candidates, each chunk is evaluated individually against the question. Irrelevant chunks — semantically adjacent but not actually useful — are dropped. If the filter removes everything, a `min_relevant_chunks=1` fallback ensures at least one chunk reaches generation. The key design insight is output format: 'Answer with ONLY one word: YES or NO.' A 3B model will reliably output a single word with that constraint; without it, you get paragraphs that require fragile parsing. In our benchmark, Self-RAG scored recall@3=0.900 vs 1.000 for others — the relevance filter was slightly too aggressive, removing chunks that would have contributed to recall@3."

# Checkpoint 5.6 — CRAGRetriever

## What we built
- `CRAGRetriever` — evaluate retrieved docs (CORRECT/AMBIGUOUS/INCORRECT), correct if poor
- Two-signal `_evaluate()`: LLM semantic judgment + keyword overlap heuristic
- Reformulation + re-retrieval as correction action
- `crag_action` and `crag_attempt` metadata on every result
- Result: Tokyo query correctly INCORRECT via keyword heuristic; BM25 query AMBIGUOUS (boundary artifact); metrics query CORRECT on attempt 2

## Core concepts

### 1. CRAG's three evaluations
**CORRECT:** retrieved passages are relevant and sufficient → use as-is.
**AMBIGUOUS:** some relevant, some not → filter to relevant ones, optionally supplement.
**INCORRECT:** passages are about completely different topics → reformulate and re-retrieve.

In the original paper, INCORRECT triggers a web search. We substitute reformulation + re-retrieval (same principle, no web API required).

### 2. Small LLMs are unreliable critics
Qwen2.5-3B consistently classified unrelated chunks (BM25 content for a Tokyo weather query) as CORRECT. The model pattern-matches on "retrieved content exists" rather than reasoning about topic alignment. This is a known limitation — the original CRAG paper uses a fine-tuned critic model.

### 3. The two-signal solution
```python
# LLM says CORRECT but <30% of meaningful query terms appear in chunks
if llm_eval == "CORRECT" and overlap_rate < 0.3:
    return "INCORRECT"
```

LLM for semantic nuance, keyword overlap for ground truth. When they disagree significantly, trust the heuristic. "tokyo", "weather", "today" have zero overlap with a RAG-concepts corpus → override to INCORRECT regardless of LLM judgment.

### 4. crag_action metadata — operational diagnostics
- `attempt=1, action=correct` → corpus is healthy, query matched on first try
- `attempt=2, action=correct` → reformulation helped, second retrieval succeeded
- `attempt=3, action=fallback` → max corrections exceeded, corpus may have quality issues

Monitoring this distribution over time reveals corpus health. Rising fallback rate signals degrading corpus quality or query distribution shift.

### 5. Chunk boundary artifacts propagate through the stack
The BM25 chunk boundary ("ses embedding similarity... BM25 is a...") caused:
- M4: TF-IDF to score it lower
- M5.5: Self-RAG to mark it not-fully-relevant
- M5.6: CRAG evaluator to call it AMBIGUOUS (not CORRECT)

One bad chunk boundary creates problems at every downstream stage. CRAG amplifies corpus quality — it makes good corpora better and exposes bad corpora's problems.

### 6. CRAG is appropriate when quality signal matters more than speed
46s/query at max_corrections=2. The correction mechanism adds 2× the retrieval cost. Worth it when: serving regulated domains where incorrect context is worse than no context, when corpus is noisy and many queries would otherwise get irrelevant chunks, when "I don't have information on this" is a valid answer.

## Interview flashcards

1. **Q:** What triggers CRAG's correction mechanism?
   **A:** The evaluator returns INCORRECT or AMBIGUOUS with insufficient relevant chunks. INCORRECT means the retrieved passages are about different topics than the question. AMBIGUOUS means some are relevant, some aren't — filter the relevant ones; if there aren't enough, treat as INCORRECT and reformulate.

2. **Q:** Why did your 3B model fail to identify Tokyo weather as INCORRECT without the heuristic?
   **A:** 3B models are unreliable relevance judges — they pattern-match on "content exists" rather than reasoning about topic alignment. The original CRAG paper uses a fine-tuned critic model trained specifically on relevance judgment. The keyword overlap heuristic compensates: "tokyo", "weather", "today" have zero occurrence in a RAG-concepts corpus → override to INCORRECT.

3. **Q:** What does crag_action=fallback mean?
   **A:** The corrective loop exhausted max_corrections without achieving a CORRECT evaluation. The last retrieval's results are returned as-is. In production, this signals: the query is off-topic (no relevant content in corpus), the corpus has quality issues (relevant content exists but chunks are malformed), or max_corrections is too low.

4. **Q:** How does CRAG differ from Self-RAG?
   **A:** Self-RAG decides before retrieval (gate) and evaluates per-chunk after. CRAG evaluates the batch of retrieved results holistically and can trigger a completely new retrieval attempt. Self-RAG is about whether to retrieve and whether each piece is relevant. CRAG is about whether what was retrieved is good enough and how to correct if not.

5. **Q:** CRAG took 46s/query. When is that acceptable?
   **A:** In regulated domains (legal, medical, financial) where a wrong answer from irrelevant context is worse than no answer. When corpus is noisy and first-attempt recall without correction would be 0.6 — correction improves it to 0.85. For real-time conversational RAG: not acceptable. For nightly research synthesis: fine.

## Code walkthrough prompt

*"How does CRAG work and when would you use it?"*

> "CRAG adds a quality evaluation loop after retrieval. After retrieving candidates, the evaluator asks: are these passages relevant (CORRECT), partially relevant (AMBIGUOUS), or off-topic (INCORRECT)? I use two signals: the LLM's semantic judgment and a keyword overlap heuristic. The heuristic catches LLM false positives — if the LLM says CORRECT but less than 30% of meaningful query terms appear in the chunks, override to INCORRECT. This was necessary because Qwen2.5-3B would call unrelated chunks CORRECT without the heuristic. On CORRECT, return the results. On AMBIGUOUS, filter to only relevant chunks. On INCORRECT, reformulate the query and re-retrieve, up to max_corrections times. Every result carries crag_action (correct/ambiguous_filtered/fallback) and crag_attempt metadata — monitoring this distribution tells you when corpus quality is degrading. I'd use CRAG for regulated domains where incorrect context is worse than no context, or for noisy corpora where first-attempt retrieval has low precision. On our clean corpus, it matched baseline at 46× the latency — the correction mechanism adds overhead but no benefit when the corpus is already high quality."

# Checkpoint 5.7 — AgenticRetriever

## What we built
- `AgenticRetriever` — ReAct pattern: Thought → Action → Observation → loop
- Three tools: `vector_search`, `keyword_search`, `filter_search`
- Regex response parser: extracts (thought, action_name, action_args)
- Union accumulation across steps — chunks from all hops contribute
- Result: r@1=1.000 — first perfect recall on this corpus, closing the persistent "dense vs sparse" miss

## Core concepts

### 1. The ReAct pattern
Reason + Act — interleaved:
```
Thought: To find BM25 info, I'll use keyword search (entity matching)
Action:  keyword_search("BM25 sparse retrieval")
Observation: Found 2 chunks. BM25 is a sparse retrieval algorithm...
Thought: I have BM25 info. Do I need dense retrieval info too?
Action: vector_search("dense retrieval neural embeddings")
Observation: Found 2 chunks. Dense retrieval uses neural embeddings...
Thought: I have both sides of the comparison. I can finish.
Action: FINISH
```

Each iteration the LLM sees its history and builds a chain of reasoning. Published by Yao et al. (2022), validated across many tasks.

### 2. Tool selection emerges from LLM understanding
- BM25 (entity query) → agent chose `keyword_search` (correct — BM25 is an exact term)
- Dense vs sparse comparison → agent chose `vector_search` (correct — conceptual query)
- Evaluation metrics → agent alternated `vector_search` + `keyword_search`

No hard-coded rules. The LLM reasons about which tool fits the query type. This flexibility is the core value proposition of agentic retrieval.

### 3. Why agentic achieved r@1=1.000
The persistent miss was "How is dense retrieval different from BM25?" The agent used both keyword and vector search across its 2 steps. The union captured the correct chunk that single-method retrievers missed — the agent effectively discovered that hybrid retrieval was needed for this query without being told.

### 4. The regex parser is the fragile component
```python
thought_match = re.search(r"Thought:\s*(.+?)(?=Action:|$)", response, re.DOTALL)
action_match  = re.search(r"Action:\s*(.+)", response)
fn_match      = re.match(r"(\w+)\(([^)]*)\)", action_str)
```
The model mostly follows "Thought: ... Action: tool(args)" but occasionally deviates. Fallback: use the original query if parsing fails. Production upgrade: use function calling or JSON mode for reliable structured output.

### 5. Agentic is the most expensive retriever
23s/10 queries = 2.3s/query at max_steps=2. Each step is one Ollama call (~2-3s) plus one index search (<10ms). At max_steps=4, that's 4 Ollama calls + 4 searches = ~10s/query. For async research tools this is fine; for real-time chat it's too slow.

### 6. Small corpus = agent loops without new information
The trace showed the agent reasoning "I need more info" but retrieving the same 8 chunks with shifted emphasis. On a 100K-chunk corpus, step 2's different search query would explore genuinely different vector space regions.

## Interview flashcards

1. **Q:** What is the ReAct pattern and why use it for retrieval?
   **A:** ReAct interleaves Reasoning (Thought) with Acting (tool calls). The LLM sees its previous thoughts, actions, and observations at each step, building a reasoning chain. Applied to retrieval: the LLM plans which tool to use, executes it, evaluates the results, and decides whether to continue or stop. This makes retrieval transparent, debuggable, and adaptable to query complexity.

2. **Q:** Agentic retrieval achieved r@1=1.000 when others maxed at 0.900. How?
   **A:** The agent used both keyword and vector search across its 2 steps, unioning the results. The persistent miss was a query where single-method retrieval failed at rank 1. The agent's combination of tools covered different parts of the corpus, and the union included the correct chunk. The agent effectively discovered hybrid retrieval was needed without being told.

3. **Q:** The regex parser is your weakest component. What's the production upgrade?
   **A:** Function calling (OpenAI tool_use API, Anthropic tool_use) or structured output (JSON mode). Instead of parsing free-text "Action: vector_search(query)", the model returns a structured JSON object: `{"function": "vector_search", "args": {"query": "..."}}`. Parsing is trivial and reliable. Requires a model that supports function calling — Qwen2.5 does via Ollama.

4. **Q:** How does the agent's tool selection emerge?
   **A:** From the LLM's pre-trained understanding of tool descriptions and query types. The system prompt describes each tool's purpose ("keyword/BM25 search — good for exact terms and entities"). The LLM learned during pretraining that entity queries benefit from keyword search and conceptual queries from vector search. No fine-tuning required.

5. **Q:** When would you deploy agentic retrieval in production?
   **A:** Async research assistants (latency budget of seconds to minutes). Complex multi-document synthesis where the retrieval strategy isn't known in advance. Enterprise RAG where query types vary dramatically (some need keyword, some semantic, some filter-based). Not for: real-time chat (<500ms budget), simple Q&A where a single vector search always suffices.

## Code walkthrough prompt

*"Walk me through your agentic retriever."*

> "The agentic retriever implements the ReAct pattern — Reason then Act, interleaved. Each step, the LLM receives the original query plus a history of all previous thoughts, actions, and observations. It outputs: Thought (reasoning about what to do next) and Action (which tool to call with what arguments). I support three tools: vector_search for semantic similarity, keyword_search for BM25 exact matching, filter_search for metadata-filtered vector search. The tool call is executed against real indexes, and the retrieved chunks become the next Observation. This continues until the LLM outputs FINISH or we hit max_steps. All chunks from all steps are accumulated, deduplicated by chunk_id, ranked by retrieval score. The trace shows the agent correctly chose keyword_search for a BM25 entity query and vector_search for a conceptual comparison query — tool selection emerged from the LLM's understanding without hard-coded rules. The parser is the fragile part: regex extracting Thought/Action from free-text. Production upgrade is function calling for reliable structured output. Agentic scored r@1=1.000 — the first perfect recall on this corpus — by using both keyword and vector search across steps and unioning the results."

# Checkpoint 5.8 — Retrieval Benchmark

## Benchmark results

| Rank | Retriever | recall@1 | recall@3 | MRR | time/10q |
|------|-----------|----------|----------|-----|----------|
| 1 | agentic | 1.000 | 1.000 | 1.000 | 230s |
| 2 | vector | 0.900 | 1.000 | 0.950 | 0.2s |
| 3 | hybrid_rrf | 0.900 | 1.000 | 0.950 | 0.2s |
| 4 | filtered_boost | 0.900 | 1.000 | 0.950 | 0.2s |
| 5 | query_rewrite | 0.900 | 1.000 | 0.950 | 35s |
| 6 | crag | 0.900 | 1.000 | 0.950 | 465s |
| 7 | self_rag | 0.900 | 0.900 | 0.900 | 307s |
| 8 | multi_query | 0.800 | 1.000 | 0.900 | 58s |

## Core concepts

### 1. The three-way split: instant / moderate / expensive
```
0.2s:  vector, hybrid, filtered  → r@1=0.900
30-60s: query_rewrite, multi_query → r@1=0.800-0.900
230-465s: self_rag, crag, agentic  → r@1=0.900-1.000
```

The latency/quality curve is not smooth. The first tier (instant) is the practical default for real-time RAG. The third tier is for async workflows. The middle tier (LLM-augmented) pays latency without consistent recall gain on this corpus.

### 2. Agentic won by discovering hybrid retrieval
The persistent miss ("How is dense retrieval different from BM25?") was closed by the agentic retriever — not because the agent was told to use both tools, but because it reasoned its way to keyword + vector search across steps. This is the qualitative difference between agentic and algorithmic retrievers: the agent can discover strategies.

### 3. Multi-query consistently loses — confirmed
multi_query = 0.800 is consistent across both checkpoint 5.3 (0.800) and the full benchmark. Union noise on 8 chunks is reproducible. This is a validated finding, not a one-off.

### 4. Self-RAG's recall@3=0.900 — the filter penalty
All other retrievers hit recall@3=1.000. Self-RAG's relevance filter drops chunks from the candidate pool, shrinking the top-3 window. The faithfulness query's correct chunk was dropped as marginally relevant. Tuning `min_relevant_chunks` or relaxing the relevance threshold would recover this.

### 5. CRAG at 465s is the most expensive mediocre retriever
CRAG matched the baseline at 0.900 but took 465s for 10 queries (46s/query). On this clean corpus, the correction mechanism added overhead but no benefit. CRAG's value shows on noisy corpora where first-attempt precision is low — the correction loop recovers from initial retrieval failures.

### 6. The central production trade-off
```
vector:  r@1=0.900, 0.02s/query   → 1 miss per 10 queries, instant
agentic: r@1=1.000, 23s/query    → perfect, 23s per query
```

Is 11% recall improvement worth 1150× latency? Application-dependent:
- Real-time chat: NO
- Research assistant: YES
- Batch document analysis: YES
- Enterprise search: depends on SLA

### 7. The benchmark infrastructure transfers; the result doesn't
On a 10K-chunk corpus with diverse vocabulary and query types, the picture would change: hybrid would show its advantage over pure vector, multi-query would show lift on ambiguous queries, CRAG would show lift on noisy retrievals. The 8-chunk result is directional. The infrastructure runs on any corpus in minutes.

## Interview flashcards

1. **Q:** Why did agentic achieve perfect recall when algorithmic hybrid didn't?
   **A:** The agentic retriever chose to use both keyword and vector search across its steps based on its own reasoning — it discovered hybrid retrieval was needed without being told. Algorithmic hybrid always uses both tools. The agentic retriever used them in a different order and combination that happened to cover the failing query's correct chunk.

2. **Q:** CRAG took 465s for 10 queries but matched baseline at 0.900. Should you deploy CRAG?
   **A:** Not on this corpus — the correction mechanism adds 46× overhead with zero quality gain. CRAG earns its cost on noisy corpora where first-attempt precision is low. On a well-curated corpus, first-attempt retrieval is already high quality and correction adds nothing. Always benchmark on your actual corpus.

3. **Q:** Self-RAG scored recall@3=0.900 while all others scored 1.000. Why?
   **A:** The relevance filter removed a chunk from the top-3 candidate pool that would have contributed to recall@3. The filter was slightly too aggressive — it filtered a genuinely relevant chunk that had a chunk boundary artifact (mixed content). Tuning `min_relevant_chunks` or reducing filter strictness would recover the recall@3.

4. **Q:** Multi-query scored 0.800 again. Why is this finding important?
   **A:** It's reproducible — same result across checkpoint 5.3 standalone test and the full benchmark. Reproducibility validates that it's a real finding, not a one-off. The failure mode (union noise on small corpora) is documented and explained. This is how scientific benchmarking works: run the same test on the same data and get the same answer.

5. **Q:** How would you select a retriever for production?
   **A:** Three-axis decision: (1) latency budget — real-time needs sub-100ms, eliminates LLM-augmented; (2) corpus size and quality — large noisy corpora benefit from CRAG/Self-RAG, small clean ones don't need it; (3) query complexity — simple factoid needs vector, complex multi-document needs agentic. Vector retrieval is the right default; upgrade based on measured need.
