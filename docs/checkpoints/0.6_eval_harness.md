## Core concepts

### 1. Evaluation as science, not vibes
Every claim about "this new chunker is better" has to be backed by a number, measured on the same gold set, with the same metric. That's what makes the swap-and-measure loop trustworthy. Without a harness, "better" becomes "feels better to me" — the biggest single failure mode of ML projects.

### 2. The gold set is the foundation
Ours is 10 query→relevant-text pairs — deliberately small enough to hand-curate carefully, large enough to give stable averages. Each entry is:
```python
{"query": "What is BM25?",
 "relevant_text": "BM25 is a sparse retrieval algorithm..."}
```
The `relevant_text` is a **substring the correct chunk must contain**. It's the ground truth — a human's judgment that this text is what the retriever should have found.

**Gold set quality dominates every downstream metric.** A biased or sloppy gold set means you're optimizing for the wrong thing. Real production teams spend disproportionate effort here.

### 3. Retrieval metrics decomposed

**Recall@k** — did the top-k results contain a relevant chunk?
- Binary per query (1 if any relevant chunk in top-k, else 0)
- Averaged across queries
- **Interpretation**: "How often does the right answer appear at all in what we retrieved?"

**MRR (Mean Reciprocal Rank)** — how *high* did the first relevant chunk rank?
- `1 / rank` of first relevant, or 0 if none
- Rewards putting the best chunk first
- **Interpretation**: "How much did we make the LLM's job easy?"

**recall@1 vs recall@3 gap** — diagnostic signal
- Small gap → retriever is confident *and* correct
- Large gap → relevant chunks are in the top-3 but not always at #1
- **Fix for a large gap: reranking (M6).** You're literally seeing why rerankers exist in the metrics.

Our baseline: recall@1 = 0.8, recall@3 = 1.0. Gap of 0.2 → strong reranker signal.

### 4. Faithfulness — the generation metric
Our implementation: fraction of the answer's **4-grams** (4-word sequences) that appear literally in some retrieved chunk. Grounded answers score high; hallucinated content scores low.

**Known limitations:**
- Penalizes paraphrasing (semantically correct rewording gets 0)
- Rewards copying (parroting chunks scores 1.0 but is bad UX)
- Blind to logical entailment

**Why we use it anyway:** it's cheap, deterministic, no API calls, no LLM judge. Directionally useful — a model that drops from 0.7 → 0.4 has probably started hallucinating. Real production uses LLM-as-judge or NLI models (bge-nli, entailment models) on top of this. For a scientific baseline where the *change* matters more than the absolute value, 4-gram is fine.

### 5. Boundary-tolerant relevance matching
Original substring match failed on chunks where boundaries cut the gold text ("Evaluation → etrics"). Fix: sliding-window word matching with `min_overlap=0.6` — a chunk is relevant if at least 60% of the gold text's words appear consecutively in the chunk.

**The meta-lesson: your eval harness is software too.** Bugs in the evaluator make correct systems look broken. Every zero-score should be double-checked before it's believed. This is a general engineering principle — instruments themselves need validation.

### 6. Rate-limit awareness
Free-tier LLM APIs have concurrency caps (Nemotron's 32-request limit hit us). The runner uses `time.sleep(2.0)` between generation calls and wraps them in `try/except` so one failure doesn't kill the whole run. **Production eval harnesses handle rate limits, retries, and partial-failure gracefully** — otherwise a large benchmark run gets wrecked by the 47th query.

### 7. Retrieval eval ≠ generation eval
- **Retrieval eval**: fast, deterministic, no API cost. Run every commit.
- **Generation eval**: slow, non-deterministic (even with temp=0, providers can drift), costs money or rate-limits.
- Design the runner so retrieval-only can run independently. Ours does — `run_generation=False` skips API entirely.

This split is how mature teams keep CI cheap while still measuring end-to-end quality.

## Why the design choices

- **10 queries, not 100**: hand-curation quality > quantity for a personal project. Bad gold entries poison metrics silently. Grow gradually.
- **Substring + fuzzy match**: readable ground truth. Alternative (chunk-ID mapping) is more precise but reindexing invalidates it every time.
- **`try/except` around generation**: partial results are more useful than no results. A benchmark that dies at query 5 of 100 taught you nothing.
- **Aggregated + per-query in output**: aggregates give the headline; per-query tells you *which* queries broke, which is what you actually debug.
- **Metrics as pure functions**: `recall_at_k(retrieved, relevant_text, k)` has no state. Easy to test, easy to swap.

## Interview flashcards

1. **Q:** Why did you build an eval harness before adding more chunkers or embedders?
   **A:** Because "did this help?" is unanswerable without measurement. Adding more components without a harness produces a bigger project that no one can tune. Eval-first is the difference between engineering and vibes.

2. **Q:** What's the difference between recall@k and precision@k?
   **A:** Recall@k asks "of all relevant items, how many appeared in the top-k?" Precision@k asks "of the top-k retrieved, how many were relevant?" In RAG with one relevant chunk per query, recall@k is binary (was it found?) and precision@k = recall@k / k. For queries with multiple relevant chunks, they diverge and both matter.

3. **Q:** What is MRR and why do you need it separately from recall?
   **A:** Mean Reciprocal Rank averages `1/rank` of the first relevant result. Recall@3 = 1.0 tells you the answer is *somewhere* in the top-3, but MRR tells you *where*. An MRR of 1.0 means always at #1. An MRR of 0.5 means often at #2. Recall says "did we find it?"; MRR says "how much did we make the downstream generator's job easy?"

4. **Q:** Your faithfulness metric penalizes paraphrasing. Why use it anyway?
   **A:** Directional utility. It's cheap enough to run on every experiment, and the *change* between two configurations is more informative than the absolute value. A shift from 0.7 to 0.4 signals worsening grounding regardless of paraphrasing effects. For absolute assessment, production systems use LLM-as-judge or NLI models — those are M8-level upgrades.

5. **Q:** How large should a gold set be?
   **A:** Big enough for stable averages (10 queries: expect ±10% swings; 100 queries: ±3%; 1000: ±1%). Small enough to hand-curate carefully. Start at 20–50 for a personal project, grow to hundreds for production. Automated gold-set generation using an LLM is possible but risks encoding LLM biases into your ground truth.

6. **Q:** How would you detect a bug in your eval harness?
   **A:** Any zero score should be diagnostically inspected before it's believed. Look at what the retriever actually returned versus what the gold set expected. In our case, `Evaluation → etrics` was a boundary artifact — the retriever was correct, the matcher was wrong. Zero-score queries are almost always either a real regression or an evaluator bug.

7. **Q:** Why separate retrieval and generation evaluation?
   **A:** Cost and speed. Retrieval eval is pure CPU/GPU, deterministic, free. Generation eval hits paid APIs and is non-deterministic. In CI, you want retrieval eval on every commit — under a minute — and generation eval on a schedule or before releases. Coupling them means either everything is slow or nothing is measured.

8. **Q:** Your baseline shows recall@1 = 0.8 but recall@3 = 1.0. What does that tell you?
   **A:** The correct chunk is always in the top-3 but sometimes at rank 2 or 3 instead of 1. That's exactly the failure mode a reranker fixes: retrieve broadly with a fast bi-encoder, then rerank the top candidates with a more accurate cross-encoder. My baseline metrics are literally motivating M6.

9. **Q:** What are three ways your faithfulness metric could be fooled?
   **A:** First, a model that copies chunk text verbatim gets high faithfulness but produces terrible UX. Second, a model that paraphrases correctly gets low faithfulness. Third, a model that says a correctly-cited claim followed by a hallucinated one gets partial credit — the metric averages over 4-grams and can't distinguish grounded vs ungrounded segments. Production faithfulness eval decomposes the answer into claims and checks each against the context using an NLI model.

10. **Q:** How would you extend this eval harness for multi-hop questions?
    **A:** Multi-hop queries need multiple relevant chunks. The gold entry would list all of them: `{"query": ..., "relevant_texts": [...]}`. Recall@k would be redefined: "fraction of the relevant chunks that appeared in top-k." A new metric — retrieval completeness — would matter: did we get all of them or only some? Faithfulness stays the same but the context assembly logic gets richer.
