# Checkpoint 8.1 — Gold Set Expansion

## What we built
- `gold_set_v2.py` — 12 typed, annotated queries across four categories
- Query types: factoid (5), comparison (3), thematic (2), negative (2)
- Difficulty levels: easy (4), medium (6), hard (2)
- Accessor functions: get_by_type(), get_by_difficulty(), get_positive_queries(), get_negative_queries()

## Core concepts

### 1. Why query typing matters
The original 10-query gold set was all specific factoid questions. Aggregate recall@1=0.900 looked like "one miss." With typed queries, you can say "recall@1=0.800 for factoid, 0.667 for comparison, 1.000 for thematic" — a completely different actionable diagnosis.

**The four types serve different evaluation purposes:**
- **Factoid:** tests basic retrieval — can you find the right chunk for a simple question?
- **Comparison:** tests cross-concept retrieval — can you find chunks about two related concepts?
- **Thematic:** tests synthesis — can you retrieve a chunk that covers a multi-faceted question?
- **Negative:** tests robustness — do you correctly say "not in context" when the answer isn't there?

### 2. Why negative queries are the most important addition
A RAG system that returns chunks for "What is the capital of France?" is actively harmful — it will either confuse the generator or cause it to hallucinate an answer that sounds authoritative but is based on irrelevant context. Negative queries test whether the system knows what it doesn't know.

Three mechanisms can handle negatives:
- **Retrieve gate (Self-RAG):** decides before retrieval whether to retrieve
- **System prompt:** "if not in context, say so" — cheapest, works for clean off-topic queries
- **Faithfulness checking:** post-generation verification against retrieved context

Our evaluation showed the system prompt alone achieves decline_rate=1.0 — for clean off-topic queries, the most expensive mechanism isn't needed.

### 3. Difficulty annotation drives targeted evaluation
```
easy:   r@1=1.000  faith=0.889  ← should be perfect baseline
medium: r@1=0.667  faith=0.708  ← where the interesting failures live
hard:   r@1=1.000  faith=0.000  ← retrieval works, generation quality is the issue
```

The hard query (dense vs BM25 comparison) retrieves correctly but the generated answer paraphrases the source — triggering NLI false positive. Without difficulty annotation, this failure mode would be hidden in aggregate metrics.

### 4. The negative query expected_chunks=0 convention
```python
{
    "relevant_text": "",   # empty = not in corpus
    "expected_chunks": 0,  # system should return nothing
}
```
The empty `relevant_text` signals to the evaluator that this is a negative query. `expected_chunks=0` documents the expected system behavior. This convention makes the evaluation logic trivial — `if not relevant_text: is_negative = True`.

## Interview flashcards

1. **Q:** Why do you include negative queries in your gold set?
   **A:** To test whether the system correctly handles questions whose answers aren't in the corpus. A system that returns chunks for "What is the capital of France?" will hallucinate an answer from irrelevant context. Negative queries measure the decline rate — the fraction of off-topic queries the system correctly refuses to answer.

2. **Q:** Your original gold set had 10 factoid queries. What's wrong with only factoid queries?
   **A:** Factoid queries test a single retrieval pattern (find one relevant chunk). They don't test comparison (find two related chunks), synthesis (aggregate multiple chunks), or robustness (don't retrieve for off-topic queries). A system that scores 0.900 on factoid queries might score 0.333 on comparison queries — completely different architecture implications.

3. **Q:** What's the difference between difficulty levels in your gold set?
   **A:** Easy queries have exact keyword matches in the corpus — any retriever should find them. Medium queries require semantic understanding — the query language differs from the document language. Hard queries require cross-concept reasoning or have multiple valid interpretations. The difficulty annotation lets you measure where your system degrades.

4. **Q:** How do you programmatically identify negative queries in your evaluator?
   **A:** By empty `relevant_text` field. When `relevant_text = ""`, the evaluator treats it as negative — no recall/MRR computation, instead measures whether the system correctly declined. This convention avoids a separate boolean flag and keeps the gold set format simple.

5. **Q:** Your gold set has 12 queries. Is that enough for a rigorous evaluation?
   **A:** For a learning project on an 8-chunk corpus — yes. For production: no. Production benchmarks use 100-1000 queries with human-labeled relevance judgments. Our 12-query set is representative for comparing configurations (is hybrid better than vector?) but not for absolute quality claims. The infrastructure scales — adding queries is one dictionary entry.

# Checkpoint 8.2 — Retrieval Evaluator

## What we built
- `RetrievalEvaluator` — formal typed evaluation with nDCG, per-type breakdown, negative query handling
- `ndcg_at_k()` and `precision_at_k()` added to eval/metrics.py
- Key finding: comparison queries r@1=0.333 (Vector) → 0.667 (Hybrid+Rerank)
- neg_acc=0.0 for both deterministic retrievers — expected

## Core concepts

### 1. nDCG — why it's better than recall for position-aware evaluation

**recall@3:** correct chunk at rank 1 = 1.0, at rank 3 = 1.0 (same score — ignores position)
**MRR:** correct chunk at rank 1 = 1.0, at rank 3 = 0.33 (position-aware, binary)
**nDCG@3:** correct chunk at rank 1 = 1.0, at rank 2 = 0.63, at rank 3 = 0.50 (position-aware, graded)

```
DCG@k  = Σ rel_i / log2(i+1)  for i in 1..k
IDCG@k = DCG of perfect ranking (1/log2(2) = 1.0 for binary relevance at rank 1)
nDCG@k = DCG@k / IDCG@k
```

nDCG is the standard metric in TREC, BEIR, and MS MARCO benchmarks because it matches user behavior — users click the top result most often. Recall@k doesn't distinguish "found at rank 1" from "found at rank 5."

### 2. Per-type breakdown — the actionable diagnosis
```
Vector retriever:
  factoid:    r@1=0.800  ← one miss (faithfulness query chunk placement)
  comparison: r@1=0.333  ← two misses (requires cross-concept retrieval)
  thematic:   r@1=1.000  ← perfect

Hybrid+Rerank:
  comparison: r@1=0.667  ← one miss (cross-encoder fixed one comparison miss)
```

Without per-type breakdown: "Vector r@1=0.700 → Hybrid r@1=0.800, +14%." With per-type: "Hybrid + cross-encoder specifically fixes comparison query retrieval while having no effect on factoid." Completely different guidance for next steps.

### 3. neg_acc=0.0 is expected for deterministic retrievers
Vector and BM25 always return candidates — they have no concept of "the answer isn't here." neg_acc=0.0 is correct behavior for these systems. Only retrieval-gated systems (Self-RAG) or generation-gated systems (grounded system prompt) can handle negatives. The evaluator correctly distinguishes this.

### 4. The retrieval evaluator is O(N × retrievers)
Adding a new retriever to the benchmark is one line: `RETRIEVERS.append(("MyRetriever", my_retriever))`. The per-type and negative breakdowns come for free. The infrastructure cost of adding a new retriever to the formal evaluation is zero.

## Interview flashcards

1. **Q:** What is nDCG and why is it preferred over recall@k for IR evaluation?
   **A:** Normalized Discounted Cumulative Gain weights relevance by position — finding the correct result at rank 1 scores higher than at rank 3. recall@k gives equal credit regardless of position. nDCG = DCG / IDCG where DCG = Σ rel_i / log2(i+1). It's the standard metric in academic IR benchmarks because it matches user click behavior — users engage most with top results.

2. **Q:** Comparison queries scored r@1=0.333 with Vector and 0.667 with Hybrid+Rerank. What explains the improvement?
   **A:** The cross-encoder reranker sees query+chunk jointly — it can reason about the specific contrast relationship "different from" connecting "dense" to "BM25." The bi-encoder can't express this token-level relationship. The hybrid retrieval also ensures both sparse and dense signals contribute candidates, improving coverage for cross-concept queries.

3. **Q:** Why is neg_acc=0.0 for deterministic retrievers not a failure?
   **A:** Deterministic retrievers (BM25, dense) are designed to always return candidates. They have no mechanism to judge whether the answer exists in the corpus. neg_acc=0.0 is correct architectural behavior — these systems need a separate layer (Self-RAG gate, grounded system prompt) for negative query handling. The evaluation correctly measures this as a distinct capability.

4. **Q:** Your gold set has only 3 comparison queries. Is that enough to measure comparison query performance?
   **A:** No — 3 queries has high variance. One miss = 0.667, two misses = 0.333. For production evaluation, you'd want 20+ comparison queries for stable estimates. Our 12-query set is sufficient for comparing configurations directionally, not for absolute performance claims.

5. **Q:** How does the per-type breakdown change your architecture decisions?
   **A:** Instead of "we need 14% better retrieval overall," you know "we need better cross-concept retrieval specifically." This points to: multi-hop retrieval (fetch concept A, then concept B), larger chunk size (more context per chunk), or better reranking for comparative queries. Aggregate metrics give you a target; typed breakdowns give you a direction.

# Checkpoint 8.3 — Generation Evaluator

## What we built
- `GenerationEvaluator` — faithfulness, citation coverage, answer relevance, negative decline
- Per-type generation breakdown: comparison/factoid/thematic
- Automatic negative decline detection via phrase matching
- Key results: faith=0.700, rel=0.815, cov=0.366, decline_rate=1.0

## Core concepts

### 1. The four generation quality dimensions

**Faithfulness (0.700):** fraction of answer claims supported by retrieved context. 0.700 means 30% of claims are flagged — mostly NLI false positives on paraphrased claims. True hallucination rate is lower.

**Citation coverage (0.366):** fraction of retrieved chunks that appear in the answer's citations. 0.366 means the model cites ~1 of 3 retrieved chunks. For focused answers, this is appropriate. For synthesis answers, it suggests the model isn't using all relevant context.

**Answer relevance (0.815):** RAGAS reverse-question score. 0.815 means answers are clearly on-topic. Comparison queries score highest (0.855) because comparative answers are richer and generate better reverse questions.

**Decline rate (1.0):** fraction of negative queries correctly declined. 1.0 = perfect — the grounded system prompt handles all off-topic queries without Self-RAG overhead.

### 2. Citation coverage reveals answer strategy
```
coverage=0.33: model cites 1 of 3 chunks (focused single-source answer)
coverage=0.67: model cites 2 of 3 chunks (synthesis from multiple sources)
```
The dense/BM25 comparison query achieved coverage=0.67 — the model correctly cited both the dense chunk and the BM25 chunk. Simple factoid queries used only 1 chunk.

### 3. Negative decline via phrase matching
```python
NOT_IN_CONTEXT_PHRASES = [
    "not in context", "does not contain", "no information",
    "not mentioned",  "cannot find",      "not found",
    "don't have",     "no relevant",
]
```
Phrase matching is simpler and more reliable than an LLM classifier for this binary task. The grounded system prompt produces predictable decline phrasings — pattern matching catches them reliably. LLM classification adds latency with no accuracy benefit.

### 4. Per-type faithfulness breakdown
```
thematic:   faith=0.500  ← synthesis answers = more paraphrase = more NLI false positives
factoid:    faith=0.800  ← direct answers = more verbatim = better NLI scores
comparison: faith=0.667  ← mixed
```
Thematic queries score worst on faithfulness because synthesis requires connecting concepts with transitional language that NLI flags as paraphrase. This is an NLI calibration issue, not a faithfulness issue.

## Interview flashcards

1. **Q:** Citation coverage=0.366 means the model cites 1 of 3 chunks. Is this good or bad?
   **A:** Context-dependent. For focused factoid answers, citing 1 specific chunk is correct — the other 2 chunks aren't needed. For synthesis answers, low coverage means the model isn't using all relevant context. The right target depends on query type: factoid coverage 0.33 is fine; thematic coverage 0.33 may indicate under-utilization of context.

2. **Q:** Your decline rate is 1.0 without Self-RAG. Does this mean Self-RAG is unnecessary?
   **A:** For clean off-topic queries (capital of France, pgvector), yes — the grounded system prompt handles them at zero extra latency. Self-RAG's retrieve gate adds value when: the boundary between "in corpus" and "not in corpus" is ambiguous, when users phrase off-topic queries using corpus vocabulary, or when you want to skip retrieval entirely for parametric queries (saves 2ms + compute).

3. **Q:** Thematic queries have the lowest faithfulness (0.500) but highest relevance (0.912). What does this tell you?
   **A:** Synthesis produces rich, on-topic answers that may paraphrase the source. NLI flags paraphrase as unfaithful; the answer is actually grounded. This is an NLI calibration issue, not a faithfulness issue. The combination of high relevance + low faithfulness signals: answer is correct and on-topic, but the faithfulness checker is too strict.

4. **Q:** How do you distinguish NLI false positives from genuine hallucinations in production?
   **A:** Three signals: (1) if relevance is high and faithfulness is low → likely NLI false positive (answer is on-topic but paraphrased). (2) If the unsupported claims are specific facts not in the corpus (dates, names, statistics) → genuine hallucination. (3) Add a second-pass LLM check when NLI says unsupported — if LLM says supported, trust LLM.

5. **Q:** How do you use generation metrics to trigger different actions in production?
   **A:** faith < 0.5 AND rel < 0.6 → bad retrieval, regenerate with different context. faith < 0.5 AND rel > 0.7 → good answer but possible hallucination, flag for review. faith > 0.8 AND rel < 0.5 → grounded but evasive, retry with better prompt. decline_rate < 0.8 → system is answering questions it shouldn't, tune system prompt.

# Checkpoint 8.4 — Pipeline Evaluator

## What we built
- `PipelineEvaluator` — single entry point for unified retrieval + generation evaluation
- Per-type and per-difficulty breakdowns in one pass
- Complete 12-query run: r@1=0.800, faith=0.692, rel=0.822, decline=1.0
- Key insight: hard queries have best relevance (0.950) despite faithfulness issues

## Core concepts

### 1. Single-pass unified evaluation
Rather than running retrieval eval then generation eval separately, PipelineEvaluator runs one pass:

```
for query in gold_set:
    candidates = retriever.retrieve(query)          # retrieval metrics
    answer     = generator.generate(query, chunks)  # generation
    faith      = faith_checker.check(answer, chunks) # faithfulness
    rel        = rel_scorer.score(query, answer)    # relevance
    row        = merge(retrieval_metrics, gen_metrics)
```

One run, all metrics. Avoids running the full pipeline twice (once for retrieval, once for generation). Critical for CPU-bound systems where each query takes 16+ seconds.

### 2. The hard query paradox
```
hard queries:   r@1=1.000  faith=0.000  rel=0.950
```
The hardest retrieval query (dense vs BM25 comparison) retrieved perfectly, produced the most relevant answer (0.950), but got flagged as unfaithful (0.000). Three things are simultaneously true:
- Retrieval is perfect (correct chunks at rank 1)
- Generation quality is excellent (most relevant answer)
- Faithfulness checker is wrong (NLI false positive on paraphrased claims)

This paradox would be invisible without per-difficulty breakdown.

### 3. Medium difficulty is the systematic failure zone
```
medium: r@1=0.667  ← 2 retrieval misses
easy:   r@1=1.000  ← perfect
hard:   r@1=1.000  ← perfect (cross-encoder fixes the hard one)
```
The two retrieval misses are both medium difficulty: "faithfulness in RAG evaluation" and "cross-encoder rerankers work." Both are about concepts that appear within larger paragraphs rather than being primary paragraph topics. The fix isn't a better retrieval algorithm — it's smaller chunk sizes that isolate these concepts.

### 4. The evaluator is the regression test
Running PipelineEvaluator before and after any architecture change tells you whether the change improved or degraded quality:
- Changed chunking strategy → did recall@1 improve?
- Changed NLI model → did faithfulness improve?
- Changed system prompt → did decline_rate improve?
- Changed embedding model → did nDCG improve?

Without a pipeline evaluator, you're deploying blind. With one, every change has a measurable impact.

## Interview flashcards

1. **Q:** Why run retrieval and generation in one pass rather than separately?
   **A:** Efficiency on CPU-bound systems. Each query takes 16s on CPU — running two passes doubles that to 32s. More importantly, the single-pass result links retrieval and generation quality for the same query — you can see "this query retrieved perfectly but generated poorly" vs "this query retrieved poorly and generated poorly." The causal chain matters.

2. **Q:** Hard queries scored r@1=1.000 but faith=0.000. What does this paradox tell you?
   **A:** Three things are simultaneously true: retrieval is perfect, the answer is highly relevant (0.950 relevance), and the NLI faithfulness checker is producing a false positive on a paraphrased claim. The paradox reveals a calibration issue with the NLI checker specifically for comparative paraphrase claims. Without the per-difficulty breakdown, this would be hidden in aggregate faithfulness=0.69.

3. **Q:** Medium difficulty queries have r@1=0.667. Why do medium queries fail more than hard ones?
   **A:** Hard queries (dense vs BM25 comparison) are hard conceptually but the cross-encoder reranker handles them. Medium queries fail because the relevant content appears as a sub-paragraph within a larger chunk, not as the primary topic. The retrieval algorithm works correctly; the chunk granularity is wrong. Fix: smaller chunk sizes for medium-difficulty concept coverage.

4. **Q:** Your pipeline evaluator took 16s/query on CPU. How do you make it faster?
   **A:** Three parallelizable stages: retrieval (2ms) + generation (7s) + quality checks (9s). Parallelize quality checks: run faithfulness and relevance concurrently with `asyncio.gather()` — reduces 9s sequential to ~6s parallel. Use GPU for generation: drops 7s to 0.5s. Total with GPU + parallel quality: ~3s/query. For batch evaluation, process 4 queries concurrently on GPU: ~1s effective/query.

5. **Q:** How would you use this pipeline evaluator in a CI/CD pipeline?
   **A:** Add a `scripts/ci_eval.py` that runs PipelineEvaluator on a 20-query gold set and compares results against a baseline JSON file. If recall@1 drops by >5% or faithfulness drops by >10% vs baseline, fail the CI build. This prevents merging changes that degrade quality. The gold set becomes your test suite, the evaluator becomes your test runner.

# Checkpoint 8.5 — HTML Evaluation Report

## What we built
- `generate_report()` — takes results dict, outputs standalone HTML
- Zero external dependencies — CSS-in-style, no JS frameworks
- Color-coded metrics (green/yellow/red thresholds)
- Per-query expandable table with type/difficulty badges
- Two-panel breakdown: by query type + by difficulty

## Core concepts

### 1. Standalone HTML is the right format for portfolio artifacts
PDF: requires Adobe Reader or specific renderer. Notebook: requires Jupyter. Dashboard: requires a server. Streamlit: requires Python environment. HTML: opens in any browser on any platform, can be emailed, viewed offline, shared as a file attachment.

For a portfolio project, the evaluation report is something you'd attach to a job application email or share in a GitHub README link. Standalone HTML is the only format that guarantees the recipient can open it.

### 2. Color thresholds — green/yellow/red
```python
def color(v, lo=0.60, hi=0.85):
    if v >= hi:  return "#16a34a"  # green
    if v >= lo:  return "#ca8a04"  # yellow
    else:        return "#dc2626"  # red
```
These thresholds encode domain knowledge: above 0.85 is good RAG quality, 0.60-0.85 is acceptable, below 0.60 needs work. They make the report self-interpreting — a hiring manager who doesn't know RAG metrics can still read "most metrics are green, faithfulness has some yellow."

### 3. The report is the benchmark output artifact
Run `python scripts/generate_eval_report.py` before and after any architecture change:
- Before: `eval_report_v1.html`
- After: `eval_report_v2.html`

Compare side by side in two browser tabs. No code needed to interpret the diff — the color coding makes improvements/regressions immediately visible.

### 4. The per-query table enables failure diagnosis
Each row shows: query text, type badge, difficulty badge, recall@1, faithfulness, relevance, answer snippet. A row with red recall@1 AND red faithfulness tells a different story than red faithfulness only (retrieval worked, generation failed). The table is the diagnostic layer beneath the summary cards.

## Interview flashcards

1. **Q:** Why did you choose standalone HTML over a Streamlit dashboard for the evaluation report?
   **A:** Portability. Streamlit requires a running Python server. Standalone HTML works offline, can be emailed, opens in any browser without setup. For a portfolio project or client deliverable, the report must be viewable without installing dependencies. HTML is the only format that guarantees this.

2. **Q:** Your color thresholds are hardcoded at 0.60 and 0.85. How would you make them configurable?
   **A:** Add a `thresholds` parameter to `generate_report()`: `thresholds={"lo": 0.60, "hi": 0.85}`. For domain-specific applications, different thresholds apply — a medical RAG system might require faithfulness >0.95 (high = green) vs >0.80. Configurable thresholds make the report domain-adaptable.

3. **Q:** The report shows metric variance across runs (faith=0.700 vs 0.667 in two runs). How do you handle this?
   **A:** Run the evaluation N times and report mean ± std. Add confidence intervals to metric cards. For a single-run portfolio report, note that LLM-based metrics (relevance uses n=1 generation) have variance. For a rigorous production benchmark, n=3 runs with averaged metrics is the right standard.

4. **Q:** A hiring manager opens your report and sees faithfulness=67% in yellow. What does that mean?
   **A:** 67% of extracted claims in generated answers are verified as supported by the retrieved context. The remaining 33% are either NLI false positives (correct paraphrased claims that the NLI model flags) or genuine hallucinations. In context: decline_rate=1.0 means off-topic queries are correctly refused, and relevance=0.82 means answers are on-topic. The faithfulness number is the most conservative quality signal.

5. **Q:** How would you extend this report for a multi-configuration comparison?
   **A:** Add a comparison table: run PipelineEvaluator for each configuration (Vector, Hybrid+MS-MARCO, Hybrid+BGE), collect all results, generate a comparison section showing delta vs baseline configuration. Color-code improvement/regression. The generate_report() function would accept `results_list: list[dict]` instead of a single results dict.
