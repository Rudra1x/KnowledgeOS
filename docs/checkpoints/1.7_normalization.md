# Checkpoint 1.7 — Normalization Pipeline

## What we built
- `Normalizer` ABC — new plugin type; each transformer takes a `Document` and returns a modified `Document`
- `TextCleaner` — Unicode NFC normalization, invisible/control char removal, whitespace collapse
- `LanguageDetector` — confidence-gated language detection with graceful fallback
- `MetadataEnricher` — auto-derived `char_count`, `word_count`, `line_count`
- `NormalizationPipeline` — composable chain of normalizers, applied in order
- All exported from `core` as first-class citizens

## Core concepts

### 1. Normalization is a canonicalization boundary
Every loader emits Documents in its own style. TXT gives raw text. PDF strips headers/footers per page. HTML extracts via trafilatura. Email includes subject prefix. Downstream chunkers/embedders/retrievers need *invariants* — consistent whitespace, consistent Unicode form, consistent metadata fields.

The normalization layer is where all of that gets enforced. After normalization, every Document from every loader has the same invariants.

### 2. Unicode NFC normalization matters silently
"Café" (with é as a single precomposed codepoint) and "Café" (with e + combining acute accent) are visually identical but are different byte sequences. Different byte sequences → different embedding vectors → no retrieval match.

NFC (Canonical Composition) picks the composed form, deterministically. Applied at ingestion, this eliminates a whole class of "mysterious retrieval failures no one debugs."

### 3. Confidence gates beat hard thresholds
We saw this in real time this checkpoint:
- `min_chars=50`: short text falsely detected as Indonesian
- `min_chars=200`: legitimate short French text falls back to English

Both fail. The right pattern is a **confidence gate** — try detection on anything ≥50 chars, but reject the result if the top candidate's probability is below 0.85. langdetect exposes probabilities via `detect_langs()`. Use them.

This generalizes: any time you have a "how confident should I be to accept the model's output" decision, prefer the model's own confidence to a proxy like input length.

### 4. Pipeline pattern separates orthogonal concerns
`TextCleaner` and `LanguageDetector` and `MetadataEnricher` do orthogonal things. Bundling them into one `normalize()` function means every change risks breaking two others.

Small transformers composed in a list is:
- Testable (mock the input, assert the output, per stage)
- Configurable (drop a stage, add a stage, reorder — one line each)
- Debuggable (log after each stage, isolate which one changed what)

This matches how mature data pipelines are built (Airflow tasks, dbt models, LangChain document transformers).

### 5. Order matters — and should be documented
Cleaning must run *before* language detection. Reason: control chars, zero-width chars, and mojibake bias the detector. Running detection first on unclean text gives worse results.

The `NormalizationPipeline` docstring states this invariant explicitly. If someone reorders these later, results silently degrade — the docstring is the guardrail.

### 6. Auto-derived metadata is compound interest
`char_count`, `word_count`, `line_count`. Every downstream stage benefits:
- Chunker uses `char_count` to skip already-tiny docs
- Retriever uses `word_count` for filter thresholds
- Eval uses `word_count` for length-normalized metrics

Compute once at ingestion → available forever. Compute on demand → repeated CPU + inconsistent implementations across stages.

### 7. Determinism for benchmarks
`DetectorFactory.seed = 0` makes langdetect deterministic. Without this, the same input can produce different language outputs across runs — poisoning your benchmarks with hidden noise.

Same principle as `temperature=0` in the generator: eval science requires determinism.

## Why the design choices

- **ABCs for normalizers**: same plugin pattern as loaders/chunkers/embedders — composable, swappable, testable
- **NFC over NFD**: composed form is what most fonts and libraries expect
- **Confidence gates over hard thresholds**: matches the actual failure mode
- **`en` as fallback language**: majority of the training corpus, safest default for unknown
- **Metadata mutation, not copy**: cheap; Documents flow through the pipeline as mutable state
- **`langdetect` over `pycld3` / `fasttext-lid`**: pure Python, no C dependency, adequate quality — trade slight accuracy for reliability

## Interview flashcards

1. **Q:** What is Unicode NFC normalization and why does it matter for RAG?
   **A:** NFC picks the composed form of a character when there are equivalent representations (é as one codepoint vs e + combining acute). Without it, visually identical strings are byte-different, producing different embedding vectors and breaking retrieval. NFC is one line, essentially free, and eliminates a whole class of silent failures.

2. **Q:** You used a confidence gate for language detection. Why not a length threshold?
   **A:** Length threshold has two failure modes. Too low → short text produces low-confidence false positives. Too high → legitimate short-text detection is blocked. A confidence gate uses the model's own uncertainty — try detection on anything long enough to be meaningful, but reject if probability is below 0.85. Matches the actual failure mode.

3. **Q:** Why is normalization a pipeline of small stages rather than one function?
   **A:** Separation of orthogonal concerns. Cleaning, detection, and enrichment do different things. Bundled into one function, every change risks breaking two others. Split into stages, each is testable, configurable, and debuggable independently. Matches how Airflow/dbt/LangChain structure data pipelines.

4. **Q:** In what order do the normalization stages run and why does it matter?
   **A:** Clean → Detect → Enrich. Cleaning must precede detection because control chars and mojibake bias the language detector. Enrichment (word/char count) must come last so it counts the final cleaned text. The docstring documents this invariant so someone reordering doesn't silently degrade quality.

5. **Q:** Why set `DetectorFactory.seed = 0` for langdetect?
   **A:** langdetect is nondeterministic by default — the same input can produce different language guesses across runs. That's poison for benchmarks and reproducibility. Seeding it makes results deterministic. Same principle as `temperature=0` in generation: eval science requires determinism.

6. **Q:** How would you extend normalization for PII redaction?
   **A:** Add a `PIIRedactor(Normalizer)` stage. Run before or after cleaning based on need — spacy NER or presidio for detection, replace matches with `[REDACTED]` or hash. The pipeline pattern absorbs the change trivially — one class, add it to the list, done. That's why the pipeline pattern matters: new requirements don't force refactors.

## Code walkthrough prompt

*"How do you make sure documents from different loaders are consistent downstream?"*

> "Every Document from every loader passes through a normalization pipeline. The pipeline is a list of small transformers, each doing one thing. First, `TextCleaner` runs Unicode NFC normalization — critical because visually identical strings can be byte-different otherwise, breaking retrieval silently. It also strips control chars, zero-width characters, and collapses whitespace runs. Second, `LanguageDetector` — with a confidence gate rather than a length threshold, so short-text noise doesn't produce false positives. `langdetect` is seeded for determinism, and results below 85% confidence fall back to English rather than take a bad guess. Third, `MetadataEnricher` adds char/word/line counts every downstream stage benefits from. Order matters — cleaning must precede detection because garbage in gives garbage out — and the docstring documents that invariant. Adding a new stage (PII redaction, translation, whatever) is one class and one line to append to the pipeline. This is the difference between an ingestion layer that consistently works on any corpus and one that has mysterious 'why doesn't retrieval find this document' bugs from the field."
